**人工反馈后的命名收敛：**

  获取 VM 锁、更新 publication 和登记 TLB 缓存 CPU，同名会掩盖副作用与锁边界。
- 按接收者已经提供上下文的原则，收敛为 `TrapContext::prepare_return()`、
  `ProcessControlBlock::prepare_user_vm()`、`AddressSpace::activate_on(cpu)` 和
  `MmTlbState::attach_cpu(cpu)`。本次只改标识符、调用点和文档，不改变控制流、内存序、
  锁持有范围或架构失效指令。
- `rg` 针对方法定义与调用形式确认源码和架构文档不再使用旧接口；RV64、
  LA64 Docker normal kernel build 分别为 PASS（130.577 秒、133.933 秒），exit 0、无
  timeout/forbidden marker/source mutation。纯命名整理未重复执行 8 核 QEMU；上一轮 QEMU
  证据继续证明未改变的运行语义，本轮双架构编译只证明 cfg 分支和调用点完整。

**为什么拆成基础设施与下一批锁外提交：**

- 当前所有 `AddressSpace::with_tlb_batch()` 调用都在外层进程 VM `spin::Mutex` 持有期间
  完成。若直接在 `TlbBatch::commit()` 内等待远端 ack，目标 CPU 可能正以 IRQ-off 状态
  在 page fault 中等待同一 VM 锁；发起者等目标 IPI，目标等发起者释放锁，会形成确定死锁。
- 因此本批不在既有 batch 内“顺手”加等待。B23 必须在 VM 锁内完成 PTE 写入、generation
  推进和目标快照，把 deferred frame 移交给独立提交对象；释放 VM 锁后才发送 IPI、等待
  ack，最后释放 frame。这个拆分是锁序要求，不是为了人为切小功能。

**激活侧实现与内存序：**

- `MmTlbState` 由 `AddressSpace` 持有，`CLONE_VM` 线程因共享同一个 VM `Arc` 而自然共享
  同一份状态。`generation` 从 1 开始，`observed[cpu]` 从 0 开始，使每个新 MM 在每颗 CPU
  第一次返回用户态前都执行一次明确的本地全用户失效。
- `cached_cpus` 采用只增不减的保守集合。在尚无 switch-out 清 bit 握手时，CPU 即使已经
  离开 MM，也可能保留旧翻译；不清 bit 会多发最多 8 核 IPI，但不会把潜在缓存者漏出目标集。
- trap-return 在恢复用户页表根前，通过进程 VM 锁调用 `prepare_user_vm()`；内部依次调用
  `AddressSpace::activate_on()` 与 `MmTlbState::attach_cpu()`。顺序固定为
  `cached_cpus.fetch_or(AcqRel) -> generation.load(Acquire) -> local invalidate ->
  observed.store(Release) -> generation recheck`；先读 generation 再登记 CPU 会产生漏失窗口。
- 激活登记和未来修改方的 generation/目标快照必须由同一个 VM 锁串行化。DeepSeek 提醒
  “不同 Atomic 之间仅靠各自 Acquire/Release 不自动建立所需顺序”是有价值的；但其建议的
  单独 `generation.fetch_add(AcqRel)` 并不能凭空解决跨原子证明。人工裁决是 B23 继续保留
  共享 VM 锁作为 join-vs-update 的真实同步边界，不采用未经证明的 lockless 修补。

**IPI 与架构失效实现：**

- Per-CPU 新增独立 `user_tlb_request/user_tlb_ack` 和 `USER_TLB_SYNC` reason，不能与
  kernel-global sequence 共用，否则两个并发协议可能互相覆盖确认。
- 发送方先为每个远端目标推进 request，再执行本地全用户失效并发布 reason/doorbell；
  handler 以 Acquire 读取最新 request，执行失效后 Release ack。reason 可以合并，较新
  sequence 对应的全用户失效同时覆盖此前请求；若新请求到达 handler 快照之后，新的 pending
  reason/doorbell 会触发下一轮处理。
- `synchronize_user_tlb_mask()` 只允许在 VM/PTE/runqueue 等普通锁全部释放后调用；等待窗口
  暂时开放本地 IRQ，使两个并发 shootdown 发起者仍可互相处理 IPI。STOP 是不可恢复终态，
  stopped CPU 不会再次使用旧翻译，因此可作为撤映射式同步的终态确认。
- RV64 当前使用无 operand `sfence.vma`，LA64 使用 `invtlb 0x3` 清除全部 `G=0` 项。
  LA64 ASID 尚归 TCB，所以本批故意不传单一 ASID；全 non-global 失效保证正确，精确范围与
  MM-owned ASID/epoch 留到后续优化和独立验收。

### B20 提交与 B21 kernel-global 撤映射/内核栈回收（已提交）

**提交与目标：**

- 按维护者批准提交 B20，commit 为
  `145220d8ba85e5a5eee1a3c0301c69a5a5da0030`（`feat(smp): wake blocked tasks on remote cpus`）。
- B21 补齐动态 kernel-global 映射的撤销半边：远端 CPU 确认 TLB 失效之前，既不释放
  被撤映射 frame，也不归还 kernel-stack slot。由此删除 B19/B20 为规避 stale TLB 而保留
  AP TCB 到关机的 workaround。该批随后按维护者批准提交为
  `bac670710e65d5e62f8e27042c7d6111f1cf906e`。

**为什么不能直接在 `KernelStack::drop` 中撤映射：**

- `Drop` 可能在 task/process 锁的析构链中被触发；若它再获取 `KERNEL_SPACE`、发送 IPI 并
  等待 ack，真实锁序取决于隐式析构位置，极易形成锁反转或在仍使用任务栈时自毁。
- 仅清 PTE 后立刻释放 frame 也不正确：别的 CPU 可以继续通过旧 TLB 访问已复用物理页。
- 因此析构只做不可失败、短临界区的“退休提交”；真正撤映射放到 CPU0 已切回 idle 栈、
  未持普通锁的调度安全点。固定数组队列不在低内存析构路径分配堆内存。

**实现与顺序不变量：**

- HAL 增加固定容量 `KernelStackRetireQueue` 和统一 `kernel_tlb_invalidate()`。RV64 使用无
  operand `sfence.vma`，LA64 使用 `invtlb 0`，这里刻意采用包含 global entry 的全失效；
  当前低频栈回收优先保证语义，范围优化留到测得实际开销后再做。
- `PageMapper::unmap_no_flush()`、`KernelMapper::unmap_page_no_flush()` 与
  `KernelSpace::detach_area_with_start_vpn()` 只在 MM 锁内清 PTE、移出 mapping，并把
  `FrameTracker` 保留在返回对象。`remove_kernel_mapping_synchronized()` 释放 MM 锁后执行
  全核同步，全部 ack（或撤映射场景下的 terminal STOP）到齐才 drop frame。
- shootdown 发送端先为每个目标推进 request sequence，再本地 flush、一次性发布 reason；
  handler 必须先 Acquire 快照 request，再执行 full invalidate，最后 Release ack。先 flush
  后读 request 会让一次旧 flush 错误确认随后到达的新 sequence，因此顺序不可交换。
- 等待 ack 的 `KernelTlbWaitIrqGuard` 保存调用入口 IRQ 状态，并在等待期间临时开放本地
  中断，使两个 CPU 同时 shootdown 时仍能互相处理 IPI。退出时先关中断再恢复入口状态，
  timer IRQ 仍只发布 deferred pending，回到 trap/scheduler 安全点后处理。
- publish 与 unmap 对 STOP 的语义不同：新增映射要交付给仍会运行任务的 CPU，STOP 必须
  报错；撤映射面对已终止且永不再访问共享状态的 CPU，STOP ack 可替代 TLB ack。
- 两架构 `KernelStack::drop` 在 cache 未满时保留已有映射；cache 溢出时仅入退休队列。
  CPU0 每个 idle 调度安全点最多回收 16 项，顺序为 pop → 同步撤映射 → allocator dealloc。
  字节地址必须显式 `VirtAddr::from(bottom).floor()` 后才是 VPN；LA64 的 allocator 编号
  从 1 开始，因此回收时保持既有 `slot + 1` 对称关系。
- init ELF、exec ELF 和 interpreter 的临时 kernel mapping 均改走统一同步撤映射入口；
  删除 `AP_TASK_RETAINED`，zombie TCB 在 idle 栈上正常释放。新增快速 zombie 计数只用于
  观察真实生命周期，不参与生产协议判定。

**focused 测试如何证明不是 test-only 假绿：**

- 新用例每轮创建 `KERNEL_STACK_CACHE_LIMIT + 1 = 129` 个 AP kernel-only 任务，前 128 个
  真实填满 stack cache，第 129 个触发退休队列；随后验证所有弱引用失效，证明 TCB 已析构。
- 回收前后读取每颗 AP 的生产 `kernel_tlb_ack` sequence，要求全部增长；第二轮再创建
  129 个任务，证明已撤销 slot 可以重新分配、同一 VA 可以绑定新 frame 后再次运行与回收。

### B19 提交与 B20 远程 blocked wake

**提交与目标：**

- 按维护者批准提交 B19，commit 为
  `3a5bb9ead418fda07d542b957772cf5f868afaa3`（`feat(smp): enable secondary cpu schedulers`）。
- B20 在不扩张 `TaskStatus` 的前提下，使已经在 AP 运行的受控 kernel-only 任务经真实
  Completion/WaitQueue 阻塞后，可由 CPU0 唤醒并回到最近运行 CPU。普通新任务、用户任务、
  affinity、迁移、steal 和用户 MM 跨核仍不开放；B20 当前未提交，等待维护者人工批准。

**实现与理由：**

- TCB 新增原子 `last_cpu`，初值为无效值；只有本地 RunQueue 成功提交
  `Queued(cpu) -> Running(cpu)` 后才以 Release 记录。该字段不表达 owner，真实归属仍由
  `sched_state` 与 runqueue/current 容器决定，避免为一个唤醒提示新增 `Blocked(cpu)` 状态。
- `TaskManager::try_wake_interruptible()` 保留原有两种竞态结果：提前 wake 赢得
  `Blocking(cpu) -> Running(cpu)` 时只撤销睡眠；idle 先提交 `Blocked` 时，wake 在
  `TASK_MANAGER -> 一个目标 RunQueue` 下唯一提交 `Blocked -> Queued(target)`。
- 目标优先复用 online、已进入 scheduler 且未 STOP 的 `last_cpu`，提示无效时回退 CPU0。
  普通任务从未离开 CPU0，因此现有用户调度行为没有改变。
- 单个 wake 返回目标 CPU，批量 wake 聚合 target mask。外层在释放 `TASK_MANAGER` 和所有
  runqueue 后才调用 `request_reschedule_mask()`；目标本 CPU 被排除，远端 AP 通过
  “先入队、后 doorbell”退出 idle，不在 IPI handler 中获取调度锁。
- focused test 向每个 AP 发布一个任务，所有任务等待同一个 Completion。CPU0 必须先观察到
  每项均为 `Blocked`、current 已清空且目标队列为空，才一次 complete 批量唤醒；任务恢复后
  校验 CPU/current owner，随后正常 Zombie。AP TCB 继续保留到 terminal STOP，未越过
  kernel-global unmap shootdown 尚未完成的生命周期边界。

**DeepSeek 协作与人工裁决：**

- 首次只读设计审查与 GPT/Codex 实现并行，包装器因受测 worktree 指纹变化 fail-closed；
  模型自身 exit 0 且报告可读，但该 job 不作为冻结证据。后续 Docker 验证期间保持源码冻结。
- 采纳报告中“显式 Release/Acquire 发布 `last_cpu`”和“排除 STOP CPU”的防御建议；未采纳
  “relaxed store 必然无 happens-before”的 P0 定级，因为同线程先行写可由后续 release CAS

### B18 提交与 B19 AP 本地调度闭环

**提交与目标：**

- 按维护者批准提交 B18，commit 为
  `4177456d831e675a75e621f0e91ed9455dc502c5`（`feat(smp): split per-cpu run queues`）。
- B19 建立 scheduler-ready 屏障、AP 本地调度循环、`RESCHEDULE` 唤醒和受控
  kernel-only 远程 enqueue。该段记录的是提交前状态；B19 后续已按本日志上方记录
  提交。本地 `cc-codex` job、模型输出和原始 Docker 日志不进入 GitHub。

**实现与理由：**

- `PerCpu` 新增 `scheduler_entered/need_resched`。CPU0 在堆、VFS、task registry 等
  一次性对象完成后以 Release 发布 scheduler-ready，并以 Acquire 等待全部 CPU 进入；
  AP 观察到 Release 后先安装本 CPU 的 kernel page-table root，再进入 `run_tasks()`。
  页表根寄存器属于 CPU-local 状态，CPU0 的 `mm::init()` 不能替 AP 写入。
- `run_tasks()` 分为 CPU0 housekeeping 和 AP 精简循环，但共用
  `dispatch_task()`、current 发布、`__switch` 与 switch-out，避免维护两套 owner 顺序。
  AP 只打开 IPI line，不推进 timer/console/net/FS/OOM；空队列在 IRQ-off 状态重查后
  `wfi/idle`，发布者先入队、释放 runqueue 锁、再发 `RESCHEDULE`，关闭 lost-wakeup 窗口。
- ktest trampoline 不再读取全局“下一任务函数”，入口改为 TCB 不可变字段，避免多 CPU
  首次切入时互相覆盖。focused test 向每个 AP 显式发布一个短任务，验证目标 CPU、
  current、状态、exactly-once、队列清空和后续 STOP。
- 新动态 kernel stack 只由创建者完成本地 PTE flush。为避免 AP 激活页表后仍使用旧翻译，
  远程发布增加 `kernel_tlb_request/ack`：释放 `KERNEL_SPACE` 锁后发 IPI，目标 hard IRQ
  执行本地全失效并 ack；确认后才入目标 runqueue。等待期间不持有 MM/PTE/runqueue 锁。
- AP 使用过的测试 TCB 保留到终态 STOP 后关机，避免通用 kernel-global unmap shootdown
  完成前释放并复用栈地址。普通用户任务、blocked wake、生产 target、迁移和 work stealing
  均未开放；AP 短任务运行时 IRQ-off，STOP 最长延迟到函数返回或主动 yield。

### B17 提交与 B18 Per-CPU RunQueue

**实现与原因：**

- OOM 路径按 CPU、索引逐个克隆候选 `Arc`，不在低内存场景为全队列快照额外分配。

### HAL v2 + FDT 平台抽象重构 — 方案规划与 fdt crate fork

**背景：**
