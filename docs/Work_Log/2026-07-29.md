## PageCache pwrite 瓶颈深度分析

**涉及文件：**
- `os/src/fs/page_cache.rs` — `write_with_copy_callbacks` (~1378), `write_with_copy_callbacks_locked` (~1395), `prepare_write_lease` (~824), `commit_write_lease` (~913), `acquire_existing_write_lease` (~885), `balance_dirty_pages_for_write` (~81)
- `os/src/fs/ext4_lwext4/layout.rs` — `write_at` (~924), `sync` (~785)
- `os/src/mm/frame_allocator.rs` — `frame_alloc` (~920)
- `os/src/syscall/fs/common.rs` — `pwrite_from_user` (~944)

**分析结论：**

1. **656K cycles 并非 PageCache 纯业务开销**。主要成分为：
   - `perf_time_now_unconditional()` 读全局 `mcycle` CSR → 测量窗口捕获了单核 4 线程环境下其他线程的工作（~90%）
   - `spin::Mutex` 在 QEMU TCG 下的原子指令翻译放大（`lr.w/sc.w` CAS loop → 每条数十条 host 指令）
   - `frame_alloc()` 清零 4KB 在 TCG 下被放大到 ~100K cycles（6.25% 调用中）

2. **PageCache 纯业务路径**（复用页）：~3,700–5,500 cycles。首次分配页 ~130K cycles。加权平均 ~12,400 cycles。

3. **Linux 对比**：Linux per-folio 锁 + RCU page cache lookup + per-CPU PCP 脏页记账，1KB buffered write 约 3,000–8,000 指令。MangoCore 差距在锁粒度（per-file io_gate vs per-page folio_lock）和分配器清零的 TCG 放大。

4. **close/sync 691M cycles**：~58% 是 256 页 VirtIO 块写入，~20% VirtIO FLUSH，~14% lwext4 cache flush，~7% journal/inode 提交。

5. **推荐优化优先级**：
   - P0：`frame_alloc` 对全页覆盖写使用 `frame_alloc_uninit()`（跳过 4KB 清零）→ 消除 ~65% 的首次页分配成本
   - P1：提升 pwrite chunk size（`IO_CHUNK_SIZE`）→ 减少 io_gate 加锁次数 64x
   - P2：`io_gate` 改为单核 yield 锁 → 减少 spin 浪费

6. **可达目标**：P0+P1 落地后 iozone writers 可达 **2,000–3,000 kB/s**（QEMU TCG 下，受 icount 速率限制）。

**验证：** 纯分析，无代码变更。基于已归档的 `docs/Work_Log/evidence/2026-07-29/pwrite-phase-timing.md` 中的 RV64 cycle 数据。
