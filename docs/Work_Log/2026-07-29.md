### B26 LoongArch ASID+VPN 精准 shootdown 与固定原子槽

**目标与架构依据：**

- B25 已使 ASID 归 MM 所有，但 LA64 单页修改仍退化为 `invtlb 0x3` 全 non-global
  失效。B26 不增加第二条 MM 提交链，只给现有 `MmuGather -> TlbFlush` 补齐页级后端。
- LoongArch 官方手册规定 `invtlb 0x5` 按 `G=0 + ASID + VA` 匹配；Linux LoongArch
  `local_flush_tlb_page()` 同样取得目标 MM 的 ASID，并把 VA 对齐到
  `(PAGE_MASK << 1)`。这是因为普通 TLB entry 同时覆盖相邻偶/奇页，所以 LA64 的
  最小硬件粒度是一个对齐 8 KiB 页对，不能把它描述成只清一个 4 KiB 页。

**实现与并发边界：**

- `MmuGather::seal()` 在原有 VM 锁持有期同时冻结 target mask、MM-owned ASID 和 VPN，
  再构造唯一 `TlbFlush`。解锁后不读取当前 `CSR.ASID`，避免发起 CPU 正运行其它 MM，
  也避免 rollover 与本轮失效上下文拼成不同快照。
- `smp.rs` 增加固定的 `MAX_CPUS` 个 `UserTlbPageSlot`，每个发起 CPU 独占一个槽。
  payload 由 `asid/vpn/targets` 组成，以 targets 的 Release store 发布；handler 对
  targets 做 Acquire load，扫描全部槽，执行架构失效后才写 ack。这样多个发起者即使
  共用一个幂等 reason bit，也不会覆盖彼此 payload；hard IRQ 路径不分配内存、不获取
  普通锁。
- 正常完成时，发起者收齐所有 live target ack 后才复用槽并释放退休 frame。timeout
  时故意保留 claimed slot，随后由既有 `TlbFlush` fail-stop；迟到 doorbell 因而只能看见
  旧 payload，不能把旧中断错配到新请求。目标已 STOP 时等价于完成 ack，因为该 CPU
  不会再使用旧用户翻译。
- RV64 仍优先调用同步 SBI RFENCE；固件返回不支持时也可使用同一固定槽，当前传入
  ASID 0，保持原 `sfence.vma va, zero` 的全 ASID 匹配语义。真正的 RV64 MM-owned
  SATP ASID 与 `REMOTE_SFENCE_VMA_ASID` 留给 B27。

**测试与人工裁决：**

- 增加生产接口测试：真实 `AddressSpace` 先激活取得 ASID，再调用页级同步，并断言
  `user_tlb_request` 不增长，防止实现悄悄退回全用户 flush。
- 增加 8 核并发用例：CPU0 与所有 AP 共享同一个 MM/ASID，同时发布各自不同且按 LA64
  页对隔开的 VPN；等待全部任务结束，并断言所有 CPU 的 full-request 计数不变。该用例
  证明多 slot payload 隔离，不代表“不同 ASID 并发”；MM-owned ASID 与 rollover 分别由
  既有测试验证。
- DeepSeek 在冻结源码上只读审查锁序、slot reuse、STOP/timeout、LA64 对齐和 frame
  生命周期，并通过本地 Docker gateway 严格串行执行 RV64/LA64 normal build 与两架构
  `CORE_NUM=8 KTEST=smp KREPEAT=1`。四项 exit 0、无 timeout/forbidden marker，
  `mutation_detected=false`；focused 均为 20/20 PASS，online mask 均为 `0xff`。
- GPT/Codex 独立核对源码与原始日志，并纠正模型把并发测试写成“不同 ASID/VPN”的
  过度表述。冻结 HEAD 为 `8a5a875741019c23a7593c367bc7d319174c4ee6`，tracked diff
  SHA-256 为 `c6c365d2ce660341c85e857f00c0b21a5114f03cd00b0878fa7b97ef879e4663`；
  详见 `docs/Work_Log/evidence/2026-07-29/smp-b26-precise-shootdown-summary.md`。

**文档与经验：**

### B25 LoongArch MM-owned ASID 与 flush-before-reuse epoch

**问题与上游依据：**

- 旧实现把 ASID 放在 `TaskControlBlock`，clone 时分配、TCB drop 时立即归还。同一个
  `CLONE_VM` 地址空间可被多个线程标上不同 ASID；编号也可能在其它 CPU 仍缓存旧翻译时
  被新任务复用。`__restore` 为维持正确性只能在 context switch 时固定全刷 non-global
  TLB，既掩盖所有权错误，也带来不必要的 refill 成本。
- 先核对 LoongArch 官方 `CSR.ASID`/`INVTLB` 定义，再对照 Linux LoongArch
  `mm_context_t.asid` 的 versioned ASID：高位软件 version、低位硬件 ASID，只在编号
  wrap 时全刷。DragonOS 未找到可直接复用的 LoongArch ASID allocator，因此本批只沿用
  其 MM/TLB 职责分层，不机械移植无对应硬件语义的类型。

**实现与命名收敛：**

- `os/src/hal/arch/loongarch64/tlb.rs` 删除 bitmap/free 接口，改为
  `AsidAllocator { epoch, next, max }`。CPU0 从 `CSR.ASID.ASIDBITS` 读取容量；一个 epoch
  内只递增分配，MM 销毁时不立即复用。耗尽时一个 CAS leader 先调用既有
  `synchronize_user_tlb(online_mask, None)`，收齐全 CPU ack 后才推进 epoch 和重置 cursor。
- `os/src/mm/tlb.rs` 把 `asid_context` 放入每 MM 的 `TlbContext`；低 10 位是硬件 ASID，
  高位只保存软件 epoch。`os/src/task/task.rs`、clone 和 drop 路径删除 task-owned ASID，
  使一个共享 MM 只有一个标签所有者。
- `os/src/mm/address_space.rs` 只新增一个有独立边界的值对象
  `UserVmContext { token, asid }`。生产调用链固定为
  `trap_return -> activate_user_vm -> AddressSpace::activate_on`；页表根和 ASID 来自同一个
  AddressSpace 快照，避免 exec/线程路径分别读取两份状态。
- `activate_on()` 发现编号耗尽时先结束 VM 锁作用域，再执行 rollover/ack 并重试；等待
  rollover 的 CPU 临时开放本地中断，保证它仍可响应 leader 的 TLB IPI。rollover flag
  在 flush 前发布。远端 CPU 若已在用户态，由 IPI 在 ack 前清除旧翻译；若正处于
  trap-return 的 IRQ-off 交接窗口，则不可能先 ack 再使用旧快照；尚在内核的 CPU 下次
  返回用户态时会按新 epoch 重新取得 ASID。
- LA64 `__restore` 继续把 PGDL/ASID 成对比较和写入，但删除每次 context switch 的
  `invtlb 0x3`。编号唯一性由 MM 所有权保证，编号复用安全性由 epoch 全 CPU flush 保证。
  RV64 保持 ASID=0 的统一接口，不改变 SATP 行为。
- 初版 `trap_return()` 用四个泛型 `in(reg)` 配合连续 `move $a0/$a1/$a2` 传递恢复参数。
  release 反汇编证明 LLVM 把 ASID 输入分配到 `$a0`，随后 `$a0` 被 trap-context 覆盖，
  最终生成 `move $a2,$a0`，把错误 ASID 写入 CSR。修复后固定 ABI 参数直接绑定
  `$a0/$a1/$a2`，跳转地址独占 `$a3`；最终 ELF 反汇编逐项确认参数归属。
- `laflex.rs` 的裸 `PageTable::activate()` 没有外层 MM 所有权信息，只允许 ASID 0 并保守
  全刷；普通用户返回不走该低层入口。LA64 单页 shootdown 尚未携带目标 ASID，本批仍使用
  全 non-global fallback，不把 B25 与下一批固定 slot/range payload 混在一起。

### B24 RV64 单页 RFENCE 与软件 IPI fallback

**目标与上游对照：**

- B23 已保留 `FlushRange::Page/Full`，但含远端目标时统一丢弃范围并执行全用户 IPI。
  B24 只接通 RV64 单页远端优化，不新增 MM batch/commit 类型，不提前实现 LA64 ASID/slot。
- 先核对 RISC-V SBI RFENCE 官方 ABI，再对照 Linux RISC-V
  `local -> SBI RFENCE -> on_each_cpu IPI fallback` 的后端选择，以及 DragonOS
  `MmuGather` 只收集范围、TLB 层负责同步的分层。MangoCore 继续使用既有术语和主链，
  没有机械复制 Linux 的 `FlushTlbInfo` 或 DragonOS 的额外 CSD 层。

**实现与并发边界：**

- `sbi_call_v02()` 增加 a3 参数，并抽出统一 `probe_extension()`；CPU0 在 AP 上线前只探测
  一次 RFENCE 并缓存结果，避免每次 PTE 修改额外 probe ecall。启动日志明确报告 RFENCE
  或软件 IPI fallback，不静默降级。
- `synchronize_user_tlb(targets, page)` 是唯一 SMP 同步入口：无远端时本地页级/全量失效；
  RV64 单页且有远端时，把 OS 逻辑 CPU mask 逆映射为物理 hart mask，并同步调用
  `REMOTE_SFENCE_VMA(start, PAGE_SIZE)`；full、LA64 或 RFENCE unavailable 继续用既有
  全用户 request/ack。
- RFENCE 参数由 ecall 立即复制进 OpenSBI，自身使用固件 FIFO/同步计数；MangoCore 不增加
  可被并发发起者覆盖的共享 range payload。调用返回后 `TlbFlush` 才推进 observed 并释放
  `MmuGather` 的退休 frame。固件返回其它错误时 fail-stop，不把错误伪装成成功。
- 原有退休窗口改为撤销两个 VPN，使 `MmuGather` 明确升级为 `Full`，继续验证软件 IPI 的
  request-before-flush-before-ack 和两页 frame 延迟释放；独立页级用例验证 RV64 不增加
  software request、LA64 明确增加 request。

**维护性规则：**

- 根 `AGENTS.md` 和 SMP agent 规范新增成熟实现对照规则：命名混乱、层次重复或调用链过深
  时先查官方规范/Linux/DragonOS，但只借鉴职责与术语；新增类型、文件和 wrapper 必须对应
  独立生命周期、所有权或并发边界。

**验证：**

- DeepSeek 在冻结初稿上自主串行执行 RV64/LA64 normal build 与
  `CORE_NUM=8 KTEST=smp KREPEAT=1`；四项均退出 0、`mutation_detected=false`，focused
  均为 17/17。RV64 启动日志为 `SBI RFENCE enabled`，cold-boot hart 为 4；LA64 页级

### B23 用户 PTE shootdown 与 MMU 接口收敛

**目标与边界：**

- B22 已提供每 MM 的 cached CPU/generation 激活侧，以及独立 user-TLB IPI/ack
  原语；B23 把真实用户 PTE 修改接入“锁内记录—解锁—flush/ack—frame 释放”。
- 首版 B23 虽然通过双架构 focused/初赛回归，但出现
  `take_tlb_commit -> take_commit -> prepare_commit -> finish` 的过深调用链，
  同时存在 batch、pending、commit 三套相近概念和重复 frame 队列，人工审查成本
  过高。本轮按维护者要求先重构可读性，再重新冻结验证。
- 普通用户任务仍固定 CPU0；本批不开放 affinity/迁移，不实现 range/RFENCE、
  LoongArch MM-owned ASID/epoch 或 CPU detach。当前全用户失效和单调历史 CPU mask
  是保守正确性基线，不是最终性能形态。
- B23 的实现、维护性重构和冻结验证均已完成，维护者已批准把本批作为一个独立提交
  落盘；验证基线仍是 B22 `1560ed6eaa817eaa6dfe98d111a7fd41d2eac90d`，未执行 push。

**维护性重构：**

- 不再新增 `locked_address_space.rs`。`os/src/mm/address_space.rs` 同时定义：
  - 外层 `AddressSpace<T>`：只持有 VM `Mutex` 和长期 `TlbContext`；
  - 锁内 `AddressSpaceInner<T>`：持有页表、VMA、heap/mlock 数据和一个 `MmuGather`。
  PCB 共享 `Arc<AddressSpace<_>>`；调用方只能使用 `read/write/try_write`，不能取得
  可变 guard 并把 VM 锁带过 IPI/ack 等待点。
- 删除 `tlb_batch.rs`、`tlb_state.rs` 以及首版 B23 的 pending/commit 包装，改为：

  ```text
  AddressSpace::write
    -> UserMapper 修改 raw/no-flush PTE
    -> MmuGather::record_change / retire_frame
    -> MmuGather::seal(&TlbContext)
    -> 释放 VM 锁
    -> TlbFlush::execute
  ```

  公开思维模型只有 `record_change -> seal -> execute` 三段。
- `UserMapper` 直接借用页表和本轮 `MmuGather`。VMA、page fault、filemap、CoW、
  mmap/munmap/mprotect、exec/OOM/zombie 路径不再反复构造嵌套 batch，也不自行决定
  flush 时机。每个 raw PTE 写入后立即记录 VPN。
- `MmuGather` 是一次 `write()` 内唯一的临时所有者，只保存：
  `FlushRange`、开始写操作时的 cached CPU mask 快照和一份 `retired_frames`。
  同一 VPN 合并为页级失效，多个 VPN/页表层级变化升级为全用户失效；无 PTE
  修改时 `seal()` 返回 `None`，不推进 generation、不发 IPI。
- `TlbContext` 只保存跨写操作的 MM ID、cached CPU mask、generation 和 per-CPU
  observed；`TlbFlush` 只表示一次已经脱离 VM 锁的同步工作，并直接拥有完整
  `MmuGather`，不复制 dirty/range/frame 字段。
- 目标语义直接从 cached mask 推导，不再维护 `Unpublished/LocalOnly/Published`
  状态：mask 为 0 时无需失效；仅当前 CPU 时按单页/全量本地失效；含远端 CPU 时
  使用全用户 request/ack。新地址空间包装前没有观察者，构造期记录由
  `discard_unpublished()` 明确清除。
- unmap、CoW 回滚和 zombie 页表释放都使用同一个 `retired_frames`。正常路径只有
  `TlbFlush::execute()` 在同步完成后释放；远端目标存在且退休队列 OOM、generation
  溢出、IPI/ack 失败或执行对象被遗弃时，先保留 frame 再 fail-stop，禁止 stale
  translation/page walk 访问已复用物理页。
- RV64 增加统一页级 user-TLB 入口，单页本地失效使用 `sfence.vma va, zero`。
  LA64 的 ASID 仍归 TCB，通用 MM 无法安全指定目标 ASID，因此页级入口当前保守
  清除本核全部 non-global 项；注释明确把精确失效留给 MM-owned ASID 阶段。
- `ProcessInner.vm`、procfs、syscall、uaccess、trap、clone/exec/exit、OOM、SysV SHM
  和统计调用点迁移到新的 outer/inner 接口。trap/clone/OOM/SHM 锁序继续保证不把
  `task.inner`、`TASK_MANAGER` 或 `SHM_REGISTRY` 带过 TLB 等待点。
- focused 用例改用真实 `AddressSpace`：CPU1 登记 MM 后保持关中断，CPU0 撤销一页；
  request 已发布但 AP 尚未 ack 的窗口内 frame 不回到分配器，`write()` 返回后才退休。

**性能与安全判断：**

- 一个 `write()` 无论触及多少 PTE 只形成一个 generation 和一轮同步；只读写作用域
  不产生空 flush。已登记 CPU 的 trap-return 快路径先读 cached bit，只在首次登记时
  `fetch_or`；ack 后用 `fetch_max` 推进 observed。
- 当前远端路径仍对单调历史 CPU 集合执行整个用户地址空间失效，因此高频
  CoW/mprotect/munmap 的 IPI、等待和 TLB refill 成本仍需后续计数器与 workload 实测。
  本轮重构减少的是概念和调用层数，不把它宣传为性能优化。
- 激活登记和修改侧 mask 快照由同一 VM 锁串行；不同 Atomic 的
  Acquire/Release 不是替代这把锁的证明。两代同一 MM 的并发 flush 通过
