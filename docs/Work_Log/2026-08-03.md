## 00:45 — B79 进程级 legacy interval timer

**Date:** 2026-08-03 00:45 +08:00
**Author:** AI:GPT/Codex + DeepSeek | Human:Pneuma
**Tags:** [area:smp, area:task, area:syscall, type:fix, risk:concurrency]
**Mango Gate:** skill loaded=yes; references=debugging-patterns.md, harness-patterns.md

**Summary:** `ITIMER_REAL/VIRTUAL/PROF` 从 TCB 私有状态迁入 PCB 独立 owner。REAL 由
monotonic heap action 按 generation/deadline 领取，VIRTUAL/PROF 由 trap-return 与
schedule-out 安全点按线程组 user 或 user+system CPU 累计领取；owner 锁内只提交状态，
锁外才进入 signal queue、runqueue 和 timer heap。

**Files:**

- `os/src/task/{process,task,manager,processor}.rs` — PCB timer owner、生命周期、安全点与 callback。
- `os/src/syscall/process/time.rs` — Linux 式 set/get ABI、三类时钟域和锁外 copyout。
- `os/src/{hal/arch/riscv/trap,syscall/utils,task/threads}.rs` — 删除旧 TCB remaining 刷新旁路。
- 时间、TCB、WaitQueue、锁序、SMP 计划、`AGENTS.md`、AI 披露与调试经验同步。
- `docs/Work_Log/evidence/2026-08-03/smp-b79-interval-timer-summary.md` — 冻结证据。

**Verification:**

- Linux 6.6 `kernel/time/itimer.c` 与 `kernel/fork.c` 对照 — ✅ timer 属于线程组；普通
  fork 创建新 timer 状态，exec 保留，REAL 使用 monotonic elapsed clock。
- Docker 双架构 `CORE_NUM=8` kernel build — ✅ RV64 125.158s、LA64 133.627s。
- 双架构 8 核 focused + 初赛门禁 — ✅ RV64 406.791s、LA64 438.430s；musl/glibc
  `setitimer01/02` 的 REAL/VIRTUAL/PROF 全部 PASS，`online_mask=0xff`；初赛保持
  RV64 312/314、LA64 308/314，既有 `busybox kill 10` 非满分项未扩大。
- 四项 accepted job 源码指纹一致；生产 diff SHA-256 为
  `3a2858cd39f0a25368a0e89eb6bfe5e8a2bd4d8e1db0b85ba566f309f77edf4d`。

**Notes:** DeepSeek 的早期只读审查误称普通 fork 继承 interval timer，已由 Linux 6.6
`copy_signal()` 的新 `signal_struct` 初始化路径纠正。运行验收后模型又把 REAL 与 wall-clock
调整列为缺口；REAL 实际使用 monotonic elapsed time，不随墙钟重定位。多 sibling 在不同 CPU
上精确跨越 VIRTUAL/PROF deadline 的动态注入仍为 NOT RUN；表锁提供唯一领取的静态证明。

## 01:40 — B80 POSIX timer 精确 pending 与 overrun

**Date:** 2026-08-03 01:40 +08:00
**Author:** AI:GPT/Codex + DeepSeek | Human:Pneuma
**Tags:** [area:smp, area:task, area:syscall, type:fix, risk:concurrency]
**Mango Gate:** skill loaded=yes; references=debugging-patterns.md, harness-patterns.md

**Summary:** POSIX timer 不再用进程 shared signal bitmap 猜测某个 timer 是否已有事件。每个
timer 对象以 `timer ID + instance_seq` 标识 pending，同一 timer 的重复到期合并为 overrun，
不同 timer 即使使用同一个非实时 signal 也分别排队。signal dequeue 后锁外回到 timer owner
固化本次 siginfo 和最近交付 overrun；delete/exec/exit 以精确身份执行反向锁外清理。

**Files:**

- `os/src/task/signal/{pending,mod,delivery}.rs` — timer 事件身份、SI_TIMER 字段和精确合并规则。
- `os/src/task/process.rs` — instance/arm/pending 三类状态、overrun 生命周期和双锁拆分。
- `os/src/task/manager.rs`、`os/src/syscall/process/time.rs` — wall/CPU/realtime 到期统一记录事件。
- `os/src/syscall/process/signal.rs` — signalfd 返回真实 timer ID/overrun，sender 字段归零。
- 时间、signal、锁序、SMP 计划、`AGENTS.md`、AI 披露与调试经验同步。
- `docs/Work_Log/evidence/2026-08-03/smp-b80-posix-timer-pending-summary.md` — 冻结证据。

## 01:55 — B81 shared signal hint 锁内发布

**Date:** 2026-08-03 01:55 +08:00
**Author:** AI:GPT/Codex + DeepSeek | Human:Pneuma
**Tags:** [area:smp, area:task, area:signal, type:fix, risk:concurrency]
**Mango Gate:** skill loaded=yes; references=debugging-patterns.md, harness-patterns.md

**Summary:** process shared signal queue 的四个 mutation 写点不再于解锁后发布
`shared_pending_hint`。queue mutation、完整位图重算和 Release store 现在属于同一个 signal
临界区，Acquire fast reader 不会再被较早 writer 的锁外 stale store 长期覆盖。POSIX timer
discard/finalize 仍在 signal 解锁后执行，未引入双锁嵌套。

**Files:**

- `os/src/task/process.rs` — 四个 shared queue writer 锁内发布 hint，读端使用 Acquire。
- signal/锁序/SMP 计划、`AGENTS.md`、AI 披露与调试经验同步。
- `docs/Work_Log/evidence/2026-08-03/smp-b81-shared-signal-hint-summary.md` — 冻结证据。

**Verification:**

- 静态全调用面审查 — ✅ shared queue 只有 enqueue、两类 dequeue 和精确 timer remove 四个
  mutation，全部在同一 `self.signal` mutex 内发布 hint；timer owner 只在解锁后进入。
- Docker 双架构 `CORE_NUM=8` kernel build — ✅ RV64 134.984s、LA64 134.831s。
- 双架构 8 核 sigtimedwait gate — ✅ RV64 140.681s、LA64 139.029s；两架构
  `online_mask=0xff`，glibc `sigtimedwait01` 各 11 TPASS，TFAIL/TBROK/TCONF 均为 0。
- 四项 job 均 exit 0、无 forbidden marker、无 timeout、无源码 mutation；冻结 tracked diff
  SHA-256 为 `e81919e2a0904ecd52047f4db968ca54110ec3e49140adcb0a5b2d83f0d862a0`。

**Notes:** 修复成立的关键是 mutex 把所有 writer store 纳入同一全序；Release/Acquire 只负责
无锁发布关系。若仅把旧锁外 Relaxed store 改成 Release，旧 writer 仍能晚于新 writer 覆盖，
因此不算根因修复。普通 LTP 没有精确注入三 CPU stale-store 顺序，该动态交错登记为 NOT RUN，
以完整 mutation 搜索和锁序证明作为静态证据；本批没有重复 B80 timer 或初赛矩阵。
