### BuildStorm 慢速原因与 Bad address 修复

**性能分析：**
- 初步分析曾把 BuildStorm profile 未显式写 `-accel tcg,thread=multi` 视为主要慢因；随后在当前 QEMU 10.0.2 上实测，省略该参数时 QEMU 线程数为 10，与显式 `thread=multi` 相同，而显式 `thread=single` 仅为 3。QEMU 在当前 RV64 后端会默认启用 MTTCG，因此该项不是本轮慢速根因；仍可在 profile 中显式声明以固定跨版本行为，但不应据此宣称有性能提升。
- 本轮使用 `LOG=info`，而 `os/src/syscall/mod.rs` 会对绝大多数 syscall 打印参数或返回值；日志共约 579,605 行、61 MB。串口输出经 QEMU `-nographic` 和 `tee` 串行化，显著放大了每次 syscall 的成本。
- guest 实际执行的是带 `build-std` 的 Rust/Cargo 构建，阶段中出现约 70,233 次 `mprotect`、45,103 次 `statx`、17,468 次 `openat` 和 18,148 次 `futex`，说明主要时间花在动态装载、Cargo 元数据扫描、文件映射和并发同步，而不是单次大块写入。
- 从 `BUILDSTORM_BEGIN` 到首次 EFAULT 约 1,422 秒；在 EFAULT 前已经向 rustc 临时归档文件成功写入约 37.1 MiB。`another_ext4` 的 80 次 `plan_reject` 未伴随 I/O 错误或磁盘空间不足，是竞争放大因素而非唯一慢因。

**Bad address 根因与修改：**
- file-backed 缺页在 PageCache 页处于 `Loading`/`Writeback` 时返回瞬时 `EAGAIN`；旧 `map_pc_error()` 将所有非 `ENOMEM`/`EIO` 错误统一映射为 `MemoryError::BackingStoreFailure`，最终被用户态看到为 `EFAULT`（Rust 的 `Bad address`）。
- `os/src/fs/page_cache.rs` 暴露 `filemap_fault_wait()`；`os/src/mm/filemap.rs` 的读 fault 和私有写 fault 将 `EAGAIN` 返回为 `FaultOutcome::Retry`；`os/src/mm/page_fault.rs` 透传该结果，避免把可重试状态伪装成地址错误。

**验证：**
- `git diff --check` 通过。
- Docker 内串行 `make kernel ARCH=rv64 PROFILE=normal MODE=release` ✅（约 2m18s）。
- Docker 内串行 `make kernel ARCH=la64 PROFILE=normal MODE=release` ✅（约 2m40s，1044 warnings）。
- 尚未用修复后的内核跑完整 BuildStorm；下一轮应关闭 syscall 日志、补上 BuildStorm 的 MTTCG 参数后，以同等 fresh 镜像复测并比较 EFAULT/EAGAIN 计数与阶段耗时。

### 修复 BuildStorm 命名空间变更 EAGAIN 重试
