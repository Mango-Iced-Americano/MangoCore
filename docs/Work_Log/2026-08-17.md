## LA64 `-smp 1` SMP boot panic 根因实证与最小修复

**Date:** 2026-08-17 +08:00
**Author:** AI + 人工实证
**Tags:** [area:loongarch64, area:smp, area:boot, type:bugfix]

**前置更正：** 上文 A/B 调查曾把 LA64 panic 误判为「CORE_NUM=1 vs FDT 固定 2 核错配」。
经临时诊断 patch 实测，该判断不准确；真正根因如下。LA64 的 FDT `/cpus` 本身随 `-smp`
正确收缩（`-smp 1` 只有 `cpu@0`），并非固定 2 核。

**实证（临时打印固化，已验证后还原）：**
- `Boot protocol: LoongArchEfi, hart_id=1, dtb_paddr=0x0`
- 同时在 `rust_main(cpu_id, _)` 打印 `cpu_id`（= CSR 0x20 CPUID）= `0x0`
- 结论：**真 boot 核 = CSR CPUID = 0**（与 FDT `cpu@0` 一致），而 `RAW_HART_ID` 被固件
  `$a0`（=1）污染。

**根因：** `os/src/hal/arch/loongarch64/boot.rs` 的 `_start` 按 RV64 旧惯例把固件 `$a0`
存进 `RAW_HART_ID`。但 Linux LoongArch 启动 ABI 中 `a0` 是 flags（QEMU `hw/loongarch/
boot.c::init_cmdline` 恒设 `a0=1`，bit0=EFI 标志），**不是 CPU 编号**；真正的 boot 核在
CSR 0x20（CPUID），代码只用它选启动栈、没存进 `RAW_HART_ID`。于是
`boot_info().hart_id = 1`，与 FDT `[0]` 错位，触发 `count_cpus`（fdt.rs BSP 兜底插入）
把 hart 1 硬算为第 2 个逻辑核 → `cpu_count()=2` → `expected=0x3` → `-smp 1` 只给 1 个
vCPU → cpu1 永不 online → panic。RV64 的 `entry.asm` 存的是 OpenSBI 真 hart id，故不触发。

**修复（最小，仅 boot.rs +6 行）：** 在 `csrrd $a0, 0x20` 读取真 CPUID 后，把 `$a0`
重新写回 `RAW_HART_ID`，覆盖掉固件 `a0`（EFI 标志）。保留开头原存储作为无 CSR 时的防御初值，
不顺手重构。

**验证（全矩阵）：**
- LA64 `-smp 1`（默认）waitqueue ktest：**19/19 PASS**（修复前 panic `expected=0x3`）
- LA64 `-smp 2` waitqueue ktest：**19/19 PASS**
- RV64 `-smp 1` waitqueue ktest：**19/19 PASS**（无回归）
- RV64 + LA64 `make kernel` release build：✅
- boot log 现正确显示 `hart_id=0`

**遗留（已完成，见下方「编译期 CPU 数债务删除」）：** 用户要求删除编译期 `MANGO_CORE_NUM`/`CONFIGURED_CPU_COUNT`
债务（让 `runtime_cpu_count()` 纯 FDT 探测、数组定界统一用 `MAX_CPUS`）。此为独立重构，
涉及几十处调用点与「FDT 解析前回退」的 boot 时序语义，单独设计并双架构验证，未在本工作包
混入。

## 2K1000LA 默认持久化根与 AHCI 合并回归修复

**Date:** 2026-08-17 +08:00
**Author:** AI:Codex:GPT-5 | Human:lzm
**Tags:** [area:loongarch64, area:board, area:block, area:fs, type:debugging, type:validation]

**根因：** develop 合并后，通用 AHCI 核心仍保留 64 KiB DMA、IDENTIFY、容量和 flush
能力，但 `os/src/drivers/block/sata_blk.rs` 的 2K1000 板级适配退回了通用 PCI 扫描，丢失
固定 `00:08.0`、DMW2 SUC MMIO 别名、`0014:7a08`/BAR0 校验和 reset 后 CAP/PI 恢复；

- 固定探测 2K1000 SATA identity/class/BAR，以 16-bit PCI Command RMW 启用 Memory Space
  和 Bus Master；CPU MMIO 走 DMW2，HBA DMA 保持低物理地址。
- 使用连续、页数向上取整且低于 4 GiB 的 64 KiB DMA extent，恢复 CAP/PI 和稳定硬件延时。
- 发布 `sda`/`sda1` Linux 命名、容量、`FLUSH CACHE EXT` 与可靠 flush 能力；I/O/flush 错误
  返回 `BlockDeviceError`，probe 失败打印 `SataInitError` 后保留 initramfs rescue。

  当作完整根；P3 包含可执行 `bin/sh`、运行库和工具。因此 `la64-2k1000-mainline` 改为固定注入
  `mango.mode=normal profile=mainline root=/dev/sda3`。内核把可写 another_ext4 挂到
  `/sdcard`，PID1 绑定运行期伪文件系统、chroot，并优先执行盘内 init；静态合同测试同时
  锁定 root selector、默认后端和 SATA flush 门禁。

## 2K1000LA 上板脚本详细审查

**Date:** 2026-08-17 +08:00
**Author:** AI:Codex:GPT-5 | Human:lzm
**Tags:** [area:tooling, area:board, area:net, type:audit, type:validation]

**审查范围：** `scripts/boot_2k1000_tftp.py` 全文件、Docker Compose/Makefile 构建合同、
CLI 交互、macOS 网卡/TFTP、串口/U-Boot 命令和错误恢复；审查后已在同一工作包实施修复。

**已验证：** Python AST、CLI `--help`、`git diff --check` 和四个板级 Make 目标 dry-run
通过；此前实板 `shell` 流程的 TFTP 长度、CRC32、`iminfo` 和 `bootm` 通过。仓库没有
针对该脚本的自动化单元测试，宿主环境也没有安装 ruff/pyflakes/mypy。

**主要问题：**
- `--tftp-root` 只改变复制位置，macOS `tftpd` 仍固定服务 `/private/tftpboot`；自定义
  根目录会让“本地校验成功、板端下载旧文件或失败”。
- `board_ip`、`host_ip`、`netmask`、`loadaddr` 和镜像 basename 未做严格校验，直接拼入
  U-Boot 原始命令；异常输入可造成命令注入、错误内存地址或错误网络配置。
- 找不到 U-Boot 时每 200ms 盲发 `c`；若板子实际已进入 Linux/用户 Shell，会把大量 `c`
  写入目标串口，且失败信息把所有原因都归为“RESET 未观察到”。
- `screen` 占用检测匹配大写 `SCREEN`，macOS 常见进程命令为小写 `screen`，自动接管可能
  失效并在随后以串口独占错误退出。
- 网卡已有目标 IP 时不核对实际 netmask；自动设置的网卡地址和加载的 TFTP 服务也没有
  成功/失败后的状态恢复，文档所称“只在当前会话”并不成立。
- TFTP 服务检查只确认 `launchctl print` 成功，不验证实际 UDP/69 和服务根目录；镜像复制
  不是临时文件后原子 rename，也没有构建/TFTP 并发锁。
- 构建只检查目标文件“存在”，不检查产物是本次构建生成的合法 uImage；从仓库外启动向导
  时，候选镜像也只搜索当前工作目录而不是 `REPO_ROOT`。
- U-Boot prompt 固定要求末尾 `=> `，串口固定 115200；非交互运行遇到 stdin EOF 会关闭
  启动后的监视器，命令/异常路径也没有统一捕获 `OSError`、`KeyboardInterrupt` 和友好
  清理。

**已实施修复：**
- 仅接受可用 IPv4、连续掩码、不同的主机/板端地址、对齐的 64 位 load address 和安全
  TFTP 文件名；网卡已有目标地址时同时核对实际掩码。
- macOS system tftpd 的根目录与 launchd plist 不匹配时 fail-closed；镜像先写同目录
  临时文件再 rename，构建使用进程锁，shell/构建产物额外验证 U-Boot legacy uImage
  magic、header CRC、payload 长度和本次构建时间。
- 不再隐藏只暴露 tty 的第二个串口；screen 检测大小写无关；U-Boot 只有在观察到
  U-Boot/autoboot banner 后才发送 `c`，避免把字符洪泛到已经运行的 Linux shell；新增
  `--baud`，stdin EOF 也不会误关串口监视。
- `la64-2k1000-shell` 注入 `profile=rescue`，PID1 现在真正跳过持久盘挂载并进入
  `/rescue/sh`，修复了此前实际启动 `mode=run` 测例的问题。

**剩余边界：** 主机网卡地址不会在脚本结束时自动恢复，这是为了保证刚启动的板卡仍可
继续访问宿主；`--tftp-root` 当前只允许 macOS 默认 `/private/tftpboot`。这些限制会在
入口错误时明确拒绝，而不会产生“本地复制成功、板端取到旧文件”的假成功。
