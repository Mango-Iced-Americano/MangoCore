## LA64 `-smp 1` SMP boot panic 根因实证与最小修复

**Date:** 2026-08-17 +08:00
**Author:** AI + 人工实证
**Tags:** [area:loongarch64, area:smp, area:boot, type:bugfix]

**前置更正：** 上文 A/B 调查曾把 LA64 panic 误判为「CORE_NUM=1 vs FDT 固定 2 核错配」。
经临时诊断 patch 实测，该判断不准确；真正根因如下。LA64 的 FDT `/cpus` 本身随 `-smp`
正确收缩（`-smp 1` 只有 `cpu@0`），并非固定 2 核。

**实证（临时打印固化，已验证后还原）：**
- `Boot protocol: LoongArchEfi, hart_id=1, dtb_paddr=0x0`
- 同时在 `rust_main(cpu_id, _)` 打印 `cpu_id`（= CSR 0x20 CPUID）= `0x0`
- 结论：**真 boot 核 = CSR CPUID = 0**（与 FDT `cpu@0` 一致），而 `RAW_HART_ID` 被固件
  `$a0`（=1）污染。

**根因：** `os/src/hal/arch/loongarch64/boot.rs` 的 `_start` 按 RV64 旧惯例把固件 `$a0`
存进 `RAW_HART_ID`。但 Linux LoongArch 启动 ABI 中 `a0` 是 flags（QEMU `hw/loongarch/
boot.c::init_cmdline` 恒设 `a0=1`，bit0=EFI 标志），**不是 CPU 编号**；真正的 boot 核在
CSR 0x20（CPUID），代码只用它选启动栈、没存进 `RAW_HART_ID`。于是
`boot_info().hart_id = 1`，与 FDT `[0]` 错位，触发 `count_cpus`（fdt.rs BSP 兜底插入）
把 hart 1 硬算为第 2 个逻辑核 → `cpu_count()=2` → `expected=0x3` → `-smp 1` 只给 1 个
vCPU → cpu1 永不 online → panic。RV64 的 `entry.asm` 存的是 OpenSBI 真 hart id，故不触发。

**修复（最小，仅 boot.rs +6 行）：** 在 `csrrd $a0, 0x20` 读取真 CPUID 后，把 `$a0`
重新写回 `RAW_HART_ID`，覆盖掉固件 `a0`（EFI 标志）。保留开头原存储作为无 CSR 时的防御初值，
不顺手重构。

**验证（全矩阵）：**
- LA64 `-smp 1`（默认）waitqueue ktest：**19/19 PASS**（修复前 panic `expected=0x3`）
- LA64 `-smp 2` waitqueue ktest：**19/19 PASS**
- RV64 `-smp 1` waitqueue ktest：**19/19 PASS**（无回归）
- RV64 + LA64 `make kernel` release build：✅
- boot log 现正确显示 `hart_id=0`

**遗留（已完成，见下方「编译期 CPU 数债务删除」）：** 用户要求删除编译期 `MANGO_CORE_NUM`/`CONFIGURED_CPU_COUNT`
债务（让 `runtime_cpu_count()` 纯 FDT 探测、数组定界统一用 `MAX_CPUS`）。此为独立重构，
涉及几十处调用点与「FDT 解析前回退」的 boot 时序语义，单独设计并双架构验证，未在本工作包
混入。
