## WaitQueue L2：共享纯核心、有界 DFS 与 B71 deterministic replay

**Date:** 2026-08-17 +08:00  
**Author:** AI:GPT-5.6-terra | Oracle architecture review  
**Tags:** [area:task, area:waitqueue, area:testing, type:feature, type:validation]
**Mango Gate:** skill loaded=yes/reused; references=none（功能实施，非调试/性能任务）

**Summary:** 新增 `mango-kernel-core::wait_queue_core`：`WaitToken` 保留
`WAITING -> NOTIFIED/CLOSED` 的 Acquire/AcqRel CAS，`WaitEntryCore<P>` 持有 payload、
不复用 `EntryId` 和 token，`WaitQueueCore<P>` 实现生产 FIFO batch/single wake、精确
finish、stale 回收。生产 `WaitQueue` 仅改为 façade，仍以共享 `Arc<WaitEntry>` 支持多队列
poll/epoll；New/Zombie 前置过滤、每次成功 claim 的 timer generation 和单次/批量调度尾部
仍留在 `manager.rs`。host L2 对这同一 core 运行有界 DFS、context-switch 上限、严格 schedule
replay 与固定 LCG scale 序列；B71 legacy wrapper 仅在测试中模拟“登记后不复查”。

**Files:**
- `libs/mango-kernel-core/src/wait_queue_core.rs`、`wait_queue_core/queue.rs`、
  `wait_queue_core_tests.rs`、`lib.rs` — 共享 token/entry/queue core 及 10 个 L1 单测。
- `os/src/task/manager.rs` — 保持现有公开 façade 签名，组合 core；多队列共享 token 和
  `wake_one` hot path 保持原有调度尾部。
- `libs/mango-kernel-core/tests/l2_waitqueue.rs` 与 `tests/l2_waitqueue/{protocols,explorer,
  generator,invariants,scale}.rs` — Correct/B71 协议、DFS、replay、invariant 和 10~10000
  scale 测试。

**Verification:**
- Docker `cargo test -p mango-kernel-core` — 163 L1 + 6 L2 + 3 doc tests，全部 PASS。
- Docker 串行 `make kernel ARCH=rv64 PROFILE=normal && make kernel ARCH=la64 PROFILE=normal` — ✅。
- Docker `KTEST=waitqueue`：RV64 19/19 PASS；LA64 未进入 waitqueue，启动期要求
  `online_mask=0x3` 但 QEMU 仅 CPU0 online，`secondary CPU online timeout` 后 FAIL。
- LA64 FAIL 已用**干净基线 A/B 证实为预存在环境问题**：在未含本批改动的 `develop`
  worktree 上跑相同 `make -C os ktest-run ARCH=la64 KTEST=waitqueue`，得到
  **完全一致**的 `secondary CPU online timeout: expected=0x3 online=0x1 missing=0x2:
  src/smp.rs:2536`。根因：内核按 `runtime_cpu_count()`（FDT 动态探测）期望 2 个 CPU，
  而 `make -C os ktest-run` 默认 `CORE_NUM ?= 1` 使 QEMU 以 `-smp cpus=1` 只起 1 个 vCPU，
  二者错配导致 cpu1 永不 online。本批改动只触及 `wait_queue_core`/`manager.rs`，未碰
  SMP/FDT/firmware/config/Makefile，故判定非本批引入。本环境无法跑通 LA64 QEMU
  waitqueue（4 核容器 + ktest 默认单核 vs 内核期望多核），未在本批扩大范围修 SMP 拓扑。
- deterministic B71 replay：`MANGO_L2_CASE=b71_bad MANGO_L2_SEED=1234
  MANGO_L2_SCHEDULE=0,1,1,0,0 cargo test -p mango-kernel-core --test l2_waitqueue -- --exact
  known_bad_b71_is_discovered --nocapture` — 稳定得到
  `quiescent_satisfied_condition`。
