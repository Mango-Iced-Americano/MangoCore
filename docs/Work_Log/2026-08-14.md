LA12 1718 秒口径下，剩余差距为 503 秒（RV/LA=1.2928，RV 慢 29.28%）。只读复核现有

**Findings:**
- 历史完整诊断记录 4,165,223 次 page fault、587.656 CPU-s handler 成本；但
  `pagefault_ticks_total` 不包含 trap 汇编、返回和部分 TLB 同步，不能用它排除边界外固定成本。
- `UserMapper::map_page()` 在确定 PTE 从 invalid→valid 后仍无条件
  `MmuGather::record_change()`；seal 会推进 MM generation，并可能执行本地 flush、SBI RFENCE
  或 IPI 与远端等待。本机 QEMU 10.0.2 的 RV8 FDT 每个 hart 都暴露 `svvptc`；该扩展允许
  invalid→valid 的叶/非叶 PTE 不执行内存管理 fence。Linux RISC-V 的
  `update_mmu_cache_range()` 也在 Svvptc 可用时直接返回。
- Svvptc 快路只能覆盖 V=0→1；unmap、PPN/权限变化、A/D 清除、SATP/ASID epoch 仍必须刷新。
  还需为偶发 stale-invalid fault 增加“PTE 已 valid 且满足 R/W/X 时本地单页 fence 后重试”快路，
  避免 private store fault 被现有分类误判为 COW。
- 当前 `CpuDiagnostics` 已累计 RFENCE/backend、range pages、remote targets、sync total/max ticks，
  但正常 BuildStorm 不导出，只在 panic diagnostics 打印。这是判断 503 秒中 TLB/SBI 占比的最大
  观测盲区。历史 900 秒样本的 page flush 约 4.68 CPU-s、锁外 VM flush 约 10.97 CPU-s，支持
  优化但不足以声称 Svvptc 单独解释全部差距。
- `riscv::sbi::send_ipi()` 每个 doorbell 都先 probe IPI extension，再执行 send，即两次 SBI ecall；
  能力应在 BSP 初始化时 fail-closed 缓存。历史远端唤醒仅数千量级，预计这是确定但次于
  Svvptc/RFENCE 的收益，不能先验视为主根因。
- RV `trap_return()` 每次执行 `fence.i` 后才跳入静态 trampoline；Linux RISC-V 常规
  `ret_from_exception` 直接恢复后 `sret`，其 I-cache 同步按 stale CPU/MM 状态延迟。Mango LA
  每次返回也执行 `ibar 0`，因此这里只能判为高频可疑项；应先做 null-syscall/固定 crate 短 A/B
  与正确性审计，不能静态删除后直接进入长测。
- RV 使用 VirtIO-MMIO、LA 使用 VirtIO-PCI，但两端 Mango block driver 都只用 queue 0 且受全局
  mutex 串行化；差别更可能是 transport/QEMU device-model 成本，而不是 LA 多队列并行。现有
  363,411 次、平均 5.44 KiB 的读请求支持将 RV PCI/MMIO A/B 列为次级实验。
- LA12 是官方口径，不是错误配置。若 503 秒全部来自 8→12 核，Amdahl 模型要求约 94.43% 工作
  完美并行；这与现有 60.23% 快照 active≤2、约 783 秒低并行单 crate 长尾不符。LA8 只应作为
  诊断控制，不替换正式 LA12 结果。
