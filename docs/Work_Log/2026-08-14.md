### 修复：normal 模式实板测试结束走 SBI shutdown 挂起 → 统一改走 JH7110 watchdog 复位

**涉及文件：**
- `os/src/hal/mod.rs` — `shutdown()` 在 `platform::is_real_board()` 时改调 `arch::reboot()`（VF2 watchdog 整机复位回 U-Boot），QEMU/未知平台保持 `machine_shutdown()`。

**根因：** normal 模式 test_runner 跑完调 `shutdown()` syscall → `sys_shutdown()` → `hal::shutdown()` → SBI legacy shutdown。OpenSBI 的 shutdown/SRST 都依赖 PMIC 电源管理，而 U-Boot 关闭 I2C5 后 PMIC 不可读（`pmic_ops: cannot read pmic power register`）→ 板子永久挂起，只能手动断电。watchdog 复位（`jh7110_watchdog_reboot`）此前只接入 ktest 路径（`finish_test_run()` → `reboot()`），normal 模式漏接。

**验证：**
- Docker 串行双架构 build：`make kernel ARCH=rv64 PROFILE=normal`、`ARCH=la64` ✅。
- QEMU ktest `CORE_NUM=4` 重跑 `163 passed, 0 failed` ✅（QEMU 下 `is_real_board()`=false，shutdown 行为与改动前一致；首轮一次偶发 1 fail 为 MTTCG 竞态，与本次改动无关）。
- **VF2 实板（mask=0x4000 cagent，含修复镜像）**：cagent 10 个 testcase 全部 pass（factorial/date/network/cpu/kernel/fs-create/fs-directory/fs-usage/fs-readwrite/fs-search），`#### OS COMP TEST GROUP END cagent-glibc ####`、`run_selected_groups done` 后**不再出现 `pmic_ops`**，watchdog 复位回 U-Boot，`vf2_cli.py boot` 报告 `REBOOTED back to U-Boot after 190s`——板子测试完自动恢复，无需手动断电。
- 完整串口日志：`docs/Work_Log/evidence/2026-08-14/vf2-boot-cagent-wdt-20260814.log`。
- 验证后 `os_test.conf` 恢复基线 `mask=0x6000`。

**备注：** 该修复同样覆盖实板 panic 路径（`shutdown()` 也被 panic 兜底调用）：实板任何致命异常后 watchdog 自动恢复。未暂存、未提交。

**实板部署流程（首次成功启动）：**
- 构建 `make kernel ARCH=rv64 PROFILE=normal`，Image（9.56 MiB，magic2=0x05435352）复制到 `/srv/tftp/vf2/kernel-rv-image`（旧镜像已备份）。
- `scripts/vf2_cli.py boot kernel-rv-image`：U-Boot `booti 0x40200000 - $fdtcontroladdr`，板子 `/dev/ttyUSB0` 在线。
- 第一次启动：`[kernel] Boot protocol: RiscvFdt, dtb_paddr=0xf76df9b0`，4 GiB 内存解析正确，但在 `mapping memory-mapped registers` 处 panic `AlreadyMapped: src/mm/page_table.rs:91`。
- **根因**：VF2 vendor DTB 的 `dc8200@29400000`（显示控制器）声明两个 reg 条目 `[0x29400000,0x29400100)` 与 `[0x29400800,0x29402800)`，落在**同一 4 KiB 页**内；fdt.rs 以字节粒度 `push_range` 不合并这两个不重叠子区间，`kernel_space` 按页映射第二段时对同一 VPN 重复映射 → `AlreadyMapped`。QEMU 生成 DTB 无此类同页多 reg 设备，故只在实板暴露。用脚本复现内核收集逻辑（fdt crate 用**父节点** `#address-cells`）确认唯一碰撞即 dc8200；Oracle 验证根因与修复方向。
- **修复**：页对齐后再 `push_range`，同页子区间必然合并；模拟验证碰撞数 1 → 0。
- 验证：`make kernel ARCH=rv64 PROFILE=normal` + 串行 `ARCH=la64` ✅；rv64 全量 ktest `149 passed, 10 skipped, 0 failed`；`make test ARCH=rv64 PROFILE=regression` `25 passed` ✅。
- 第二次启动（修复后）：越过 MMIO 映射，SMP bring-up 阶段暴露**新问题**——`secondary CPU online timeout: expected=0x1f online=0x1d missing=0x2`，且 `sbi_trap_error: hart0: mcause=5 (load access fault @0x4003d068)`。内核从 hart1 启动，logical CPU1 = 物理 hart0（S7 小核）未上线，hart2/3/4（U74）正常。

**备注：** 板载 rootfs 只有 cagent/buildstorm 测试组（无 basic 等），板测配置临时改用 `mask=0x4000`（cagent）；`os_test.conf` 基线为 `mask=0x6000`（已备份，板测后恢复）。hart0(S7) 未上线根因见下一条目（SMP 拓扑工作包）。未提交、未暂存。
