## RV64 L2：FDT 驱动的 per-CPU PLIC context 与 AP 页表后 SEIE

**Date:** 2026-08-16 +08:00  
**Author:** AI:GPT-5.6-terra | Oracle review | Human:lzm  
**Tags:** [area:riscv64, area:firmware, area:smp, area:irq, type:feature, type:validation]  
**Mango Gate:** skill loaded=yes/reused; references=debugging-patterns.md

**Summary:** 将 RV64 PLIC 从单一 BSP context 扩展为 FDT `interrupts-extended`
驱动的 per-CPU context 表。解析链为 PLIC entry phandle → `riscv,cpu-intc` →
父 CPU `reg` hart → 冻结的稀疏 logical CPU；标准 supervisor external interrupt
9 优先，同一 hart 缺少 9 时才采用兼容值 11。解析、引用或 MMIO 范围不满足契约时
fail-closed，仅回退既有 BSP context，绝不推断 AP context。实现按 Oracle 审查后的
边界拆分全局 `init_controller()` 与当前 CPU `init_local_context()`：controller 先
quiesce 全部已发布 context，local 初始化后才允许 claim/complete。AP 继续在
bootstrap 阶段只开 SSIE，待安装本 CPU 内核页表并刷新 TLB 后才访问高半区 direct-map
PLIC MMIO 并开启 SEIE。默认设备 handler 仍绑定 logical CPU0，因此没有扩大网络
IRQ 或 smoltcp 数据面迁移范围。

**Files:**

## LA 评测 boot 段停滞根因：线程组收尾丢 leader exit_signal，父进程等不到 SIGCHLD

**Date:** 2026-08-16 +08:00
**Author:** AI:DeepSeek | Human:lzm
**Tags:** [area:loongarch64, area:signal, area:process, area:buildstorm, type:bugfix, type:liveness]

**Summary:** 官方 LA buildstorm 评测日志停在隐藏 boot 段
（`boot arceos-helloworld in qemu` 的两条 unsupported syscall 之后）直至
50 分钟墙钟被杀，而 RV64 同段瞬间完成。定位为：线程组退出时最后完成
进程级收尾的可能是非 leader sibling，其 TCB `exit_signal` 为空；旧
`finish_exit()` 按该线程的 exit_signal 通知父进程，导致以
`timeout --foreground` 包装内层 QEMU 的父进程永远收不到 SIGCHLD，

`exit_signal_hint` 快照，非 `CLONE_THREAD` clone 时写入 exit_signal、
非 leader exec 接管时恢复 SIGCHLD，`finish_exit()` 一律按快照通知父进程。

**Files:**

  setter/getter；`finish_exit()` 改用 `exit_signal_hint()` 通知父进程。
- `os/src/task/task.rs` — `sys_clone()` 非 `CLONE_THREAD` 时记录
  exit_signal；`become_group_leader()` 恢复 SIGCHLD。

**Verification:**

## LA buildstorm 静默卡死根因：Pipe::poll 在 ring 锁内析构对端 Arc

**Date:** 2026-08-16 +08:00
**Author:** AI:DeepSeek | Human:lzm
**Tags:** [area:loongarch64, area:pipe, area:scheduler, area:buildstorm, type:bugfix, type:liveness]

**Summary:** 专项 LA12 fork/pipe 压测复现了 deferred publish 化后残留的
buildstorm prebuild 静默卡死。根因不是 RESCHEDULE IPI 丢失，而是管道
轮询路径的锁重入：`Pipe::poll`（以及 splice/tee）持有 `PipeRingBuffer`
的 ring `Mutex` 时调用 `all_write_ends_closed()`/`all_read_ends_closed()`；
旧实现用 `Weak::upgrade().is_none()` 判断对端存活。对端仍存活时，
`upgrade()` 产生的临时 `Arc<Pipe>` 在语句末尾被立即 drop，`Pipe::drop`
又反向获取同一把 ring `Mutex`，形成单核自死锁。修复为使用
`Weak::strong_count() == 0`，不构造强引用、不在锁内触发对端析构。

**复现与定位：**
- 自定义 LA12 initramfs fork+pipe 工作负载（父进程持写端存活时读/poll
  空管道）在修复前稳定复现：round 0 后无进展，所有 AP 停在 idle。
- Ctrl-O 现场快照显示 CPU0 无 current、本地 queued=1；QEMU monitor
  `info registers -a` 显示 CPU0 PC=0x80291e24，位于 `<Pipe as Drop>::drop`
  的 ticket-Mutex 自旋段，ticket=9 等待 serving=8；其余 11 个核均停在
  `__mango_cpu_idle_interrupt_exit`。
- disassembly 定位到 `Drop for Pipe` 第二分支（writable 端 drop →
  `peer_read_end()` → 再次 lock ring），与 `poll` 中临时写端 Arc
  drop 的调用链完全一致。
- 同类锁内 `upgrade().is_none()` 调用同时存在于 splice/tee 的 ring 锁
  路径，一并由 `strong_count` 修复覆盖。

**Files:**
- `os/src/fs/dev/pipe.rs` — `all_write_ends_closed()` /
  `all_read_ends_closed()` 改用 `Weak::strong_count()`；注释记录禁止在
  ring Mutex 内 `upgrade()` 的原因。
- `os/src/kernel_tests/waitqueue.rs` — 新增
  `waitqueue::pipe_poll_live_peer_no_ring_reentry` 回归用例。

**Verification:**
- LA12 `KTEST=waitqueue,smp`：58/58 PASS。
- 修复后同机 fork+pipe 定向压测（2000 轮 poll 空管道 + 子进程写端存活）：
  PASS。
- 完整 LA buildstorm 无追踪连续 3 轮（12C/8G、官方 pub 镜像、LOG=off）：
  1. `BUILDSTORM_COMPILE ok=true elapsed_s=1606.00 bytes=1714568`，qemu exit=0
  2. `BUILDSTORM_COMPILE ok=true elapsed_s=1596.00 bytes=1714568`，qemu exit=0

## LA 内层 QEMU 启动 ArceOS 极慢排查：LOG=info 追踪放大，LOG=off 正常

**Date:** 2026-08-16 +08:00
**Author:** AI:DeepSeek | Human:lzm
**Tags:** [area:loongarch64, area:buildstorm, area:qemu, area:trace, type:performance, type:debugging]

**Summary:** LA 内层 QEMU（MangoCore guest 内运行 qemu-system-loongarch64 启动
ArceOS hello）在 `LOG=info` 内核上极慢，180s 观察窗内只输出到 OVMF 早期
PROGRESS CODE，最终被测试脚本 kill（`rc=137`），拿不到 `Hello, world!`。
相同内核源码、相同 overlay 和 12C/36G 外核配置下，`LOG=off` 连续 3 轮均在
约 137–143s 内完成内层启动并 `rc=0`。因此这是 syscall 追踪开销问题，不是
新的调度/IPI/锁卡死。

**证据：**
- LOG=off（buildstorm kernel, 12C/8G）：`MANGO_LA64_LONG_WAIT rc=0
  start=30 end=163 loops=25`，即内层约 133s。
- LOG=off（12C/36G × 3）：内层分别约 138s、137s、137s，均 `rc=0`。
- LOG=off 且外层关闭 MTTCG：内层约 143s，仍 `rc=0`。
- LOG=info（12C/36G）：内层 `MANGO_LA64_LONG_BG uptime=40` 后，
  30/60/90/120/150/180s 输出行数仅 4/6/12/15/19/21，180s 时
  `MANGO_LA64_LONG_ALIVE`，脚本 kill，`MANGO_LA64_LONG_WAIT rc=137`；
  194s 内日志 29.8 万行，其中 `[syscall] clock_gettime` 21.0 万条、
  `futex` 4.9 万条、`ppoll` 1.7 万条。

**结论/处置：**
- 正式 50 分钟评测必须使用 `LOG=off` 构建；`make buildstorm` 默认 `LOG ?= off`
  已满足。`LOG=info` 只用于局部 bug 定位，不能作为 LA 正式评测内核。
- 以 LOG=off 的 LA buildstorm 编译 1572–1606s + 内层 QEMU 137–143s + 外层
  启动约 30s 计，总预算约 29–30 分钟，低于 50 分钟墙钟。
- 若仍需要在 LOG=info 下观察内层 QEMU，可先只跑 boot 阶段，不建议跑完整
  BuildStorm。
