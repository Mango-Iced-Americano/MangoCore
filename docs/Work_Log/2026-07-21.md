### LA64 mmap arena 边界修复与双架构最终证据

**涉及文件：**
- `os/src/hal/arch/loongarch64/config.rs` — 修正用户 mmap arena 结束边界。
- `os/src/hal/arch/loongarch64/kern_stack.rs` — 保持 one-based TID 的 trap-context 槽位计算与范围保护。
- `os/src/mm/mmap.rs` — 在普通 mmap 路径中于 unmap 前拒绝与 trap window 相交的 LA64 `MAP_FIXED` 和 `MAP_FIXED_NOREPLACE` 请求。
- `os/src/mm/address_space.rs` — 保持新映射路径直接返回已分配的 trap-context PPN。
- `os/src/task/pid.rs` — 保持进程和线程槽位分配边界。
- `user/src/layout.rs` — 同步用户地址布局中的 mmap arena 结束边界。
- `user/src/bin/regression/main.rs` — 注册 6 项 regression 用例。
- `user/src/bin/regression/regression_mmap_edge_cases.rs` — 覆盖非固定 mmap、固定映射边界和未对齐 `mprotect`。
- `user/src/bin/regression/regression_clone_vm_second_slot.rs` — 验证第二个 trap-context 槽位不会与 trampoline 或相邻窗口冲突。
- `scripts/test-la64-regression-gate.sh` — 提供 LA64 regression 日志分类和 PASS gate。

**根因与修复：**
- `USR_MMAP_END == TRAMPOLINE` 使半开 mmap arena 错误地覆盖了 `[TRAP_CONTEXT_BASE, TRAMPOLINE)`，因此 LA64 的固定映射请求可能触及 trap-context window。
- 最终修复将 exclusive end 设置为 `TRAP_CONTEXT_BASE`，使 mmap arena 明确为 `[USR_MMAP_BASE, TRAP_CONTEXT_BASE)`。普通 mmap 和 SysV shm mmap 都在 unmap 前拒绝与 trap window 相交的 LA64 `MAP_FIXED`、`MAP_FIXED_NOREPLACE` 请求。
- trap-context 槽位仍按 `TRAP_CONTEXT_BASE + (tid - 1) * PAGE_SIZE` 计算，并以 `1 <= tid <= KERNEL_STACK_MAX_SLOTS` 做保护。新映射路径直接返回已分配的 PPN，避免冗余页表重查。

**验证：**
- Docker 串行执行 preflight、`trap-slots`、`mmap-arena`、`trampoline`、`classifier` contracts，随后按 RV64 build/regression、LA64 build/regression 和最终 LA64 classifier 顺序完成验证，未并行构建双架构。
- 安全非固定 red 测试已保留：`mmap` 接受 trap-context slot-2 hint，记录为 `not ok 2 mmap_edge_cases`，分类器为 `STATE=TEST_FAILURE STATUS=0`。历史 RED 证据目录为 `docs/Work_Log/evidence/2026-07-21/la64-mmap-arena-red-20260721T053537+0800/`。
- 最终 RV64 → LA64 串行回归均为 TAP `1..6`，各有 6 个 `ok`，包含 `ok 2 mmap_edge_cases` 和 `ok 6 clone_vm_second_slot`，且 LA64 分类器精确为 `STATE=PASS STATUS=0`。
