### B37 affinity-aware 新任务初始放置

**状态：`pass`；默认 CPU0-only mask 保持不变。** `publish_task()` 不再无条件把普通
新任务投到 CPU0，而是按任务继承的 `cpus_allowed`、当前可调度 CPU 和近似负载选择首次
owner。这样父线程已经收紧到非 CPU0 mask 后执行 clone/fork，子任务不会在首次发布时触发
“CPU0 不在允许集合”断言。远程 Running/Blocking affinity、默认全核 mask 和 steal 仍未实现。

**实现与原因：**

- `run_queue::select_runnable_cpu()` 统一过滤 affinity、online、scheduler-ready 和 STOP，
  preferred CPU 的负载不超过最小值 `+1` 时保留 locality，否则选择
  `nr_running + current_present` 最小且 ID 最小的 CPU。计数是无锁快照，只决定放置质量，
  owner 仍由 runqueue 临界区和 `sched_state` 提交。
- `CpuTaskState.current_present` 在 current 槽安装后 Release 置位，在 idle 栈真实取走 current
  后 Release 清零。此前的 `cpu_has_current()` 需要取得 processor 锁；用原子提示避免 Blocked
  wake 在持有 `TASK_MANAGER` 时新增 `TASK_MANAGER -> processor` 锁序。
- `publish_task()` 只有在本 CPU 没有 current 的启动窗口显式走 CPU0。init/ktest runner 的
  发布早于 BSP 进入 `run_tasks()`，此时 scheduler mask 尚无 bit0；把它交给通用过滤会制造
  空候选。普通 clone/fork 均有 current，走通用选择器并把调用 CPU 作为 locality 提示。
- `spawn_ktest_task_on()` 设置单 bit mask 后改走普通 `publish_task()`。现有 AP 定向测试因此
  动态覆盖生产选择器，不增加测试专用生产字段或临时 IPI reason。
- current 自迁移、Queued affinity 和 Blocked wake 复用同一个选择器；目标 owner 的最终合法性
  仍由各自已有的 runqueue/registry 协议复核，不把负载快照当作同步原语。

### B38 远程 Running/Blocking affinity owner 交接

**状态：`pass`；没有新增调度状态。** 正 TID 的 `sched_setaffinity()` 现在可以处理正在其它
CPU 运行或正进入阻塞窗口的线程。若新 mask 仍包含当前 owner，写侧在线性化点原地更新；若
排除 owner，则 syscall 必须等 owner 在现有任务安全点完成
`Running(source) -> Queued(target)` 后才返回，避免 mask 与 current owner 短暂不一致。

**实现与原因：**

- 每个 TCB 增加唯一 `remote_affinity_request` 槽；请求对象只保存不可变的 mask、target 和
  `Pending/Applied/Retry` 完成态。它是 owner 交接的会合对象，不是第二套任务状态机，也不改变
  `TaskStatus` 的调度所有权真值。
- 远程写侧先按 affinity/online/scheduler/STOP 规则选择目标并同步该任务的内核栈映射，再在
  请求槽锁内复核 `Running(owner)`、本地迁移请求与既有远程请求。锁外发送 RESCHEDULE，调用者
  用既有 `suspend_current_and_run_next()` 协作等待；因此不在持锁区等待 IPI、TLB ack 或调度。
- owner 已切回 idle 栈后，`finish_switch_out()` 持请求槽锁取走请求、发布新 mask，并通过单个
  目标 runqueue 完成状态/容器交接，最后以 Release CAS 标记 Applied。真实锁嵌套是
  `remote_affinity_request -> 单个 RunQueue`；它保证第二个写者不能插入检查与交接之间，且没有
  `RunQueue -> remote_affinity_request` 反向路径。
- `begin_interruptible_sleep()` 固定使用
  `TASK_MANAGER -> remote_affinity_request`，把 `Running -> Blocking`、registry 登记与旧请求取消
  放在同一临界区；远程调用者观察到 Retry 后再等待状态稳定，复用 Running 或 Blocked 协议。
  `mark_zombie()`、current 自迁移和显式 migration 同样通过请求槽取消旧请求，防止退出或本地
  写侧与远程写侧共同声明 owner。
- syscall 保留 Linux raw mask/TID/uaccess 语义；这里只替换非 current Running/Blocking 的
  `EOPNOTSUPP`，New/Zombie 或已离开可管理容器的对象仍返回不支持。
- focused 新增第 15 项 `smp::running_affinity_waits_for_owner_handoff`：先以 bit0|bit1 验证
  owner 合法时不迁移，再以 bit0 验证远程调用直到 CPU1 current 已释放才返回，任务最终恰好
  在 CPU0 恢复一次并成为 Zombie。STOP 顺延到第 24 项，证明没有遗留队列或请求污染。

**锁序与证据边界：**

- 当前新增关系为 `task.inner -> remote_affinity_request -> 单个 RunQueue` 与
  `TASK_MANAGER -> remote_affinity_request -> 单个 RunQueue`；实际路径不同时持有
  `task.inner` 和 `TASK_MANAGER`。请求完成只做原子 CAS，不唤醒 WaitQueue、不取得 manager。
- 动态用例覆盖一个远程请求者与稳定 Running owner，并覆盖 mask 包含/排除 owner 两条分支。
  两个请求者同时更新同一远程 TID、以及确定性命中 `Running -> Blocking` 瞬态，仅完成了槽锁、
  Retry 和锁序源码审计，尚未做竞争压力测试。
- 普通用户任务默认 mask 仍是 bit0；B38 完成写侧协议不等于已经开放默认全核调度。

### B39 Per-CPU 调度 tick 与 CPU0 全局 timer owner

**状态：`pass`；普通任务默认 mask 仍为 bit0。** B38 后没有直接放宽默认 affinity，因为
AP 当时只靠 syscall/yield/远程 RESCHEDULE 到达调度安全点。若把普通 CPU-bound 用户任务放到
AP，一个不执行 syscall 的循环可能永久占住该 CPU。B39 先补齐每 CPU 本地调度 tick，同时保持
全局 timer callback 只有 CPU0 一个执行者，为后续默认全核调度建立必要的抢占基础。

**实现与原因：**

- `PerCpu` 增加独立的 `sched_tick_deadline_ns`；删除全局
  `NEXT_SCHED_TICK_NS`。每个 CPU 只推进自己的 100 Hz 绝对 deadline，避免多个 CPU 对同一
  deadline 重复 compare/exchange，或一个 CPU 的迟到 tick 改写另一个 CPU 的调度节拍。
- hard timer IRQ 仍只发布本 CPU deferred 标志。`run_task_safe_point()` 与 AP idle 循环在
  任务安全点消费标志、设置 `need_resched` 并重新编程 one-shot timer；不在中断帧中拿普通锁
  或直接 context switch，保持现有安全点抢占模型。
- CPU0 独占全局 timer queue、timeout、timerfd 和网络后台 poll。CPU0 每次取本地 tick 与
  全局最早 deadline 的较小值；AP 只推进本地 quantum，绝不重复执行全局 callback。
- AP 插入更早全局 timer 时，在释放 timer queue 锁后发送独立
  `TIMER_REPROGRAM` IPI。handler 只 Release/Acquire 发布原子请求，CPU0 在安全点重新读取
  queue。没有复用 `RESCHEDULE`，因为纯 deadline 变化不等于当前任务需要切换。
- `timer_cpu_init()` 成为 CPU0/AP 共用入口：先发布本 CPU deadline、编程 one-shot timer，
  最后开放 timer interrupt。RISC-V 不再在 `machine_init()` 提前开 timer；LoongArch 开
  timer line 时保留 ECFG 中已经开放的 IPI line，并把 InitVal 对齐到硬件要求的 4 倍数。
- LA64 `CLOCK_FREQ` 从 `static mut` 改为 AtomicUsize。CPU0 在 `machine_init()` 中 Release
  发布，AP 在 scheduler-ready 后 Acquire 读取；这样多核 timer 初始化不再依赖“运行期没人
  再写”的外部 unsafe 约定。
- AP 仍可用 relaxed atomic 累加调度/timer 性能计数，但 `print_snapshot` 会继续读取 FS/net
  全局状态并打印 console。人工沿 deferred 调用链发现这一隐藏入口后，把格式化快照以及
  timer/scheduler 周期触发限制到 CPU0，避免 AP timer 绕过共享子系统门禁。
- focused 新增第 8 项 `smp::user_timer_preempts_on_secondary_cpu`。它让 CPU1 先运行不含
  syscall、yield 和数据 load/store 的用户死循环，再把 kernel helper 排在同 CPU 后面；helper 只有
  在本地 timer 真正切出用户任务后才能执行，并验证该任务已经成为 `Queued(1)`。清理路径只在
  超时失败后才发送 RESCHEDULE，不能制造成功假象。

**官方规范依据：**

- RISC-V 依据 SBI TIME extension：`set_timer` 接受绝对 `stime_value`，未来 deadline 会清除
  pending timer interrupt，因此代码保存绝对 deadline 并在开放中断源前先完成编程。
- LoongArch 依据官方 Vol.1：stable counter 是每核稳定计数源，timer 使用本地 line 11；
  `TCFG.InitVal` 低两位固定为零，`TICLR` 写 1 清除。由此采用 per-CPU one-shot、4 倍数
  InitVal 和“先编程后开放”顺序。

### B40 跨 CPU 线程组退出与 clone 发布门禁

**状态：`pass`；改动保持未提交，等待人工审查。** 旧 `exit_group_and_run_next()` 会由发起
CPU 直接移除并清理其他 sibling，即使目标仍是 `Running(remote)`；这可能释放远端 CPU 正在
使用的内核栈、用户映射和 TCB。B40 改成“发起者只发布停止请求，owner CPU 在安全点自清理，
最后一个清理完成者收尾进程”的分布式退出协议。

**实现与原因：**

- PCB 新增私有 `ThreadGroupState`，用同一把 `thread_group` 锁串行化成员发布和永久退出
  gate。`group_exit_code: AtomicU64` 以 `u32 code + 1` 编码，零值表示未退出；安全点可以
  Acquire 读取而不进入组锁。
- `publish_thread()` 在组锁内完成“检查 gate、登记 Weak 成员、领取 live token、执行一次
  `New -> Queued(cpu)`”。`try_publish_task[_on]()` 在 gate 已关闭时返回 `EAGAIN`，clone
  syscall 走未发布子任务的既有回滚路径。由此不存在“退出快照完成后又出现未被停止的新线程”。
- 第一个 group-exit 调用者在组锁内 Release 发布退出码并取得成员快照，随后在锁外给 sibling
  排队不可忽略的 `SIGKILL`：Blocked/Blocking 被唤醒，Queued/Running owner 收到
  `RESCHEDULE`，Migrating 使用在线 CPU 广播兜底。发起者不替远端线程释放任何资源。
- `run_task_safe_point()` 优先检查永久退出码。所有真实清理统一收敛到
  `finish_current_exit()`：先保存 IRQ 状态，再在受控开中断窗口完成用户清理与 TLB 等待，
  最后回到关中断的调度入口；因此从 trap-return 的 IRQ-off 安全点退出也仍能响应 shootdown。
- `sleep_interruptible()` 在完成 `Blocking` 登记并释放 `TASK_MANAGER` 后复查 group-exit；
  若停止请求刚好穿过 `Running -> Blocking` 窗口，就由阻塞线程自唤醒，避免永久睡眠。
- `remove_thread()` 的 live token 改到 clear-child-tid、futex、用户资源回收和 TLB commit
  之后，以 AcqRel 发布。只有返回 `Some(0)` 的最后清理者能够执行进程级收尾。
- focused 新增 `smp::group_exit_stops_remote_sibling`：CPU0 发起真实 group-exit，CPU1 上的
  Running sibling 与稳定 Blocked sibling 都在 owner 安全点成为 Zombie；退出 gate 关闭后
  的 late sibling 精确返回 `EAGAIN`、保持 New 且从未运行，最终 live count 为零、进程 Zombie。

**官方设计核对：**

- Linux `do_group_exit()`/signal group-exit 路径使用共享退出状态通知线程组，而每个线程仍从
  自己的 `do_exit()` 清理；`de_thread()` 另有等待其他线程退出的同步语义。B40 因而不把
  永久退出和多线程 exec 混成一个协议。
- DragonOS 的 `ProcessManager::exit()` 同样让当前执行流完成自身退出与调度切换。MangoCore
  保留现有 TCB/PCB 模型，只迁移“不能由发起 CPU 远程析构运行中线程”这一所有权原则。

**DeepSeek 协作与人工裁决：**

- 初轮只读审查与双架构 build/focused 均通过，用于确认锁序、late-clone 门禁和 owner 自清理
  主体设计。
- 首次最终冻结任务启动后，人工审查发现 `bool::then_some(encoded - 1)` 会先求值参数：
  `encoded == 0` 时 debug 构建下溢 panic、release 下静默回绕。立即终止该过期任务，改为显式
  `if encoded == 0` 分支后重新冻结；失败任务不计作验证证据。
- DeepSeek 最终报告把稳定 Blocked 用例扩大解释成“确定性覆盖 Blocking 登记瞬态”。人工没有
