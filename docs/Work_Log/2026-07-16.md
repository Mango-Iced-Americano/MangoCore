### Harden lwext4 C library build invalidation — C source changes trigger archive rebuild + cargo re-link

**涉及文件：**
- `dependency/lwext4_rust/build.rs` — 新增 51 行：`cargo:rerun-if-changed=` 覆盖所有 C 源文件（`src/*.c`）、头文件（`include/*.h` 及 `include/misc/*.h`）、cmake 构建配置（`CMakeLists.txt`、`elf-linux-gnu.cmake`、`ulibc.c`）以及档案文件本身；嵌入 `cargo:rustc-env=LWEXT4_ARCHIVE_TS=<mtime>` 以在档案重建时强制 cargo 重新链接

**修复效果：**
1. **Make 层级**：任一 `.c` / `.h` / `CMakeLists.txt` / `elf-linux-gnu.cmake` / `ulibc.c` 发生更改 → `make` 检测到先决条件比目标新 → 重新运行 cmake + make 重建 `.a` 档案
2. **Cargo 层级**：档案重建后其 mtime 变化 → `build.rs` 监控到变化（`cargo:rerun-if-changed=<archive>`）→ 重新运行 build 脚本 → 输出的 `cargo:rustc-env=LWEXT4_ARCHIVE_TS=<mtime>` 不同 → Cargo 指纹变化 → 重新链接内核二进制
3. **架构隔离**：rv64 和 la64 分别使用独立的 `LWEXT4_RV_*` / `LWEXT4_LA_*` 变量集和独立的 `$(wildcard *)` 收集，互不干扰
4. **不生成/不包含构建产物**：`$(wildcard ...)` 只匹配 `src/*.c` 和 `include/*.h`，不匹配 `build_lwext4-rv64/`、`build_lwext4-la64/` 等生成目录
5. **原有命令和标志保持不变**：仅添加先决条件和 cargo rerun/rustc-env 指令，未修改工具链、链接器标志、cmake 参数或 `ulibc.c`/`CMakeLists.txt` 的注入逻辑

### LwExt4PageCacheBackend 使用物理EOF替代逻辑EOF进行空洞读取

**涉及文件：**
- `os/src/fs/ext4_lwext4/page_cache.rs` — 移除 `ensure_size_known()` 方法；重写 `read_page()` 和 `read_pages()`，锁定 `fs.lw` 后立即通过 `f.file_size()` 快照 lwext4 物理 EOF，不在物理 EOF 处或之后进行 seek/read；全部超出物理 EOF 的页面零填充；部分超出则只读取物理交叉部分并补零

**修改细节：**
- `read_page()`：持锁 → 打开 → 快照 `physical_eof` → 若 `offset >= physical_eof` 则零填充并返回 PAGE_SIZE → 否则只读取 `min(PAGE_SIZE, physical_eof - offset)` → 零填充尾部
- `read_pages()`：持锁 → 打开 → 快照 `physical_eof` 一次 → 逐页判断：全部超出 → 零填充；部分超出 → seek + 只读物理部分 + 零填充尾部 → 返回 `pages.len() * PAGE_SIZE`
- `ensure_size_known()` 已移除（在移除 `read_page` 调用点后无调用方）
- `npages()`、`write_page()`、`write_pages()`、`note_logical_size_atomic()` 保持不变

**根因：** `logical_size`（AtomicUsize）之前承担双重角色——既是 lwext4 的物理 EOF，也是 VFS 可能通过 ftruncate 等操作膨胀的逻辑 EOF。lwext4 ftruncate 扩展为无操作（不分配块），因此 `read_page` 会使用过时的逻辑大小，尝试在空洞区域内扫描/读取，触发 EIO。修复后将读取决策建立在每次读取时采集的 lwext4 真实物理文件大小之上。

**验证：**

**备注：** `LWEXT4_SIZE_UNKNOWN` 哨兵仍在 `npages()` 和 `write_pages()` 中使用，`logical_size` 仍用于回写裁剪——其语义现在仅限于"回写边界跟踪"，不再用于读取决策。

### lwext4 truncate 磁盘持久化修复 — 截断前零填 [len, old_size) 防止旧数据泄露

**涉及文件：**
- `os/src/fs/ext4_lwext4/layout.rs` — `Ext4OSInode::truncate()` 重写（第 1309-1364 行）：在获取 `self.fs.lw.lock()` 之前调用 `self.logical_size_or_refresh()` 获得 `old_size`（避免递归锁）；当收缩（`len < old_size`）时，通过已打开的 lwext4 文件句柄 seek + 写零填满 `[len, old_size)` 范围，然后调用 `file_truncate(len)` 截断；PageCache 一致性保留（`pc.truncate(len)` + 尾页直接零填）。

**根因：** 前一版修复仅在 PageCache 内存帧上直接零填尾部。页面驱逐或重挂载后，磁盘上 `[len, old_size)` 范围内的旧字节仍然存在——`ftruncate(256→512)` 重新分配块会导致陈旧字节 97 在 cold-cache 读取时暴露。

**修复：** 顺序为先零填后截断：
1. 持 lw 锁前获取 `old_size`（`logical_size_or_refresh()` 内部会锁 `self.fs.lw`）。
2. `len < old_size` 时：`file_seek(len, SEEK_SET)` → `file_write` 零块（4KB 分块，无限循环防护：写入 0 字节时 `break`）。
3. `file_truncate(len)` 截断文件。
4. PageCache 一致性：`pc.truncate(len)` + 对保留部分页尾直接零填（绕过后端 writeback，避免扩展已截断文件）。

**验证：**
- `make -C os rv64-kernel-build-only` ✅（Docker `pxy-mangocore-os-dev-1`，无新 warning）
- `make -C os la64-kernel-build-only` ✅（同上）

**备注：** 目标 LTP 用例 `ftruncate01` / `ftruncate01_64`（收缩→扩展序列）。零填在仍在 EOF 内时发生，因此磁盘持久化是持久的；`LwExt4PageCacheBackend::write_page` 写入完整页面，不可用于截断后的尾页零填。PageCache 尾页零填保持仅内存态（`frame_for_read` + `get_bytes_array`），避免触发回写。旧条目：`.omo/evidence/task-3-fs-longrun-correctness-lifecycle.log`。

### BackendLifecycle v2 — 共享后端显式生命周期状态机（mount06→mount07 GREEN）

**涉及文件：**
- `os/src/fs/vfs/mount.rs` — 删除 `BACKEND_REFS` / `backend_data_key` / `acquire_backend` / `release_backend`（含 raw pointer transmute 和 Drop 内 on_umount 回调）；新增 `BackendLifecycle`（Active/Dying/Dead 状态机，packed AtomicU64 跟踪 refcount，registered AtomicBool 防止 count-0 registry leak）；新增 `LIFECYCLE_REGISTRY` 和 `drain_one_dying_lifecycle()`（registry lock 外执行 on_umount）。生命周期在 `acquire()` 首次 0→1 时惰性注册。MountFS 字段 `inner_filesystem: Arc<dyn FileSystem>` → `lifecycle: Arc<BackendLifecycle>`。`Drop` 仅含 `lifecycle.release()` + atomic counter（无 logging/lock/allocation/callback）；cycle/cache 清理保持在显式 `finish_umount_cleanup` / `finish_propagated_cleanup` 路径。删除 `MOUNT_LIFECYCLE_SHARED_TEARDOWN` 计数器（`lifecycle_snapshot()` 返回 4 元组）。新增 `LC_NEW/ACQUIRE/RELEASE_DYING/DRAIN` 语义计数器。
- `os/src/fs/vfs/propagation.rs` — `propagate_to_mount`：EEXIST-descend 分支返回前清理临时 MountFS（`MOUNT_LIST.remove_fs` + `set_self_mountpoint(None)`），防止临时挂载泄露。
- `os/src/fs/sysfs/files/diag.rs` — 移除 `mount_lifecycle_shared_teardown`；新增 `lc_new/lc_acquire/lc_release_dying/lc_drain` 计数器。
- `os/src/syscall/fs/sys_mount.rs` — 新鲜挂载路径创建 `BackendLifecycle::new(fs)` 后传入 `mount_subtree_inner`。
- `os/src/syscall/fs/common.rs` — `do_bind_mount` / `apply_rbind_snapshot` 走 `source.lifecycle.clone()`。
- `os/src/fs/mod.rs` — VFS_ROOT 和 `mount_common_filesystems` 全部 `MountFS::new(BackendLifecycle::new(fs), flags)`。
- `os/src/fs/vfs/mod.rs` — 导出 `BackendLifecycle` 和 `drain_one_dying_lifecycle`。
- `os/src/task/processor.rs` — `run_tasks()` 每 128 tick 调用 `drain_one_dying_lifecycle()`。
- **生成文件恢复：** `os/src/lang_items.rs` / `user/src/lang_items.rs` 经 `git restore` 至提交状态（不留 build 过程残留 diff）。

**设计要点：**
- `BackendLifecycle` 独占 `Arc<dyn FileSystem>`；每 MountFS 持有 `Arc<BackendLifecycle>`。
- 新鲜构造走 `BackendLifecycle::new()` → `acquire()`（count: 0→1，惰性注册到 registry）。
- bind/rbind/propagation 从源 MountFS 派生：共享同一 lifecycle Arc，`acquire()` increment count。
- MS_MOVE 不改变生命周期计数。
- `Drop` 只做 `lifecycle.release()`（CAS count→0 则 Active→Dying），不触发任何回调、锁、分配或日志。
- Scheduler drain 逐个取出 Dying 生命周期，在 registry 锁外调用 `on_umount()` 然后标记 Dead。
- 不使用 `Arc::strong_count` 做语义决策。

### Fix: ensure_page_cache() registry-reuse path replaces stale backend logical_size

**涉及文件：**
- `os/src/fs/ext4_lwext4/layout.rs` — `ensure_page_cache()`: 命中 registry 复用 PageCache 后，不再直接返回旧 backend（指向先前 inode 实例的 `Arc<AtomicUsize>`），而是构造新 `LwExt4PageCacheBackend` 指向当前 inode 的 `self.logical_size`，通过 `pc.set_backend()` 替换

**根因：** 全局 `fs.page_caches` registry 持有 `Arc<PageCache>`，其 backend 的 `logical_size` 引用的是旧 `Ext4OSInode` 的 `Arc<AtomicUsize>`。dentries 回收后重新创建 inode 时，`ensure_page_cache()` registry 命中路径直接返回旧 PageCache。此后 `write_at` 更新新 inode 的 `self.logical_size` 原子，但 writeback 后端仍读取旧原子的值 → EOF 夹钳在旧大小上 → 扩展写入的数据不落盘。

**修复：** registry 命中路径改为：克隆 `Arc<PageCache>`，释放 registry 锁（临时守卫在 `.cloned()` 后结束），构造新 backend 并调用 `pc.set_backend()`，再存入 `self.page_cache`。

- `make la64-kernel-build-only` ✅

**备注：** 此模式属于"registry 对象复用时的内部状态刷新"通用模式—任何 registry 持有带 per-instance 引用的对象时都需注意。
