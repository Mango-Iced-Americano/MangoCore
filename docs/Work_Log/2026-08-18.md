## legacy free-list buddy 对照实验：allocator 是当前性能提升的主导贡献者

**Date:** 2026-08-18 +08:00
**Author:** AI:Sisyphus | Human:pxy
**Tags:** [area:mm, area:heap, area:performance, type:measurement, type:validation]

**结果：** 用 `legacy_buddy_heap` feature 把全局堆切回**最原始的 free-list 线性扫描
buddy**（`buddy_system_allocator::Heap<32>`，无 bitmap / 无 metadata / 无 slab，新增
`os/src/mm/heap_allocator_legacy.rs`），内核其它部分完全不变，同 workload（basic+busybox
pre + 全量 lmbench，4 窗口，rv64）复测。退化**立即复现**：`Process fork+execve`
5,147→**7,512 (+46%，逐窗口单调)**、`Pipe latency` 664→**930 (+40%，单调)**、
`fork+exit` 4,786→6,909 (+44%)；而 `null syscall`/`stat`/`read`/`write` 两类后端均平稳
（读取类免疫，与原报告一致）。证明**当前的全面提升主要来自 allocator 优化本身**，
9.2 的 metadata+slab 数据不是「内核其它优化」造成的表观差距。

**涉及文件：**
- `os/Cargo.toml` — 新增 `legacy_buddy_heap = []` feature（默认关闭）。
- `os/src/mm/heap_allocator_legacy.rs` — 新增独立 legacy 全局堆后端（`Heap<32>` +
  `add_to_heap` 挂 runtime，无 slab），含 GlobalAlloc/alloc_error_handler/统计等同名 API。
- `os/src/mm/mod.rs` — legacy feature 开启时用 re-export 伪模块顶替 `heap_allocator`，
  默认路径零改动。
- `docs/09_debug/buddy-allocator-scan-drift.md` — 第 9 节新增 9.4 对照实验表格与结论。
- `docs/Work_Log/evidence/2026-08-18/drift-lmbench-rv64-legacy-freelist.log` — 完整日志。

**验证：**
- 默认（无 feature）与 legacy（`EXTRA_FEATURES=legacy_buddy_heap`）双 build 均 ✅。
- legacy GlobalAlloc 首版有 double-lock 死锁（GlobalAlloc 内先 `self.heap.lock()` 又调
  内部 `self.alloc()` 再次 lock，首分配即挂）——已改为单次持锁内联操作后正常启动。
- legacy 启动自检：256 次 4K alloc/dealloc 全页对齐、无损坏。
- 8 窗口（musl W0–W3 + glibc W0–W3）复测完整跑完，数据见 9.4。

**关键教训（derived 盘累积状态污染对照）：** 实验初期多次 `conf-inject`（每次
`e2fsck -fy` + debugfs）会在 derived 盘上累积 metadata 状态，导致 `vda`（ext4 root）
挂载报 `another_ext4 BRIDGE EIO`——盘本身 `e2fsck -n` clean，且**连默认 metadata 内核
都稳定挂载失败**（一度误判为 legacy allocator 独有 bug）。**从 official 重新派生 + 一次性
注入 conf 后挂载恢复**。凡做 allocator/性能 A/B 前，必须重新生成干净 derived。

**Mango Gate：** `mango-workflow loaded=yes`；references=`harness-patterns.md`
（性能 A/B 前验证运行环境/镜像新鲜度，排除盘面状态污染后再归因 allocator）。

## 2K1000LA 本地持久根、自动启动与 P4 恢复

**Date:** 2026-08-18 +08:00
**Author:** AI:Codex:GPT-5 | Human:lzm
**Tags:** [area:loongarch64, area:board, area:block, area:fs, area:net, type:debugging, type:validation]

**结果：** P3 已重建为无 journal 的完整持久根，包含 BusyBox `/sbin/init`、inittab、rcS、
基础 `/etc` 和 `/boot/kernel-A.ui`。U-Boot 已保存“P3 A 槽 → TFTP → 原 bootcmd”三级启动，
保留 3 秒调试截停窗口；本地启动和 TFTP 调试均已实板验证。旧 P4 的 `apk-root` I/O error
定位为 ext4 extent 元数据损坏，已用受限的原位替换模式重建为干净无 journal P4。

**根因与安全边界：** 首版 P3 由宿主默认 ext4 参数生成，带 journal；首轮可启动，但硬复位后
当前 another_ext4 不能 replay journal，停在后端初始化。生成器现强制 `^has_journal`。
P4 原始 SATA 块读取稳定，而损坏 inode 的 extent 指向 physical block 0，因此不归因于 SSD
硬件。旧 P4 内容只得到两份约 64 MiB 的部分取证 tar，随后按授权重建；不能将其表述为完整备份。

**实板证据：** 最终 uImage 为 `16,639,472` B，SHA-256
`1fd7fef817e161f8ecfdc6cb378ae504d05e9d185c9607173b6cf870cf1ed33c`，U-Boot CRC32
`e32f750f`。P3 写入 `/root/persist-v2`、sync、硬复位并本地自动启动后，SHA-256
`193bc0922d3a50bf1cef5eab4baf065c8f85bc4625340f8edf9c3c6fe7b7be5a` 不变。P4 以 16 个
256 MiB 块写入并逐块读回一致，MBR CRC32 保持 `6538e5cb`；`apk-root` 和状态哨兵可读，
RW 写入 `REBUILD_OK`、sync、卸载、RO 重挂后读回成功。GMAC DHCP 获得 `192.168.2.2/24`，
网关 `192.168.2.1` 三次 ping 全通；公网 `1.1.1.1` 不通属于当前上游/桥接边界。

**回归：** `/tests/fs_test` 通过 74/76，核心 1–72 和 proc mount 均通过；仅两个性能项因
fixture 缺 `/tmp/bb` 失败。Unix socketpair 的 DGRAM/STREAM 通过；named STREAM connect
返回 `-111` 并使父进程停在 accept，是独立待修回归。旧 `la64-2k1000-core-tests` 目标仍请求
已删除 feature `sata_scratch_rw`，未通过恢复废弃 feature 绕过。

**宿主门禁：** Docker 内 `make toolchain-preflight`、Python `py_compile` 和
`scripts/test-init-lifecycle-contract.sh` 通过；P3/P4 均由 e2fsck 完整五阶段只读检查为 clean，
`dumpe2fs` 确认两者 feature 均不含 `has_journal`。P3/P4 镜像 SHA-256 分别为
`b533f9cf80144926b97d53aa75a1444c4d35e42054cce242c0bbd278c37899f6` 和
`ff8bceeb48efa3968bd8df2e30284a773f971872dc7d3116226e4361dc2c298e`；`git diff --check` 通过。

**涉及文件：** P3/P4 生成与受限写入脚本、本地启动配置脚本、LoongArch 主线 GMAC/DHCP
构建入口、P3 `/etc` fixture、生命周期合同，以及 FS/AHCI/工作日志文档。

## 2K1000LA 默认持久根实板闭环

**Date:** 2026-08-18 +08:00
**Author:** AI:Codex:GPT-5 | Human:lzm
**Tags:** [area:loongarch64, area:board, area:block, area:fs, type:debugging, type:validation]

**结果：** `la64-2k1000-mainline` 已在真实 2K1000LA 上把 SATA P3
`/dev/sda3` 作为默认可写根，PID1 从 initramfs 完成运行期挂载绑定后 chroot，并执行
P3 的静态 `busybox sh -i`。写入标记、`sync`、立即复读、硬件 RESET、重新 TFTP 启动和
第二次只读复核全部通过。

**从首轮失败到最终布局：**

- 修复前 panic 位于 `SataBlock::new -> pci_init().expect("AHCI new failed")`。恢复固定
  `00:08.0`、DMW2 MMIO、BAR/CAP/PI、连续低端 DMA 和错误传播后，实板识别
  `0014:7a08`、BAR0 `0x400e0000`、SSD `TS32GMTS400/S0322B`、`62533296` sectors。
- 首轮 `root=/dev/sda1` 成功挂载但 PID1 拒绝切根；盘面确认 P1 只有官方
  `glibc/musl/os_test.conf` 测试载荷。P4 虽有 `apk-root`，读取其 `bin/sbin` 返回 I/O
  error，未将可疑卷提升为默认根。P3 包含可执行 `bin/busybox`、bash、运行库和工具，故
  mainline 明确改用 `root=/dev/sda3`。
- P3 的 `/bin/sh -> bash` 能被 exec，但未进入可交互状态。最终 PID1 在 init/initproc
  之后显式执行 `/bin/busybox sh -i`，再保留 bash 作为更后的兜底；根完整性检查也要求
  BusyBox 可执行。

**实板证据：**

- 最终 uImage：`16,643,360` B，SHA-256
  `fd2504c76a9b4cfa6d16b36c5db83ac0c4cbbba8a0587804f8a0fa280efda7cf`；TFTP 长度一致，
  CRC32 `82690790`，两轮 `iminfo` 和 payload checksum 均通过。
- 两轮均输出 `[sata] AHCI ready`、`sda probe: 4 partitions`、
  `[ext4] backend: another_ext4`、`root device mounted at sdcard`、
  `mainline persistent SATA root active` 和 `mainline exec /bin/busybox sh -i`。
- 首轮执行：
