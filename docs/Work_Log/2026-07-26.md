## 2026-07-26

### 修复 /dev/shm sticky bit 与 os_test.conf mask

**涉及文件：**
- `user/src/syscall.rs` — 新增 `SYSCALL_FCHMODAT` 常量（53）和 `sys_fchmodat` 系统调用封装
- `user/src/usr_call.rs` — 新增 `chmod()` 便利封装，调用 `sys_fchmodat(AT_FDCWD, path, mode)`
- `user/src/bin/init/mounts.rs` — PID1 挂载 `/dev/shm` tmpfs 后调用 `chmod("/dev/shm", 0o1777)` 设置 sticky bit；导入 `chmod` 到作用域
- `os_test.conf` — 从测试期间的 `mask=0x010` 恢复为 `mask=0xFFF`

**验证：**
- Docker `pxy-mangocore-os-dev-1`（`/home/pxy/projects/MangoCore -> /app`）：
  - `make -B kernel ARCH=rv64 PROFILE=normal` ✅
  - `make -B kernel ARCH=la64 PROFILE=normal` ✅
- QEMU 冒烟：RV64 正常启动，init 序列完成，无 panic、无 EBUSY ✅
- `chmod("/dev/shm", 0o1777)` 在 devtmpfs 挂载和 tmpfs 覆盖后执行，tmpfs root inode 将获得 01777 权限

**备注：** 此前 `/dev/shm` 的 sticky bit 由内核 `os/src/fs/mod.rs` 中的 `set_metadata(&meta)` 设置，PID1 的伪文件系统挂载重构后不再经过该路径。修复方式是在用户态 `chmod(2)` 层级补充。仅 RV64 在 QEMU 中验证；LA64 的 `#[unsafe(naked)]` 编译错误为既有问题，与本次修改无关。未命中需要同步的 `code_paths` 文档；AI-Usage-Report 无需更新。
