# 2026-07-26 Work Log

## 2026-07-26

### SMP-P2-B12：AP→BSP IPI 请求/回复与无丢失 idle 等待

**范围与设计：**

- B09/B10 只证明 CPU0 能向 AP 单播和广播；CPU0 尚未打开本地 IPI line，
  AP 也没有安全的回复发送位置，因此不能据此外推双向通信。
- 本包只闭合真实 AP→BSP 往返及 idle check→wait 不变量，不引入 STOP、
  RESCHEDULE、runqueue、TLB shootdown 或普通长 syscall 中断窗口。
- reason mailbox 仍是可合并 bitset。测试在观察到每轮独立 ack 后才复用
  请求/回复 bit，事件次数由 ack sequence 表达，而不是错误地依赖 bit 累计。

**双架构实现与并发语义：**

- RV64 CPU0 在 machine init 中打开 SSIE；LA64 QEMU CPU0 配置运行期 IPI
  vector 并在 ECFG 中打开 IPI line。LA64 的调用受 QEMU cfg 约束，
  2K1000LA 继续保持单核路径。
- 两架构用户态和内核态 trap 共用同一个 IPI fast path：先清硬件 level
  source，再以 Acquire 消费 per-CPU mailbox。handler 只更新原子状态，
  不分配、不打印、不获取普通锁，也不从中断中发送新的 doorbell。
- AP 收到 request 后以 Release 发布 `round_trip_reply_pending`，返回
  独立 idle stack 后再调用普通 `send_ipi()` 回复 CPU0；发送错误只进入
  per-CPU 原子诊断计数。CPU0 handler 以 Release 增加 reply ack，等待方
  用 Acquire 观察。
- AP idle loop 改为一次性架构 wait：保存并关闭全局中断，重查 deferred
  work，无工作时执行一次 `wfi`/`idle 0`，随后恢复原状态。等待期间本地
  IPI line 仍 enabled，重查后的 doorbell 会保持 pending 并唤醒 CPU，
  从而闭合 lost-wakeup 窗口。
- focused test 由 CPU0 内核任务打开受控中断窗口，让每个 AP 顺序完成
  64 轮请求/回复；测试结束前消费可能到达的 deferred timer，避免把测试
  窗口的 timer 状态泄漏给后续用例。

**Docker 验证：**

- RV64 根 Make facade `CORE_NUM=4` normal kernel build：退出 0，
  124.445 秒；
- LA64 根 Make facade `CORE_NUM=4` normal kernel build：退出 0，
  130.783 秒；
- RV64 `CORE_NUM=4 KTEST=smp`：`online_mask=0xf`，7/7 PASS，
  128.256 秒；
- LA64 `CORE_NUM=4 KTEST=smp`：`online_mask=0xf`，7/7 PASS，
  131.622 秒；
- 每个架构覆盖三个 AP × 64 轮，共 192 次 AP→BSP 往返；RV64 本次
  `boot_hw_id=3`，同时覆盖非恒等逻辑/硬件 hart 映射；
- 四项验证前后的 tracked source 指纹一致，SHA-256 为
  `571b5d7b3439dc26613a7be69cc206560edbb81b05945b53d2f8c0735dd5fe25`；
- 确定性摘要位于
  `docs/Work_Log/evidence/2026-07-26/smp-b12-summary.md`。

**阶段结论：**

- `SMP-P2-B12=pass`，CPU0 已可在受控窗口接收真实 AP doorbell，AP 的
  hard-IRQ 与 deferred 回复边界及 check→wait 协议均有双架构四核证据。
- 整体 Phase 2 仍为 `partial`：STOP、通用交叉/并发 reason、10,000 次
  ping-pong、普通长 syscall 中断窗口和 RESCHEDULE 尚未完成。
- 本包没有形成新的通用故障调试模式，不追加 workflow references；
  双向 IPI 内存序和 idle 等待契约已同步到启动/trap 架构文档和 SMP 方案。
