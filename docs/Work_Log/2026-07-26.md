### SMP-P2-B14：长 syscall 受控中断窗口与调度状态交接

**范围与设计：**

- B12 只在 focused test 中手动开放 CPU0 中断；生产长 syscall 仍无法
  及时响应后续 shootdown/STOP 类 IPI。B14 只开放 user-syscall
  closure，不把缺页、信号或整个 scheduler housekeeping 扩大为开中断区间。
- 官方 RISC-V Privileged ISA 和 LoongArch Volume 1 都确认：进入 trap
  时硬件会保存旧全局中断位并清除当前位；返回指令再恢复。
  因此窗口必须在完整 trap frame/CPU-local 建立后才开放。
- 两轮独立只读审查审计了 trap-frame 生命周期、yield/block/exit、
  panic、LA64 PRMD/ERA 和测试顺序。首轮提议让整个 `run_tasks()`
  开中断，但该做法会同时暴露尚未审计的 console/net/FS 路径；复核后
  确认保留 IRQ-off legacy scheduler 不影响 B14 正确性。

**实现与并发语义：**

- HAL 新增 `with_local_interrupts_enabled()`：强制 IRQ-off 入口，guard 在
  正常返回/unwind 时先关中断再恢复入口状态。`exit/exit_group`
  等不返回路径由 `schedule()` 在切离前接管 IRQ-off。
- 双架构 syscall 分支均在释放 `task.inner` 后才进入窗口，结果写回、
  timer 安全点和信号返回仍在窗口外 IRQ-off 执行。
- `schedule()` 在任何 scheduler 锁之前保存并关闭 `SIE/IE`，idle 以
  IRQ-off 运行；任务恢复后才恢复它自己的切出快照。
- panic handler 已在任何 console/锁诊断和 STOP 之前关闭本地中断。
  同时收紧 LA64 `trap_return()`：`kernel_cpu_local/PRMD` 修改与 trace
  值快照都在 `task.inner` 锁内完成，不再使用脱锁的 `'static mut` 引用。
- focused test 在窗口内新建 helper 任务并 yield：helper 首次切入观测
  idle 为 IRQ-off，原 runner 恢复后观测 IRQ-on，再完成真实 AP→BSP
  IPI reply。窗口外还验证入口状态恢复并消费 deferred timer。

### SMP-P2-B13：AP STOP/ack 与统一停机协议

**范围与设计：**

- 本包把 STOP 做成真正的生产停机协议，而不是只在测试中修改 online mask：
  CPU0 发布终态请求，AP 必须在独立 idle stack 上关闭 interrupt source，
  再确认自己不会继续访问共享状态。
- STOP reason 仍通过可合并 mailbox 传递，请求完成则由独立的
  `stopped` 原子 ack 表达。`online` 保留启动历史，重复调用通过排除已
  stopped AP 幂等完成，不引入 CPU hotplug 的离线/重上线语义。
- 独立只读设计与补丁审查重点检查了 trap-frame 生命周期、ack 发布点、
  本地 interrupt source 关闭顺序和 `KREPEAT` 终态语义；未发现 P0/P1 问题。

**双架构实现与并发语义：**

- hard IPI handler 只以 Release 发布 `stop_requested`；AP 回到 idle stack
  后以 Acquire 消费，先执行 `prepare_secondary_cpu_stop()`，再以 Release
  发布 `stopped=true`，随后进入不可返回的架构 idle loop。
- RV64 同时清除全局 SIE 与本地 `sie`；LA64 清除 CRMD.IE、ECFG，并在 QEMU
  上向 IOCSR `CORE_EN`（`0x1004`）写零。QEMU 9.2.1 官方源码确认该寄存器
  是直接赋值语义，因此写零会关闭运行期 IPI line。
- CPU0 快照 online 且尚未 stopped 的 AP，发送 STOP 后在一秒期限内以
  Acquire 等待全部 ack；doorbell 局部失败不会回滚已经发布的 mailbox，
  最终是否成功由 stopped ack 决定。
- `hal::shutdown()` 统一在正常 CPU0 关机前 best-effort 停止 AP；online
  尚未建立的极早期 panic 与 AP fatal path 直接进入机器级关机兜底。
- ktest runner 增加 terminal test：普通测试按 repeat 完成后，STOP 只在
  整个计划末尾执行一次。测试还会重复调用生产 STOP，验证幂等快路径。

**Docker RED/GREEN 验证：**

  汇编器拒绝 `iocsrwr.w zero, ...`。根因是 inline asm 中 LoongArch 零
  寄存器必须写作 `$zero`，修正后重新冻结源码；
- 最终验证时 tracked source diff SHA-256：
  `5b6fa8b38d3f082c11f7adda9125c4a76d133055492c48feb015524710dda9c6`；
- 最终 RV64 normal kernel build：退出 0，124.312 秒；
- 最终 LA64 normal kernel build：退出 0，128.363 秒；
- 初轮 RV64 `CORE_NUM=4 KTEST=smp KREPEAT=2`：`online_mask=0xf`，
  15/15 PASS，STOP 为第 15 项，QEMU 正常退出；
- 最终 LA64 同配置：`online_mask=0xf`，15/15 PASS，131.017 秒；

**阶段结论：**

### SMP-P2-B12：AP→BSP IPI 请求/回复与无丢失 idle 等待

**范围与设计：**

- B09/B10 只证明 CPU0 能向 AP 单播和广播；CPU0 尚未打开本地 IPI line，
  AP 也没有安全的回复发送位置，因此不能据此外推双向通信。
- 本包只闭合真实 AP→BSP 往返及 idle check→wait 不变量，不引入 STOP、
  RESCHEDULE、runqueue、TLB shootdown 或普通长 syscall 中断窗口。
- reason mailbox 仍是可合并 bitset。测试在观察到每轮独立 ack 后才复用
  请求/回复 bit，事件次数由 ack sequence 表达，而不是错误地依赖 bit 累计。

**双架构实现与并发语义：**

- RV64 CPU0 在 machine init 中打开 SSIE；LA64 QEMU CPU0 配置运行期 IPI
  vector 并在 ECFG 中打开 IPI line。LA64 的调用受 QEMU cfg 约束，
  2K1000LA 继续保持单核路径。
- 两架构用户态和内核态 trap 共用同一个 IPI fast path：先清硬件 level
  source，再以 Acquire 消费 per-CPU mailbox。handler 只更新原子状态，
  不分配、不打印、不获取普通锁，也不从中断中发送新的 doorbell。
- AP 收到 request 后以 Release 发布 `round_trip_reply_pending`，返回
  独立 idle stack 后再调用普通 `send_ipi()` 回复 CPU0；发送错误只进入
  per-CPU 原子诊断计数。CPU0 handler 以 Release 增加 reply ack，等待方
  用 Acquire 观察。
- AP idle loop 改为一次性架构 wait：保存并关闭全局中断，重查 deferred
  work，无工作时执行一次 `wfi`/`idle 0`，随后恢复原状态。等待期间本地
  IPI line 仍 enabled，重查后的 doorbell 会保持 pending 并唤醒 CPU，
  从而闭合 lost-wakeup 窗口。
- focused test 由 CPU0 内核任务打开受控中断窗口，让每个 AP 顺序完成
  64 轮请求/回复；测试结束前消费可能到达的 deferred timer，避免把测试
  窗口的 timer 状态泄漏给后续用例。

**Docker 验证：**

  124.445 秒；
- LA64 根 Make facade `CORE_NUM=4` normal kernel build：退出 0，
  130.783 秒；

  128.256 秒；

**阶段结论：**

- `SMP-P2-B12=pass`，CPU0 已可在受控窗口接收真实 AP doorbell，AP 的

### 修复 /dev/shm sticky bit 与 os_test.conf mask

**涉及文件：**
- `user/src/syscall.rs` — 新增 `SYSCALL_FCHMODAT` 常量（53）和 `sys_fchmodat` 系统调用封装
- `user/src/usr_call.rs` — 新增 `chmod()` 便利封装，调用 `sys_fchmodat(AT_FDCWD, path, mode)`
- `user/src/bin/init/mounts.rs` — PID1 挂载 `/dev/shm` tmpfs 后调用 `chmod("/dev/shm", 0o1777)` 设置 sticky bit；导入 `chmod` 到作用域
- `os_test.conf` — 从测试期间的 `mask=0x010` 恢复为 `mask=0xFFF`

- `chmod("/dev/shm", 0o1777)` 在 devtmpfs 挂载和 tmpfs 覆盖后执行，tmpfs root inode 将获得 01777 权限
