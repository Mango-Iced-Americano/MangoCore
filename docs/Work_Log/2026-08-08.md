### 诊断 A/B 实验：buildstorm cargo-build 挂起根因假设验证 — prewarm PageCache 无效，无 readahead 假设被否定

### 根因定位：exec 大动态 ELF（bash 1.1MB）静默 exit 127 — PageCache 批量读超过 256 页上限 → EFBIG → EIO

**根因：** buildstorm 组 exec `/bin/bash` 时，内核零拷贝 ELF loader 的 `prefetch_load_pages` 把首个 PT_LOAD（filesz=1091440B=267 页）一次性交给 `PageCache::sync_batch_read_pages`。该函数把全部 267 个连续缺页收集成**单个 run**，未按 `fill_miss_runs`（page_cache.rs:1222）的 `MAX_BATCH_PAGES=256` 契约分片；ext4 后端 `ext4_another/page_cache.rs::read_pages` 对 `pages.len()>256` 返回 `EFBIG(27)`。`prefetch_load_pages` 把任意错误映射为 `EIO(-5)` → `load_elf_direct` 失败 → `exec_opened_file` 调 `exit_current_and_run_next(127)` —— **内核在用户态任何代码运行前直接以 127 杀进程**，无返回、无 stderr，故串口看不到任何 bash 输出。

**排查过程：**
1. `exec.rs` load_elf 失败处加 `[DBG] exec load_elf failed errno={}` → 打印 `errno=-5`（EIO），且无 `open_interp_file` 失败输出 ⇒ 排除 PT_INTERP/chroot 根解析假设（`current_root_inode()` 走 per-process chroot root，正确）。
2. `prefetch_load_pages`/`copy_from_page_cache` 失败处插桩 → `[DBG] prefetch_load_pages fail off=0 filesz=1091440 start_page=0 end_page=267 err=EFBIG backend_npages=280`。
3. 确认 ext4 后端 read_pages 硬性上限 256（`MAX_BATCH_PAGES`），`fill_miss_runs` 分片但 `sync_batch_read_pages` 不分片。
4. 验证性临时改动：`sync_batch_read_pages` run 收集条件加 `run_bufs.len()<256` 分片 → 重建后 QEMU：脚本 echo 二次出现、`BUILDSTORM_TOOLCHAIN ok`、`exit_code=0`。根因确认后**已全部回退**（源码无残留 DBG）。

### 修复：FAT32 后端扇区/块设备尺寸不匹配（512B sector vs 4096B BlockDevice）

**根因：** `EasyFileSystem::open` 直接保存原始 BLOCK_SZ(4096) 块设备（挂载路径不再套 `BlockSizeAdapter`），而 FAT32 内部以 BPB_BytsPerSec(512) 扇区为单位编址。`bitmap.rs` 的 `read_fat_entry`/`write_fat_entry` 把 512B 扇区号 + 512B buffer 直接传给 4096B 块设备 API → `validate_block_buffer_length` 失败 → Result 被 `;` 静默丢弃 → FAT 表读到全零 → 分配器误以为 cluster 2（根目录簇）空闲 → 新文件分到 cluster 2 → `FAT inode identity collision for Cluster(2)` panic（ktest 41）。数据路径 `FatPageCacheBackend` 原本就做了扇区→块换算，唯独 FAT 表路径漏了。

**修改：**
- `os/src/fs/fat32/bitmap.rs` — 新增 `sector_to_parent`/`read_fat_sector`/`write_fat_sector`：扇区号换算为父块号 + 块内偏移，整块(4096)读写 + 切片/read-modify-write；`read_fat_entry`/`write_fat_entry` 全部改走新 helper；删除“mount path 已适配”的过期注释。
- `os/src/fs/fat32/efs.rs` — 修正 BPB 读取处的误导性注释（BPB 读 block 0 本身正确，未改逻辑）。

**验证：**
- `make kernel ARCH=rv64 PROFILE=normal` ✅ exit 0
- `make ktest-run ARCH=rv64 PROFILE=normal` ✅ 98 passed, 0 failed；`ok 41 ext4::fat32_create_write_read_remove`；`[KTEST RESULT: PASS]`；无 `HEAP ALLOCATION FAILED`
- `make kernel ARCH=la64 PROFILE=normal`（串行）✅ exit 0
- 变更文件零 warning

**备注：**
- 关机阶段 `# ktest: page-cache writeback failed: EINVAL` 为存量现象：FatPageCacheBackend 写回路径只返回 Ok/EIO/EAGAIN，唯一 EINVAL 源 `BlockPageCacheBackend` 是死代码（从未实例化），与本次 FAT 修复无关；仅因修复后 ktest 能跑完到关机路径才可见，不影响 PASS 判定。
- 选用了 bitmap.rs 内联换算（方案 b）而非在 `EasyFileSystem::open` 套 `BlockSizeAdapter`（方案 a）：数据路径 `FatPageCacheBackend` 已自带换算，套适配器会导致双换算并破坏其 `buf.len() == child_size` 契约（`BlockSizeAdapter` 还被 ext4 byte_bridge 测试使用）。
