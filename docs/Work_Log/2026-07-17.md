### lwext4 inode 复用不再继承旧 PageCache 页面

**根因：** `Ext4FileSystem::page_caches` 仅以 inode number 为 key，unlink 后旧 `Arc<PageCache>` 仍被强引用 registry 保留。lwext4 复用该 inode number 创建新的 sparse file 时，新 inode 命中旧的 fully-valid 页面，绕过后端 hole zero-fill，导致顺序 LTP 中读取到旧数据 `0x0167`。

**修复：** 新建 regular file 成功并取得真实 inode number 后，先从 `page_caches` registry 移除同 key 的旧映射，再构造新的 inode。旧 inode 仍持有其 `Arc<PageCache>`，不强制清空或失效；新 inode 则必然创建独立 cache。创建路径不再 fallback 到 path hash，避免未知真实 inode 再次碰撞 registry。

**涉及文件：**
- `os/src/fs/ext4_lwext4/layout.rs` — `Ext4OSInode::create()` 取得真实 inode 后移除旧 registry entry。
- `user/src/bin/ltprunner/` — opt-in `ltp_lwext4_perf_log=1` 在现有 QEMU log 输出每个 case 的 24 项累计 counter delta；未配置时不读取 sysfs、无新增输出。
- `os_test.lwext4_perf.focus.conf` — suite focused 到 `gf14,gf18,gf27,gf28`，启用直接日志诊断；未修改 `os_test.conf`。
- `.agents/skills/mango-workflow/references/harness-patterns.md` — 明确一次性根因定位优先走有界直接日志，持久化证据仅用于跨运行分析或审计。

**验证：**

### bounded lwext4 inode-allocation diagnostic: block-group counter/bitmap mismatch tracing

**涉及文件：**
- `dependency/lwext4_rust/c/lwext4/src/ext4_ialloc.c` — `ext4_ialloc_alloc_inode()` ENOSPC 分支新增有界诊断日志

**诊断内容：**
在 `ext4_ialloc_alloc_inode()` 的 ENOSPC 分支（L293-306）中，当 `rc == ENOSPC` 时，由调用级计数器 `enospc_diag_count` 限流（单次调用最多 2 条），通过 `ext4_dbg(DEBUG_IALLOC, DBG_WARN ...)` 记录以下字段：

- `bgid` — 当前已检查完的 block group ID
- `orig_bg_count` — 进入循环前捕获的原始 block group 总数（在 `bg_count` 被 rewind 路径改写前保存）
- `desc_free` — 描述符中该 bg 的 `free_inodes_count`
- `sb_free` — 超级块中记录的全局 `free_inodes_count`
- `inodes_in_bg` — 该 bg 的 inode 总数
- `csum_ok` — `ext4_ialloc_verify_bitmap_csum()` 的校验结果（true/false）

**目的：** 区分 block group 内 free_inodes>0 但 bitmap 已全满（计数器/位图不一致）与真正的全局 inode 耗尽 — 这两种情况都会进入 ENOSPC 分支但根因不同。前者暗示元数据损坏或并发竞争，后者为预期耗尽。

**设计要点：**
- **零控制流变更**：所有 `return rc`、`continue`、`++bgid` 均未修改；diagnostic 出现在 `continue` 之前，不改变兜底/回退行为
- **限流**：`enospc_diag_count` 为局部变量，每次调用重置为 0，最多输出 2 条消息，防止已知的 bgid 停滞问题导致日志泛滥
- **`bitmap_csum_ok` 跨配置兼容**：`CONFIG_META_CSUM_ENABLE` 开启时取 `ext4_ialloc_verify_bitmap_csum()` 真实结果，关闭时宏展开为 `true`

**验证：**
- 尚未编译或运行 QEMU（按任务要求仅诊断代码就绪）

**备注：**
- 计划后续步骤：串行 Docker rv64 构建 → Docker la64 构建 → 注入 focus conf 的 `os_test.focus.conf` → QEMU 运行 `mknod01` 单用例 → 检查诊断日志输出确认 bitmap/counter 状态

### sys_splice pipe→pipe: 修正返回值优先级与等待逻辑（EAGAIN/EOF/EPIPE/ERESTART）

**涉及文件：**
- `os/src/syscall/fs/sys_splice.rs` — 重排 `splice_atomic_single()` 判定顺序：EOF（源端空+写端全关闭）→ `Ok(0)` → EPIPE（目标端无读者）→ `Err(EPIPE)` → 数据转移 → `Ok(n)` → 非终态 `Err(EAGAIN)`。非阻塞路径 `Ok(0)` 直接返回 0（不再误当 EAGAIN）；阻塞路径移除转移前的信号预检，`Err(EAGAIN)` 分支才检查信号（`ERESTART`）；等待闭包内 `Err(EAGAIN)` 返回 `None`（继续等待）、`Ok(0)` 返回 `Some(0)`（EOF 穿透等待）。

**EAGAIN / EOF / EPIPE / ERESTART 判定顺序：**

| 优先级 | 条件 | 返回值 | 说明 |
|--------|------|--------|------|
| 1 | 源端有数据 + 转移成功 | `Ok(n>0)` | 信号不抢占；通知源端可写+目标端可读 |
| 2 | 源端空 + 写端全关闭 | `Ok(0)` = EOF | EOF 优先于 EPIPE（无数据可转移） |
| 3 | 源端有数据/写端仍开 + 目标端无读者 | `Err(EPIPE)` | 仅在非 EOF 时检查；源端数据不被消耗（检查在 splice_move 之前） |
| 4 | 源端空（写端开）或目标端满（有读者） | `Err(EAGAIN)` | 非终态；阻塞路径在此分支检查信号后才等待 |

**关键语义修正：**
1. **非阻塞路径 EOF → 0**：原代码 `Ok(0)` 统一返回 `EAGAIN`，源端 EOF 被错误转换为 `EAGAIN`。现在 `splice_atomic_single` 在锁内区分 EOF 和 EAGAIN。
2. **EOF 优先于 EPIPE**：原代码先检查 EPIPE 再转移，源端 EOF+目标 EPIPE 时返回 EPIPE 而非 EOF。现 EOF 检查最先，避免误报。
3. **信号不抢占立即结果**：原阻塞路径在转移前预检信号（`has_actionable_signal`），即便数据立即可转移也会被 `ERESTART` 打断。现仅 `Err(EAGAIN)`（无进展）时才检查信号。
4. **EPIPE 数据保全**：EPIPE 检查在 `splice_move` 之前，确保源端数据不被消耗到无读者的目标管道。
5. **双 WaitQueue 闭包语义对齐**：dst_wq/src_wq 等待闭包内 `Err(EAGAIN)` 返回 `None`（继续等待），`Ok(0)`=EOF 返回 `Some(0)` 拦截等待并立即传播 EOF。

**验证：**
- 未编译（按任务约束）

**备注：**
- 未修改 `PipeRingBuffer::splice_move`、`common.rs`、确定性地止锁序（Arc 指针地址比较）、闭包外通知

### sys_splice pipe→pipe atomic transfer: 消除数据丢失（P0）

将管道对管道的 splice 数据保全从"有界丢失 4KB"升级为"零丢失"。

**涉及文件：**
- `os/src/fs/dev/pipe.rs` — 新增 `PipeRingBuffer::splice_move(src, dst, max_bytes)`：在双锁保护下原子地将字节从一个环形缓冲区转移到另一个；可见性提升：`send_sigpipe_to_current` → `pub(crate)`、`get_used_size`/`all_read_ends_closed`/`all_write_ends_closed`/`peer_read_end`/`peer_write_end` → `pub(crate)`、`read_wait`/`write_wait` 字段 → `pub(crate)`

- 移除接受/界定数据丢失的注释（原第 91-98 行："nonblocking mode a target-write failure can orphan up to 4 KB...inherent limitation"）

**设计要点：**
- **锁顺序**：`Arc::as_ptr`（稳定的堆分配地址）建立全局确定性顺序；同一管道被 `is_same_pipe` 拒绝，因此地址不可能相等

### sys_splice 验证顺序与数据保全修复（Oracle 终稿，Linux 6.6 对齐）

**涉及文件：**
- `os/src/syscall/fs/sys_splice.rs` — 完整重写传输循环和验证流程：
  ① **len==0 提前返回**：从 flags/fd 检查之后移至函数入口第一行（Linux 6.6 `do_splice` 在 `fdget()` 之前检查 `len==0`）
  ② **ESPIPE 优先于 same-pipe EINVAL**：将管道非 NULL offset 检查（ESPIPE）从 same-pipe 检查之后移至之前（Linux 6.6 `do_splice` 中 `ipipe && off_in` → `-ESPIPE` 优先于 `ipipe->pipe == opipe->pipe` → `-EINVAL`）
  ③ **文件源 offset 延迟推进**（P0 数据保全）：`off_in_val` 不再在读取路径中推进（原 `*off_val += n`），而是在目标写入成功后由写入阶段推进。防止目标写入失败导致文件偏移已越过未传输数据
  ④ **写入优先循环设计**：将循环从"先读后写"改为"先清空待发送缓冲再读"，避免已从源端消耗但无法写入目标的数据在循环中堆积

- 偏移推进现已原子化绑定到成功的写入操作；`off_in_val` 每次推进 `wrote` 字节（即实际传输量）而非 `read` 字节

### splice/tee 同一管道检测修复与 tee 语义对齐 (Linux 6.6)

**涉及文件：**
- `os/src/syscall/fs/common.rs` — `is_same_pipe()`: 从比较 `Arc::ptr_eq(&f1.inode, &f2.inode)`（端点 inode）改为比较 `Arc::ptr_eq(p1.buffer_arc(), p2.buffer_arc())`（共享 `PipeRingBuffer`），因为 pipefd[0] 读端和 pipefd[1] 写端是不同的 inode `Arc`，但共享同一 `PipeRingBuffer`。旧实现无法检测 pipefd[0]→pipefd[1] 同一管道自 splice，导致本应被 EINVAL 拒绝的操作穿通。
- `os/src/syscall/fs/sys_tee.rs` — ① `len==0` 返回 0 移到 fd-table 访问之前（对齐 Linux 6.6 顺序，`do_tee` 在 `fdget()` 前检查 `len==0`）；② 标志位掩码从 `SPLICE_F_NONBLOCK | SPLICE_F_MORE` 改为 `SPLICE_VALID_FLAGS`（接受所有 `SPLICE_F_MOVE | SPLICE_F_NONBLOCK | SPLICE_F_MORE | SPLICE_F_GIFT`）；③ 非阻塞路径：`peek_at` 返回 0 后检查 `all_write_ends_closed()`，已关闭时返回 0（EOF）而非 EAGAIN；④ 阻塞等待路径：`WaitQueue` 闭包内检查 `all_write_ends_closed()`，避免写端全部关闭后无限等待。

**锁纪律：** `is_same_pipe` 不持锁（`buffer_arc()` 返回引用，`Arc::ptr_eq` 无锁）；EOF 检查 `buffer_arc().lock().all_write_ends_closed()` 在 fd-table 锁释放后、peek 后执行，锁持有极短；阻塞等待闭包内锁仅在轮询时短暂持有，等待时不持锁。

**设计参考：** Linux 6.6 `splice_pipe_to_pipe` 中 `ipipe->pipe == opipe->pipe` 比较 `struct pipe_inode_info *`（共享缓冲区对象）；`do_tee` 中 `flags & ~SPLICE_F_ALL` 和 `len == 0` 顺序。

**备注：**
- `sys_splice.rs` 无需修改 — 已有的 `is_same_pipe` 调用自动受 common.rs 修复影响；splice 的 `len==0` 已有正确位置（在 fd validation 后，对齐 Linux）

### ext4/lwext4 特殊 inode 创建 EINVAL 级联修复（mkfifo/mknod）

**根因：** `apply_current_umask()` 在 `os/src/syscall/fs/common.rs` 中通过 `mode & S_IALLUGO` 过滤时，将 S_IFMT 类型位（S_IFIFO=0o010000 等）一并丢弃。`mkfifo`/`mknod` 在 syscall 入口传入 `S_IFIFO | 0777`，经 `apply_current_umask` 后只剩 `0777`，再传入 lwext4 `mknod()` 时无法匹配 S_IFIFO 分支，落入 `else { return EINVAL }`。次要原因：lwext4 `create_with_data()` 未将 `FileType::Pipe/CharDevice/BlockDevice/Socket` 路由到已实现的 `mknod()` 方法，而是回退到 `create()` 返回 EINVAL。

- `os/src/fs/ext4_lwext4/layout.rs` — `create_with_data()`：新增 Pipe/CharDevice/BlockDevice/Socket → `mknod()` 路由，保留 `rdev` 语义

### lwext4 ext4_fread 批量循环内部空洞丢失修复 (LA64 gf14/gf18/gf27/gf28)

**涉及文件：**
- `dependency/lwext4_rust/c/lwext4/src/ext4.c` — `ext4_fread()` 批量对齐读取循环：新增 pending-hole 检查，在 `while(size >= block_size)` 循环顶部处理上一批次断点遗留下的空洞块（fblock==0 但 fblock_count>0），避免 iblock_idx 在 break 后已越过空洞导致零填充丢失
- `dependency/lwext4_rust/c/lwext4/liblwext4-riscv64.a` — 重新编译
- `dependency/lwext4_rust/c/lwext4/liblwext4-loongarch64.a` — 重新编译

**根因分析：**
July 16 的 fix 10b (commit 14464d77) 修复了 `ext4_fread` 中对齐整块空洞和末尾非完整块空洞的零填充，但遗漏了第三种场景：**内部空洞位于两个已分配块序列之间**。

批量循环的结构为：内层循环收集连续物理块（通过 `(fblock_start + fblock_count) != fblock` 判断连续性），遇不连续时 break；外层处理批次后通过 `fblock_start = fblock; fblock_count = 1` 将断点块带到下一轮。但当断点块是空洞（fblock==0）时：
1. 内层 `iblock_idx++` 已越过该空洞
2. 下一轮外层 `!fblock_start`（`!0 == true`）被内层循环首块的非零 fblock 覆盖
3. 空洞块从未进入 `if (fblock_start == 0) { memset(...); }` 分支 → 静默丢失

症状：growfiles 在偏移 4096/4636/32768/65536 等处期望零填充，但实际读到 0x0101/0x0163/0x0167 等 ext4 元数据残留值（来自物理块 0 的误读或未初始化的缓冲区）。

**修复：**
在 `while (size >= block_size)` 顶部添加 12 行 pending-hole 检测：若 `fblock_start == 0 && fblock_count > 0`，立即 memset 零填充一个 block_size，更新所有指针和计数器，然后 `continue` 进入下一轮。

**验证：**
- `make rv64-kernel-build-only` ✅ (含 lwext4 rv64 `.a` 重新编译)
- `make la64-kernel-build-only` ✅ (含 lwext4 la64 `.a` 重新编译)

**备注：**
- July 16 修复（14464d77）的方向正确但覆盖不完整 — 本修复不是推翻而是补充
- 若 QEMU 运行时使用的内核/镜像未更新（含旧 `.a`），则即使源码已修复也会表现 RED
- 同样结构的批量循环在 `ext4_fwrite` 中也存在，但写路径通过 `ext4_fs_append_inode_dblk` 分配新块，断点空洞语义不同，暂未受影响
- Linux 6.6 通过 ext4 extent tree + `ext4_map_blocks` 统一处理空洞，不依赖批次连续假设，无此类 bug

### sys_fadvise64 管道/FIFO 错误码修正（EINVAL → ESPIPE）

**涉及文件：**
- `os/src/syscall/fs/sys_fadvise64.rs` — `sys_fadvise64()`: 将原来的 blanket `FileType::File` 检查（所有非普通文件 → EINVAL）拆分为：先 `FileType::Pipe` → `ESPIPE`，再其他非普通文件 → `EINVAL`

**根因分析：**
July 17 的上一条修改（`sys_fadvise64` 从 `is_stream_file` 改为 `file_type != File`）使用了 blanket EINVAL 策略，但 Linux 6.6 `generic_fadvise()` 对管道/FIFO 返回的是 `ESPIPE`（Illegal seek），不是 `EINVAL`。`ESPIPE` 是 `S_ISFIFO` 的语义正确响应——管道不支持定位操作，而 fadvise 语义上依赖于定位偏移。其他非普通文件类型（目录、socket、字符/块设备）没有 page cache 映射，返回 `EINVAL` 是正确的。

**验证：**
- 尚未编译/测试（按任务约束只读修改）

**备注：**
- 验证顺序保持不变：无效 fd → O_PATH → 负偏移/长度 → bad advice → Pipe(ESPIPE) → 非普通文件(EINVAL) → SUCCESS
- 与 Linux 6.6 `mm/fadvise.c:generic_fadvise()` 行为对齐：`S_ISFIFO` → `-ESPIPE` 优先于 `!mapping` → `-EINVAL`
