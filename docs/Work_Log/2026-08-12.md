## 修复 GitHub Actions CI 工具链下载超时，5a/5b 测试配置改为读取仓库 os_test_ci.conf

**涉及文件：**
- `.github/workflows/ci.yml` — 修复 CI 全部改动
- `os_test.conf` / `os_test_ci.conf` — 统一更新为评测配置（mask=0x6FDF、ltp_suites=syscalls,fs_bind、排除列表新增 fallocate05），随 CI 修改同批提交

**背景与根因：**
`scripts/rustup-setup.sh` 用 `: "${RUSTUP_DIST_SERVER:=https://rsproxy.cn}"` 做默认镜像兜底，
设计上允许 env 覆盖（评测机保留 rsproxy）。但 `docker compose exec` 只透传显式 `-e` 声明的
变量，CI 里所有 Provision toolchain 步骤只传了 `RUSTUP_HOME`/`CARGO_HOME`，导致 GitHub 美国
runner 上容器内镜像变量为空 → 兜底到 rsproxy.cn → 直连超时（error 110）。

**改动内容：**
1. ci.yml 顶层 `env:` 增加 `RUSTUP_DIST_SERVER=https://static.rust-lang.org` 与
   `RUSTUP_UPDATE_ROOT=https://static.rust-lang.org/rustup`（官方 CDN，GitHub 可达）。
2. 全部 22 处 `docker compose exec`（clippy/cargo-test/ktest/regression/comp-rv/comp-la）
   补充 `-e RUSTUP_DIST_SERVER -e RUSTUP_UPDATE_ROOT` 透传（不带值的 `-e` 转发宿主机同名变量）。
3. 删除 5a/5b 的 "Write test config" heredoc 步骤：`os_test_ci.conf` 为 git tracked 文件，
   compose 挂载 `.:/app` 后 `CONF_FILE=../os_test_ci.conf` 即解析到仓库文件，改配置只需改仓库文件。

**验证：**
- YAML 语法 `yaml.safe_load` 通过，7 个 job 结构完整 ✅
- `os_test_ci.conf` 确认 tracked；heredoc/`<<'EOF'` 已在 ci.yml 清零 ✅
- 4 个契约测试：`test-rustup-setup.sh`/`test-rustup-preflight.sh` PASS；
  `test-toolchain-make-contract.sh`/`test-source-purity-make-contract.sh` 本地 FAIL，但经
  `git stash` 基线对照确认是改动前即存在的本地环境问题（读取 Makefile/scripts，与 ci.yml 无关）✅

**备注：**
- 评测机（rsproxy 可达）行为完全不受影响：`rustup-setup.sh` 未改，默认兜底仍是 rsproxy.cn，
  评测环境不注入这两个变量时走原路径。

## 修复 CI 容器内 git dubious ownership 导致的 prepare-cargo-config 失败

**涉及文件：**
- `.github/workflows/ci.yml` — 6 处 Provision toolchain 步骤前置 `git config --global --add safe.directory "*"`

**背景与根因：**
镜像修复后 CI 首次走到 `make all` → `prepare-cargo-config` 的 `git submodule update --init --recursive`，
报 `fatal: detected dubious ownership in repository at '/app'`。原因：GitHub runner 以 runner 用户
checkout 文件，容器内以 root 执行 git，owner 不一致被 git 安全机制拒绝。本地不出现是因为文件 owner 一致。

**改动内容：**
6 处 Provision toolchain 步骤（clippy/cargo-test/ktest/regression/comp-rv/comp-la）在
`make toolchain-setup` 前先执行 `git config --global --add safe.directory "*"`：`*` 一次覆盖
/app 及其全部 submodule 目录；容器为一次性 CI 环境，通配符信任无风险。配置写入容器 root 的
~/.gitconfig，同容器内后续步骤（build/inject/run）全部生效。

**验证：**
- YAML 语法 `yaml.safe_load` 通过，6/6 处生效 ✅
- 隔离 HOME 实测 `git config --global --add safe.directory "*"` 生成合法 `[safe] directory = *` ✅

**备注：**
- 未改 Makefile：`prepare-cargo-config` 在评测机（owner 一致）上不需要 safe.directory，保持评测路径不动。

## 恢复 make all 默认制作 tools 盘（BUILD_TOOLS_DISK 默认 1）

- `os/Makefile` — `BUILD_TOOLS_DISK ?= 1`（原为 0），注释同步更新

**背景与根因：**

`Could not open '/app/build/rv64/release/normal/tools/disk.img'`：提交 `ba0919ca`
（"skip tools disk by default"，2026-08-10）为消除 Alpine 下载等网络依赖把
`BUILD_TOOLS_DISK ?= 0` 设为默认，`make all` 不再制作 tools 盘；但 `derived-comp`
的 x1 驱动仍引用 `IMAGE_ROLE_RV64_X1 = <product>/tools/disk.img`（image-roles.mk:52），
盘不存在导致 QEMU 启动失败。

**改动内容：**
`BUILD_TOOLS_DISK` 默认值改回 1：`make all`（本地/评测机/CI comp-rv/comp-la）恢复制作
disk.img/disk-la.img（含 tools-user + Alpine 工具包 + apk/cpython）；网络受限环境仍可显式
`make BUILD_TOOLS_DISK=0` 跳过。`publish-compatibility` 对缺失 tools 产物的容错保留不变。

**验证：**
