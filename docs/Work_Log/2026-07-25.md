### SMP-P1-B08：AP 切换独立 idle stack 后再发布 online

**范围与撤销：**

- 先完整撤销未提交的 B07 validation-only patch。该 patch 只增加全局初始化
  计数和栈地址 probe，没有建立新的运行期能力，还会让启动主链被验证代码
  打断，因此不保留。
- B08 改为闭合一个真实启动不变量：AP 完成本地 bootstrap 后必须离开
  firmware boot stack，在 logical CPU 独占的 idle stack 上发布
  `idle=true`，随后才允许发布 `online=true`。

**实现与理由：**

- 双架构 HAL 按构建期 `configured_cpu_count()` 分配页对齐的静态 idle
  stack；RV64 每槽 64 KiB，LA64 每槽 128 KiB。只分配 configured 数量，
  避免单核实板承担 8 核静态内存成本。
- idle 区使用 `.bss.idle_stack`，由链接脚本既有 `.bss.*` 通配符放在
  `sbss..ebss`。它与正在参与 BSS 清零的 boot stack 生命周期不同：AP
  观察 `BOOT_PHASE` Acquire 前不会使用 idle 区，因此应由 CPU0 正常清零；
  同时该区仍在 `skernel..ekernel` 内，不会被 frame allocator 回收。
- 双架构新增发散的 naked trampoline。标准 C ABI 把 logical ID、栈顶和
  Rust 入口分别放入 `a0/a1/a2`；汇编只更新 `sp`、断开旧 frame/return
  链并间接跳转，刻意保留 RV64 `tp` / LA64 `$r21` 的 PerCpu 指针。
- `PerCpu` 新增 `idle: AtomicBool`。AP 在新栈上的第一个 Rust 入口先校验
  `cpu_id()`，以 Release 发布 idle，再通过既有 Release CAS 发布 online；
  BSP Acquire 观察 online 后即可依赖 AP 已完成切栈。CPU0 保持
  `idle=false` 并继续独占旧调度器。
- `KTEST=smp` 新增 AP idle context 断言。该状态不是一次性测试 probe，
  Phase 2 会继续把它用于 idle/远程唤醒协议。

**官方规范与独立审查：**

- RISC-V psABI 与 LoongArch ELF ABI 均要求标准过程入口的 `sp` 维持 128-bit
  对齐；两架构页对齐基址和页倍数槽宽满足该约束。Rust Reference 要求
  naked body 完整承担 ABI 并明确返回或发散，本实现签名为 `-> !` 且不
  fall through。
- DeepSeek 以只读方式自主审查当前 diff 和双架构日志，结论为没有必须修的
  缺陷、现有 focused 证据已经足够，应停止追加测试并转入 IPI/可唤醒 idle
  功能。其建议把 timer、runqueue、页表一起纳入下一包会扩大并发范围，未
  直接采纳；下一包应先闭合最小 IPI mailbox/ack 协议。

**Docker 验证：**

- RV64 `CORE_NUM=8 KTEST=smp`：`boot_hw_id=6`、
  `online_mask=0xff`，3/3 PASS；真实覆盖非 hart0 冷启动映射和 7 个 AP
  idle stack 切换。
- LA64 `CORE_NUM=8 KTEST=smp`：`boot_hw_id=0`、
  `online_mask=0xff`，3/3 PASS。
- 最终 ELF 反汇编确认 RV64 为
  `mv sp,a1; li s0,0; li ra,0; jr a2`，LA64 为
  `addi.d sp,a1,0; addi.d fp,zero,0; addi.d ra,zero,0; jr a2`。
  `IDLE_STACKS` 均为页对齐 BSS 符号并位于 `sbss..ebss`。
- 未重复执行独立 build、单核或用户态全量回归：双架构 8 核 focused ktest
  已包含实际编译、链接和本工作包唯一改变的 AP 路径；CPU0 调度不变量也在
  同一次运行中覆盖。

**阶段结论：**

- `SMP-P1-B08=pass`；AP 的 online 现在承诺“已在独立 idle stack 上”，
  而不再只是“bootstrap 已返回”。
- 整体 Phase 1 仍为 `partial`：可唤醒 idle loop、内核 trap/IPI、
  console 多核串行化和其余 PerCpu 字段尚未完成。
- 本批没有新增独立 debugging/performance reference；启动栈生命周期和
  online 发布顺序已同步到启动架构文档与 SMP 实施方案。

### SMP-P1-B05：让双架构用户 trap 恢复运行期 CPU-local 指针

**涉及文件：**

- `os/src/smp.rs` — 将启动期锚点升级为运行期接口，新增先验证静态
  `PER_CPUS` 范围和表项对齐、再安全索引的 `cpu_id()`。
- `os/src/hal/{mod.rs,arch/mod.rs}`、双架构 `arch/*/mod.rs` — 统一导出
  `install_cpu_local()` 和 `cpu_local_ptr()`。
- 双架构 `trap/{context.rs,trap.S,mod.rs}` — 增加内核私有
  `kernel_cpu_local`，用户返回前刷新；入口先保存用户 `tp/$r21`，再装入
  当前 CPU 的内核指针并切换内核栈。
- `docs/01_architecture/boot-and-trap.md`、
  `docs/10_plan/smp-8core-implementation.md` — 同步寄存器所有权、trap
  顺序、LA64 LSX 对齐和 Phase 1 `partial` 边界。
- `docs/Work_Log/evidence/2026-07-25/smp-phase-1/` — 保存完整双架构
  build、两核用户 regression、反汇编和 manifest。

**设计与安全边界：**

- TrapContext 页只有内核 `R|W`、没有用户 `U` 权限，用户不能伪造下一次
  trap 装入的 PerCpu 指针。
- `trap_return()` 在 `do_signal()` 之后按当前 CPU 刷新字段，覆盖初始
  context、exec 新建、fork/clone 复制和未来迁移留下的旧值。
- RV64 入口先保存用户 TLS `tp`，LA64 入口先保存用户 `$r21`，随后才覆盖
  为内核指针；原有 restore 路径仍恢复完整用户寄存器。
- `kernel_cpu_local` 位于两架构 slot 70。LA64 `LsxRegs` 需要 16 字节
  对齐，因此 LSX 区域移到 slot 72；Rust 编译期偏移断言和最终 ELF
  反汇编共同证明布局。
- 内核上下文切换不保存 CPU-local GPR，因为该状态归 CPU 而非归任务。
  本批不实现 IPI、内核 trap、AP 调度、idle context、TLB 或完整 PerCpu。

**Docker 验证：**

### SMP-P1-B06：PerCpu online 成为 CPU 在线状态唯一真相源

**涉及文件：**

- `os/src/smp.rs` — 为每个 cache-line 对齐的 `PerCpu` 增加
  `online: AtomicBool`，删除全局 `ONLINE_MASK`，新增
  `configured_cpu_count()`、`online_cpu_mask()` 和唯一发布 helper。
- `os/src/kernel_tests/{mod.rs,smp.rs}` — 注册 `KTEST=smp`，验证 configured
  CPU 全部 online，以及 Phase 1 旧调度器仍只在 CPU0 运行。
- `docs/01_architecture/boot-and-trap.md`、
  `docs/10_plan/smp-8core-implementation.md` — 同步 online 所有权、内存序、
  focused test 和 Phase 1 `partial` 边界。

**设计与安全边界：**

- `PER_CPUS` 显式放入 `.data.boot`，因此 LA64 AP 在 CPU0 清 BSS 前安装
  CPU-local 指针时，逻辑身份和原子字段不会被后续清零。
- 每个 CPU 只写自己的 `online`。`compare_exchange(false, true, Release,
  Relaxed)` 发布本地 bootstrap 结果，并把重复发布转为可诊断的 panic。
- BSP 和运行期查询逐项执行 Acquire load；看到 true 即可观察对应 CPU 在
  Release 前完成的本地初始化。Phase 1 不支持 CPU offline，状态只会
  false→true，因此扫描到中间快照是允许的，等待循环会继续重试。
- 删除共享 `fetch_or` 后，AP 不再争用一个全局 online cache line，启动等待、
  日志和后续调用方也不会在 `ONLINE_MASK` 与 `PerCpu` 之间形成双真相。
- 本批不新增锁、unsafe、IPI、调度迁移、timer、idle context 或 TLB 语义。

**Docker 验证：**

- `make rv64-kernel-build-only CORE_NUM=2`：退出 0。
- `make la64-kernel-build-only CORE_NUM=2`：首次因 GitHub 连接超时无法更新
  `buddy_system_allocator` 失败；确认容器已有 lockfile 指定的
  `fb7c19c09162b07f7f45d11a939b96c84d358193` 后，仅补齐 Cargo 本地缓存，
  使用 `CARGO_NET_OFFLINE=true` 重跑，退出 0。未修改依赖声明或 lockfile。
- 双架构 `CORE_NUM=2 KTEST=smp`：均输出 `online_mask=0x3`，两个测试
  2/2 PASS，`[KTEST RESULT: PASS]`，QEMU 和文件系统 teardown 退出 0。
- RV64 `CORE_NUM=1 KTEST=smp`：输出 `online_mask=0x1`，两个测试 2/2
  PASS，证明无 AP 时 CPU0 走同一发布协议。LA64 单核未重复运行，因为共享
  退化逻辑已由 RV64 覆盖，LA64 架构启动路径已由双核 focused test 覆盖。
- 双架构 ELF 中 `PER_CPUS` 符号大小均为 `0x200`，类型位于 PROGBITS
  `.data`；符号表中不存在 `ONLINE_MASK`。

**阶段与维护结论：**
