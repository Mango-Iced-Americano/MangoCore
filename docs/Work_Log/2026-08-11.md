- 编译完成后的 `sync` 单独耗时约 1671 秒；324 个快照中 PID 1960 始终以 `Running(2)`、`current_cpu=2`、`syscall_id=81` 停留在同一次 syscall，没有进入任务级 Blocked。该单 CPU 同步内核循环产生 7,925,410 次恰好 4 KiB 的 VirtIO 读、约 30.24 GiB 读取、4654 次 journal commit、18,616 次 journal flush，以及 11,927,159 次 heap direct-buddy。代码路径在一次 sync 中集中 `drain_reclaims()`；每个 deferred reclaim 先经 `legacy_orphan_contains()` 全链验证，最终 `transaction_orphan_del()` 又从链头遍历。对数千个 ready orphan 顺序处理时形成强烈的 O(N²) 特征。这是数据与代码共同支持的主要根因，但旧 schema 未导出 exact reclaim count/chain visits，后续修复前仍应补两个直接复杂度计数。
- `sys_sync()` 先经 VFS lifecycle `sync_all_backends()` 调用 another_ext4 `FileSystem::sync()`，随后又调用 `sync_all_instances()`，存在同一实例重复 sync pass；应在 orphan 回收复杂度修复后去重验证。该 1671 秒发生在评分 marker 之后，不计入 `elapsed_s`，但会严重放大完整运行/清理时间，且 deferred reclaim 可能间接影响下一轮空间与碎片状态。
