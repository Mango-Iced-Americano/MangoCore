### B36 远程稳定 Queued 线程 `sched_setaffinity`

**状态：`pass`（stable-Queued-only）；完整远程 affinity 仍为 `partial`。** 非 current TID
处于稳定 `Queued(owner)` 时，现可在 owner 队列内更新 `cpus_allowed`；新 mask 排除 owner
时会把同一 TCB 唯一搬到合法目标 runqueue。远程 Running/Blocking 仍返回 `EOPNOTSUPP`。
双架构 8 核 focused 23/23 与 `mask=0x003` 初赛非回归通过。

**上游依据与最小状态选择：**

- Linux 的 `move_queued_task()` 先从源 rq deactivate、标记迁移、切换 CPU，再在目标 rq
  activate；`TASK_ON_RQ_MIGRATING` 让不持双 rq 锁的观察者重试。DragonOS 同样把 on-rq
  状态区分为 `Queued/Migrating/None`，并用 task placement 锁串行化 affinity。
- MangoCore 尚无 per-task `pi_lock`，但 owner runqueue 已能串行化 fetch/remove。B36 只增加
  一个无 CPU 参数的 `Migrating`：它精确表示“已离源 rq、未入目标 rq，唯一 owner 是同步
  迁移调用方”。没有增加 `Blocking/WakePending/Exiting` 等与本批无关的状态。
- 参考：Linux [`kernel/sched/core.c`](https://linux.googlesource.com/linux/kernel/git/torvalds/linux/+/2b414a95b8f7307d42173ba9e580d6d3e2bcbfce/kernel/sched/core.c)、
  DragonOS [`sched_info.rs`](https://github.com/DragonOS-Community/DragonOS/blob/master/kernel/src/process/sched_info.rs)。

**生产实现与每项原因：**

- `run_queue::set_queued_affinity()` 先按新 mask 判断是否需要搬队。mask 仍含 source 时，只在
  source 锁内复核 `Queued(source)` 和同一 TCB 指针，再 Release 写 mask；没有无意义的队列
  计数变化或 IPI。
- mask 排除 source 时，目标 kernel-stack 映射同步必须在取得 source 锁、尤其在进入
  `Migrating` 前完成。这样同步失败不会留下半迁移任务，exit/exec 等待 `Migrating` 时也不会
  间接等待 TLB IPI ack。
- 搬队顺序固定为：source 锁内 `Queued(source) -> Migrating` 并摘除；释放 source；迁移 owner
  发布 mask；target 锁内 `Migrating -> Queued(target)` 并插入；释放 target 后发送
  RESCHEDULE。任意时刻最多一把 runqueue 锁，状态、容器和 `nr_running` 各只交接一次。
- `set_remote_affinity()` 统一分派稳定 Blocked/Queued，避免 syscall 层复制两套锁协议。并发
  fetch 或退出先赢时，mask 尚未写入并明确返回失败；两个 affinity 写侧遇到 `Migrating` 时按
  实际完成顺序重新定位。
- `run_queue::remove()` 在迁移窗口后重新读取 owner，保证 exec/exit 不漏掉已经搬队的 TCB；
  批量退出继续使用已审计的 `TASK_MANAGER -> 单个 RunQueue` 锁序。迁移方在发布
  `Migrating` 后不取 `TASK_MANAGER`、不等 ack，所以没有反向依赖。
- nice hint 可能先于 rq 锁更新。`update_nice()` 若发现任务已离开读到的旧 owner，会先重算旧
  队列的 `nonzero_nice_count`，再追到最新 owner 重算，覆盖 fetch 与 affinity 搬队交错；该字段
  仍只是选择 fast-path 的派生计数，不成为第二个 owner 真值。
- WaitQueue 把 `Migrating` 视为已经 runnable，procfs 显示 `R`；`mark_zombie()` 对它 fail-stop，
  防止半迁移 TCB 被直接推进终态。没有新增测试专用生产字段、队列或 IPI reason。

**反假通过 focused 用例：**

### B35 远程稳定 Blocked 线程 `sched_setaffinity`

**状态：`pass`（stable-Blocked-only）；完整远程 affinity 仍为 `partial`。** 非 current TID
若仍以同一 TCB 指针登记在 interruptible registry，且状态精确为 Blocked，现可真实更新
`cpus_allowed`；后续生产 wake 按新允许集重新选择 CPU。远程 Running/Blocking/Queued/Zombie
仍返回 `EOPNOTSUPP`。双架构 8 核 focused 22/22 与 `mask=0x003` 初赛非回归通过。

**阶段选择与上游依据：**

- Linux 完整写侧用 task/rq 锁和 queued-migrating 状态稳定 placement；DragonOS 也把
  `cpus_allowed` 与 on-rq 状态置于 per-task 锁下。MangoCore 尚无同等远程 runnable 协议，
  直接给 Running/Queued 写 mask 会让现存 owner 落在新允许集之外。
- 稳定 Blocked 没有 current/runqueue owner，不需要搬队。现有 `TASK_MANAGER` 已同时保护
  interruptible registry 和唯一 `Blocked -> Queued(cpu)` wake 入口，因此可在不新增状态、锁、
  IPI reason 或迁移容器的前提下形成独立生产闭环。
- 参考：Linux [`kernel/sched/syscalls.c`](https://github.com/torvalds/linux/blob/master/kernel/sched/syscalls.c)、
  [`kernel/sched/core.c`](https://github.com/torvalds/linux/blob/master/kernel/sched/core.c)；DragonOS
  [`sys_sched_setaffinity.rs`](https://github.com/DragonOS-Community/DragonOS/blob/master/kernel/src/smp/syscall/sys_sched_setaffinity.rs)、
  [`sched_info.rs`](https://github.com/DragonOS-Community/DragonOS/blob/master/kernel/src/process/sched_info.rs)。

**生产实现与每项原因：**

- `sys_sched_setaffinity()` 把 online/scheduler/未 STOP 的 runnable 校验移到 current/remote 分支
  之前，使两条成功路径共享相同 errno 边界。目标不是 caller 时只尝试稳定 Blocked 更新；
  其它状态明确失败，不能只写 mask 后留下非法 owner。
- `manager::update_blocked_affinity()` 取得 `TASK_MANAGER` 后同时检查精确 Blocked 和 registry
  中的同一 TCB 指针。只看原子状态不够：exit/exec 先摘除 registry，稍后才标 Zombie，中间会
  短暂保持 Blocked；双重检查避免对正在退出的线程伪装成功。
- `TaskControlBlock::set_blocked_affinity()` 在权威字段旁复核非空、configured 与当前 runnable
  交集，再以 Release 发布 mask。wake 在同一 manager 锁域用 Acquire 读取；锁传手和原子内存序
  共同保证它不会越过成功写入继续使用旧 mask。
- 并发 wake 与写侧由同一锁线性化：写侧先锁则 wake 使用新 mask；wake 先锁则任务已经 Queued，
  写侧返回 `EOPNOTSUPP`。该路径只持 manager 锁，不获取 runqueue，不跨等待点持锁。
- focused 等待 helper 新增期望恢复 CPU，而不是复制第二个阻塞函数。旧用例设置 expected=origin，
  新用例设置 expected=CPU0；两者共享真实 Completion/WaitQueue 路径，命名分别表达局部性与重定向。

### B34 当前线程运行期 `sched_setaffinity`

**状态：`pass`（current-only）；完整远程 affinity 仍为 `partial`。** raw
`sched_setaffinity(0/current_tid)` 现在会真实更新当前线程的 `cpus_allowed`；若新 mask
排除当前 CPU，syscall 在返回前把同一 TCB 迁到负载最低的合法 CPU。实现没有新增
`TaskStatus`、task/rq 锁或第二套迁移容器，远程 TID 明确返回 `EOPNOTSUPP`，Queued/Blocked
任务写侧仍留给后续独立协议。双架构 8 核 focused 21/21 与 `mask=0x003` 初赛非回归通过。

**上游依据与范围裁决：**

- Linux `get_user_cpu_mask()` 会先清零内核 mask，再复制
  `min(cpusetsize, cpumask_size())`，所以非零短 mask 合法，未提供的高字节视为零；超长缓冲
  只消费内核支持的低位。当前实现据此替换旧的“只看首字节 bit0”stub，并忽略 configured
  范围外高位，交集为空才返回 `EINVAL`。
- Linux 的完整远程路径使用 `task_rq_lock()` 和 `TASK_ON_RQ_MIGRATING`，DragonOS 也以
  `pi_lock + OnRq::{Queued,Migrating,None}` 稳定 `cpus_allowed` 与 placement。MangoCore
  当前六态机尚无同等串行化；因此 B34 只闭合 current 线程，不把 `Blocked` 伪装成迁移态，
  也不在两把 runqueue 锁之间直接搬队。
- affinity 是 per-thread 属性。正参数只按 TID 调用 `ProcessManager::find_task()`，不复用
  会把进程 PID 回退成任一线程的旧 helper；权限通过后仍必须与 current `Arc` 指针相同。

参考：Linux [`kernel/sched/syscalls.c`](https://github.com/torvalds/linux/blob/master/kernel/sched/syscalls.c)、
[`kernel/sched/core.c`](https://github.com/torvalds/linux/blob/master/kernel/sched/core.c)；DragonOS
[`sys_sched_setaffinity.rs`](https://github.com/DragonOS-Community/DragonOS/blob/master/kernel/src/smp/syscall/sys_sched_setaffinity.rs)。

**生产实现与原因：**

- `sys_sched_setaffinity()` 先完成长度、指针、用户拷贝、configured mask、严格 TID 与权限校验，
  再进入 current-only 写侧。若 online/scheduler/未 STOP 的可运行交集为空，返回 `EINVAL`；
  非 current 目标返回 `EOPNOTSUPP`，不伪装成成功。
- `TaskControlBlock::set_current_affinity()` 断言调用者仍为本 CPU 唯一
  `Running(source)` current，且没有遗留 `migration_target`。新 mask 仍包含 source 时只用
  Release 发布；排除 source 时按 `nr_running + current` 选择最小负载并以 CPU ID 打破平局。
  `nr_running` 本身不包含 current，因此把 current 槽计入，避免把正在执行任务的 CPU 误判为空闲。
- 顺序固定为：同步目标 kernel-stack 映射 → Release 写 mask → Release 发布 target →
  syscall 丢弃多余 TCB `Arc` → 立即 `suspend_current_and_run_next()`。源 idle 用 Acquire 取走
  target 后，既有 `requeue_after_switch()` 只锁目标队列完成
  `Running(source) -> Queued(target)`，锁外发送 RESCHEDULE。mask 的读取升级为 Acquire，
  因而目标 owner 不会看到旧允许集合。
- `run_queue::nr_running(cpu)` 只是放置时无锁近似值，不承担正确性；真正 owner 仍由
  `sched_state + current/runqueue` 唯一决定。本批没有修改 wake、block 或远程队列锁序。

**双架构判别链：**

- 复用原有 hermetic 用户 probe，没有新增用户 ELF、生产诊断字段或临时源码文件。probe
  先由 B33 真实 IPI 从 CPU0 到 CPU1，确认 getcpu=1 和旧 mask=`0b11`；随后调用
  `sched_setaffinity(0, 8, bit0)`，要求 syscall 返回时 getcpu=0，再要求 getaffinity=bit0。
- 三段断言能分别拒绝“B33 IPI 未迁移”“B34 只改 mask 未迁移”和“发生迁移但 mask 未持久”
  三种假阳性；最终还核对 `last_cpu=0`、exit(0)、wait/reap、helper/user Zombie 与 Weak 释放。
- 首轮 RV64 真实 timeout 不是内核迁移失败：CPU0 ktest runner 只开中断却不进入任务安全点，
  无法消费 `need_resched` 后让出 CPU。加入既有 `run_task_safe_point()` 后，诊断快照证明
  task/helper/process 已全部 Zombie、两端队列为空；旧等待器仍要求瞬态 zombie 队列非空，
  而 CPU0 idle 已按生产逻辑 drain。最终删除该过时条件和临时快照，没有放宽稳定 owner 条件。

### B33 用户返回安全点消费远端 `RESCHEDULE`

**状态：`pass`。** 双架构 hard IPI 仍只发布 per-CPU `need_resched`，但运行中的
用户任务现在会在 `trap_return()` 的统一安全点消费该提示。timer 与 IPI 请求在 IRQ-off
窗口内合并，最多执行一次上下文切换；focused 用户探针不再依赖显式 yield，真实远端
IPI 已驱动同一 TCB 从 CPU0 交给 CPU1。双架构 8 核 focused 21/21 与
`mask=0x003` 初赛非回归均通过。

**生产实现与原因：**

- `smp::take_reschedule_request()` 成为唯一消费入口，AP idle 和用户返回路径共享
  Acquire `swap(false)`。handler 仍以 Release 置位，不取锁、不打印、不直接 schedule；
  这样不会把 hard IRQ 扩成任意内核点抢占。
- `task::run_task_safe_point()` 替代 timer-only 的旧长名称。它先关闭本地中断，完成
  deferred timer，再取走 IPI 提示，最后对两类请求做一次 OR 决策。判定到切换之间没有
  本地 handler 插入窗口，同时 timer/IPI 同时到达也只切换一次。
- RV64/LA64 的 `trap_return()` 都在 `do_signal()` 前调用同一入口。此时 trap frame 完整、
  syscall/task 锁均已释放；任务恢复后仍由当前 CPU 重写 `tp/$r21` 和激活 MM。
- `PerCpu.reschedule_count` 只在安全点确实消费提示时递增，作为生产诊断计数和 focused
  判别证据。它不改变调度决策，也不是测试开关。

**测试判别力：**

- 第 20 项改名为 `smp::user_task_reschedules_from_ipi`。probe 先在 CPU0 验证 getcpu=0

  因而 `reschedule_count` 增量只能来自本轮 IPI。最终同时检查 helper 发送成功、计数增长、

### B32 `sched_getaffinity()` 返回线程真实 mask

**状态：`pass`。** raw `sched_getaffinity()` 不再固定写 bit0，而是按线程读取
TCB 的 `cpus_allowed`。`pid=0` 查询调用线程，正数只按 TID 查找；当前
`MAX_CPUS=8` 的内核 mask 占一个 `usize`，成功返回实际复制的 8 字节。双架构

`sched_setaffinity()` 或运行期 mask 修改。

**上游语义与实现取舍：**

- Linux 将 affinity 定义为 per-thread 属性；raw syscall 成功返回复制字节数，而
  libc wrapper 才把成功值转换为 0。当前内核 mask 固定为一个 `usize`，因此长度必须
  至少为 8 且按 8 字节粒度对齐，用户缓冲区更大时也只复制 8 字节。
- 正数参数直接调用 `ProcessManager::find_task()`。没有复用同文件中会把 PID 回退为
  “进程内任一线程”的 scheduler helper，避免非 leader 线程读到错误 TCB。
- 先克隆目标 TCB 的 `Arc`、释放 registry 锁并读取原子 mask，随后才进入可能 fault-in
  的用户拷贝；registry、task inner 和 runqueue 锁都不会跨越 uaccess。
- B31 的 mask 只在 `New` 状态由创建者写，首次发布后不可变；runqueue 的 AcqRel
  状态交接已发布该值，所以 B32 的 Relaxed 快照不需要再制造一套锁或内存屏障协议。
  未来动态 setaffinity 必须重新证明这一点。

### B31 `cpus_allowed` 成为调度 placement 硬约束

**状态：`pass`。** 每个 TCB 现在持有权威的逻辑 CPU 允许位图；首次发布、
yield 切出后换 owner 和 Blocked 唤醒三条生产路径都在任务进入
`Queued(cpu)` 前验证目标 CPU。双架构 8 核 focused 21/21 与 `mask=0x003` 初赛
非回归全部通过。本节点不提供运行期 `sched_setaffinity()`，普通任务仍默认
CPU0-only。

**设计取舍：**

- 命名采用 DragonOS 的 `cpus_allowed`，与 Linux `task_struct` 中的
  `cpus_mask/cpus_ptr` 表达同一层 per-thread 调度约束。`MAX_CPUS=8` 且仓库已统一使用
  `usize` CPU mask，因此没有为本包额外创建 `CpuMask` 文件或包装类型。
- Linux 和 DragonOS 的运行期 affinity 修改都要与 task/runqueue 锁及迁移串行化。
  当前只建立初始不变 mask，没有把一次 Atomic store 冒充完整 `sched_setaffinity()`，
  避免 Running/Queued/Blocked 任务在旧 owner 上违反新 mask。
- 没有新增 `Migrating` 等状态。`sched_state` 继续是 owner 唯一真值，`cpus_allowed`
  只表达“可以取得哪个 owner”，两者职责不重复。

**实现与每项原因：**

- `task.rs` 在三个 TCB 构造路径中初始化 mask：普通任务为 CPU0，ktest
  构造器保留 CPU0 安全默认，clone 继承父线程值。Exec 复用原 TCB，因而自然保留。
- `set_initial_cpus_allowed()` 只接受 `New`、非空且完全落在 configured CPU 内的
  mask。调用者必须独占 mask 写入与首次发布时序；TCB 可以已登记弱引用，
  因此注释没有误称“独占整个 TCB”。
- `run_queue.rs` 在 `publish`、`requeue_after_switch` 和 `enqueue_woken` 的最终 owner
  交接前 fail-stop 验证 mask。检查位于目标 runqueue 锁之前，失败不会遗留半入队状态。
- `manager.rs::select_wake_cpu()` 把 allowed、online、scheduler-ready 和 non-stopped mask

### B30 `getcpu()` 返回真实逻辑 CPU

**状态：`pass`。** `getcpu()` 不再固定返回 0，而是返回调用瞬间的 MangoCore 逻辑 CPU
编号。B29 的同一用户探针已升级为迁移前断言 CPU0、真实 `sched_yield` 后断言 CPU1，双架构
8 核 focused 与 `mask=0x003` 初赛非回归均通过。该节点只完成 CPU 查询 ABI，不开放
affinity、普通用户任务全核调度、NUMA 或共享 I/O。

**目标与边界：**

- Linux `getcpu(2)` 返回调用线程当前所在 CPU 与 NUMA node；两个输出指针都可为 NULL，第三个
  tcache 参数在现代内核中忽略。MangoCore 使用连续逻辑 CPU 编号，不能把 RISC-V hart ID 或
  LoongArch CoreID 直接暴露给用户态。
- MangoCore v1 没有 NUMA，因此 node 明确返回 0。这个值表达“单一 node”，不代表 CPU 仍为 0。
- 本节点不修改 TCB、runqueue、迁移协议或默认发布策略。普通任务仍固定 CPU0，只有 B29 已有的
  hermetic 探针通过一次性目标迁到 CPU1。

**实现与每项修改的原因：**

- `sys_getcpu()` 在任何用户指针写入前只调用一次 `smp::cpu_id()` 并保存快照。这样 `cpu` 与
  `node` 描述同一次调用，且不会因两次查询跨过潜在 fault/copy 路径而组合出不一致结果。
- `cpu_id()` 已把硬件 ID 映射为 scheduler/PerCpu 使用的 `0..N-1`，正好满足用户态数组索引和
  affinity mask 所需的逻辑编号语义。没有增加锁、等待点或调度动作。

### B29 用户任务在显式 yield 安全点迁移

**状态：`pass`。** 同一真实用户 TCB 已在双架构 8 核环境中从 CPU0 起跑，经用户

**目标与边界：**

- B28 只证明“CPU0 构造、CPU1 从第一次 dispatch 起完整执行”；B29 必须让同一个 TCB

- 迁移只发生在任务已切回源 CPU idle 栈之后。当前不支持任意远程强制迁移、queued task
  搬队、阻塞态迁移、负载均衡、work stealing 或普通用户任务全核调度。
- 不增加 `Migrating` 等 `TaskStatus`。迁移意图不是 owner；唯一 owner 继续只由
  `sched_state` 与 current/runqueue 容器表达。

**实现与每项修改的原因：**

- `TaskControlBlock` 增加一次性原子 `migration_target`，空值为 `usize::MAX`。它只保存
  “下一次真实 yield 切出后的目标”，不参与 current/runqueue 唯一性判定。New 任务可在
  首次发布前登记；Running 任务只有本 CPU 的 current 本人可登记，避免远程请求与
  Blocking/Zombie 竞态。
- `request_migration()` 先验证目标 configured、online 且已经进入 scheduler，再完成目标
  CPU 的 kernel-stack mapping TLB 同步，最后用 Release 发布目标。同步必须早于请求可见，
  否则目标 CPU 可能先 fetch，再在 `__switch` 刚恢复新 `sp` 时命中旧的无效翻译。
- `finish_switch_out()` 只在源 current 已清空、任务已运行于 idle 栈后取走请求。
  `requeue_after_switch(task, source, target)` 只锁目标队列，并在同一锁域完成
  `Running(source) -> Queued(target)` 与入队；远程 `RESCHEDULE` 在锁释放后发送。没有同时
  持有两个 runqueue，也没有把任务提前放入目标 current。
- Blocking 成功提交为 Blocked、或任务进入 Zombie 时丢弃尚未消费的 yield 请求；wake 仍按
  `last_cpu` 走 B20 协议。本节点不把一次性请求偷偷扩成阻塞迁移语义。
- B28 的直接 AP 用户用例升级为 `smp::user_task_migrates_on_yield`：探针先发布 CPU0，runner
  主动 yield；FIFO 使探针在 CPU0 执行 getpid/yield，源 idle 收尾再将其交给 CPU1，最终

### B28 受控 AP 用户态 syscall、yield 与退出回收闭环

**状态：`partial`。** 双架构 8 核 focused 与初赛非回归均通过；仓库既有 lint warning

**目标与边界：**

- B27 已完成双架构 MM-owned ASID 和页级 shootdown，但用户 trap handler 仍断言只能在
  CPU0 运行，缺少一条真实用户任务从远程发布、trap-return、syscall/yield 到退出回收的

**实现与每项修改的原因：**

- `task/manager.rs` 增加唯一 `publish_task_on(task, cpu)`：先验证目标已 online/scheduler-ready，
  远端目标先确认动态 kernel stack 映射，再通过生产 runqueue 状态机发布，最后在队列锁外
  发送 `RESCHEDULE`。这样 kernel-only ktest 与用户探针不再复制三段协议，也不会出现
  “doorbell 先到、任务/栈尚不可见”的竞态；普通 `publish_task()` 仍固定 CPU0。
- `task/processor.rs` 增加 `current_trap_task()`，一次克隆本 CPU current，再在 processor
  锁外校验 `TaskStatus::Running(cpu)`。它取代两架构过时的 CPU0-only 断言；返回型 syscall
  后重新调用并重新读取 CPU ID，为未来 syscall 内 yield 后迁移保留正确语义，同时避免
  trap 热路径为“取 current”和“校验 owner”重复获取同一把锁。
- 双架构 syscall handler 在进入 `syscall()` 前显式 drop 临时 TCB `Arc`。`exit/exit_group`
  切回 idle 后不会返回当前 Rust 栈帧，依赖作用域析构会永久多留一个强引用；返回型 syscall
  再重新取得 current 写回结果。测试最后用 `Weak::upgrade()` 直接验证强引用已经归零。
- `kernel_tests/smp.rs` 内嵌 RV64/LA64 的最小 generic-ABI 指令，仅执行 getpid、yield、exit。

### B27 RISC-V MM-owned ASID、epoch rollover 与按 ASID 页级 RFENCE

**状态：`partial`。** 双架构构建、RV64 8 核 focused、双架构 8 核初赛非回归均通过；
仓库 lint baseline 已在 B27 之外发生漂移，因此 `make lint` 仍为 RED，不能写成完整 `pass`。

**目标与官方依据：**

- B24 已能把 RV64 单页范围交给 SBI RFENCE，但所有用户 MM 仍固定使用 ASID 0，页级
  flush 无法限定到目标地址空间；trap 每次切换 SATP 也必须全量 `sfence.vma`。
- RISC-V Supervisor 规范规定 RV64 `satp[59:44]` 是 ASID，并要求通过“向 ASID 字段写
  全 1、读回最低有效实现位”探测 ASIDLEN；写 SATP 本身既不隐含页表写入排序，也不自动
  失效旧翻译。页级 non-global 失效应使用 `SFENCE.VMA va, asid`。
- SBI RFENCE FID 2 的 ABI 是 `hart_mask, hart_mask_base, start, size, asid`，第五个参数
  位于 a4；调用同步返回后，目标 hart 已完成等价的地址范围 + ASID 失效。
- Linux RISC-V 的 `context.c` 使用 versioned ASID 与 rollover，全局无 ASID 时退化为
  switch-time flush；`tlbflush.c` 的页/范围失效同样携带目标 MM 的 ASID。MangoCore 沿用
  这些硬件语义，但不复制 Linux 的 per-CPU bitmap/调度结构。

参考：

- <https://docs.riscv.org/reference/isa/v20260120/priv/supervisor.html>
- <https://docs.riscv.org/reference/sbi/v3.0/ext-rfence.html>
- <https://raw.githubusercontent.com/torvalds/linux/master/arch/riscv/mm/context.c>
- <https://raw.githubusercontent.com/torvalds/linux/master/arch/riscv/mm/tlbflush.c>

**实现与可维护性取舍：**

- 没有新增 MM wrapper、commit 类型或源文件。RV64 allocator 直接放进现有
  `hal/arch/riscv/sv39.rs`，长期所有权仍由既有每 MM `TlbContext.asid_context` 承担；
  PTE 生命周期仍只有 `MmuGather -> TlbFlush` 一条提交链。
- BSP 在内核 Sv39 页表生效、AP 和用户任务尚未发布时探测 ASIDLEN。内核永久保留
  ASID 0，用户从 1 单调分配；QEMU virt 实测为 16 bit，即 65535 个用户编号。
- 软件 context 用高位保存 epoch、低 16 位保存硬件 ASID。MM 销毁不立即归还编号；空间
  耗尽后只有一个 CAS leader 执行全 online CPU user-TLB flush/ack，收齐后才推进 epoch
  并从 1 复用。等待者不持 VM 锁，并临时开放本地中断，避免双方等待 TLB IPI ack。
- `AddressSpace::activate_on()` 仍在 VM 锁内成对取得页表根和 ASID；发现耗尽时先释放锁，
  再 rollover 并重试。页表修改方也在同一 VM 锁内冻结 target mask、generation、ASID
  和 VPN，锁外才执行 RFENCE/IPI 和退休 frame。
- 本地页级失效改为 `sfence.vma va, asid-register`；即使 ASID 数值为 0，也让 rs2 使用
  普通寄存器而不是 x0，保留“精确匹配 ASID 0”语义。远端 RFENCE 改用 FID 2，并将 a4
  纳入 `sbi_call_v02`。固件缺少 RFENCE 时仍走 B26 固定 slot 软件 IPI fallback。
- trap 入口从旧用户 SATP 提取 ASID，返回时使用已编码 MM-owned ASID 的完整 SATP。
  非零 ASID 把用户翻译与固定内核 ASID 0 隔离，因此普通切根不再固定全刷；ASIDLEN=0
  平台仍执行原有 switch-time 全量 `sfence.vma`，不把性能优化变成兼容性前提。

**最关键的 rollover 竞态：**

- “全 CPU 已 flush 并 ack”本身还不够。如果某 CPU 在 ack 前已读取旧页表根/ASID，ack
  后再把该快照安装进 SATP，就会重新运行旧 epoch。
- 因此 RV64 `trap_return()` 明确断言 SIE 已关闭，并从 `activate_user_vm()` 取得 context
  到汇编最终 `sret` 持续保持 IRQ-off。目标 CPU 要么先带旧 context 返回，然后被 pending
  IPI 立即拉回内核、flush 后 ack；要么先 ack，之后重新取得新 epoch context。不存在
  “先 ack、后安装旧 SATP”的顺序。
- DeepSeek 的初次设计审查正确指出 SBI a4/FID 2、SATP 编码和公共 `asid_context` 三个
  接口缺口，但认为 flush 后旧快照可再次安装仍安全。GPT/Codex 按逐指令时序否决该判断，
  补上 IRQ-off 交接不变量，并把模式沉淀到 `debugging-patterns.md`。

## RV64 DTB pre-BSS 持久化快照修复

**根因：** 当前 RV64 QEMU ktest 环境下，OpenSBI 将 DTB 放置在物理地址 `0x82200000`，该地址恰好落在内核旧版 BSS 段覆盖范围内。`mem_clear()` 将 BSS 清零时，DTB 原始数据被擦除，导致 post-heap `build_platform_info()` 解析到全零 FDT 头部，回退到静态 fallback。

**设计：** 在 `rust_main()` 中 `bootstrap_init()` 之后、`populate_memory_regions()` 之内、`mem_clear()` 之前，`capture_fdt_snapshot()` 验证 DTB magic (`0xd00dfeed`) 和合法 `totalsize`，通过 `ptr::copy` 将完整 DTB 字节复制到 `#[link_section = ".data.boot"]` 标注的 `FDT_SNAPSHOT` 静态缓冲区。该缓冲区位于 `.data` 段（不受 BSS clear 影响），容量固定为 `MAX_FDT_SNAPSHOT_SIZE = 2 MiB`。`readelf` 验证：快照地址 `0x80944038`、大小 `0x200008`，位于 `.data` `[0x80467000, 0x80b45000)` 且早于 BSS 起始 `0x80b85000`。

**仅 `RiscvFdt` 协议：** `has_valid_dtb()` 检查 `BootProtocol::RiscvFdt` 以及 `dtb_paddr != 0` 和页面对齐；`UbootGo`、`LoongArchLegacy`、`Test` 不走快照路径，继续使用静态 fallback。`build_platform_info()` 从 `fdt_snapshot()` 返回的 `&[u8]` slice 构造 `fdt::Fdt`，不再从原始 firmware 物理地址读取。

**涉及文件：**
- `os/src/hal/firmware/mod.rs` — `FdtSnapshot` 结构体、`MAX_FDT_SNAPSHOT_SIZE`、`#[link_section = ".data.boot"] static mut FDT_SNAPSHOT`、`has_valid_dtb()` gate、`populate_memory_regions()` 中先捕获快照再解析 memory regions
- `os/src/hal/firmware/fdt.rs` — `read_totalsize()` 验证 DTB magic 和大小，`capture_fdt_snapshot()` 执行 `ptr::copy` 到全局快照；`fdt_snapshot()` 返回不可变 slice；`build_platform_info()` 改用快照而非原始 paddr；`parse_memory_regions()` 从快照重新解析 DTB memory 节点，原始 paddr 仅用于 `dtb_start`/`dtb_end` 物理保留区间计算
