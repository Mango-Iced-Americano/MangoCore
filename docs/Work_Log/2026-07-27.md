### SMP-P2.5-B15：切栈后调度所有权交接与统一唤醒

**根因与设计收敛：**

- 旧 B15 草案让通用 `TaskManager::add()` 同时接受 `New` 和 `Running`，yield
  又在 `__switch` 之前清空 `Processor.current` 并把仍使用自身内核栈的任务改成
  `Queued`。这会在真正多核后允许同一 TCB 被另一 CPU 提前取走。
- 最终方案没有引入 `SwitchAction`、claim token、`WakePending` 或 `Exiting`，只在
  `New/Queued(cpu)/Running(cpu)/Blocked/Zombie` 基础上增加必要瞬态
  `Blocking(cpu)`，表示“已经登记睡眠意图，但任务仍由当前 CPU 执行”。
- `Processor.current` 保留到 `__switch` 真正返回 idle 栈；idle 随后统一调用
  `finish_switch_out()`，根据最终状态提交 `Running -> Queued`、
  `Blocking -> Blocked` 或把 Zombie Arc 移入回收队列。

**实现与不变量：**

- 删除通用调度 `add_task()`，以 `publish_task()` 明确限定
  `New -> Queued(CPU0)`；保留与旧代码语义一致的 `fetch_task(cpu)`，并把内部入口
  统一命名为 `publish_task/begin_interruptible_sleep/finish_switch_out/fetch_task`。
- yield 不再自行改状态或入队；block 在 `TASK_MANAGER` 锁内执行
  `Running(cpu) -> Blocking(cpu)` 并登记 interruptible registry。早到 wake 执行
  `Blocking(cpu) -> Running(cpu)` 且不入队，晚到 wake 执行
  `Blocked -> Queued(CPU0)` 并加入队首，两者由同一个 CAS 循环裁决。
- timer、signal、WaitQueue、Completion、legacy timeout 和 realtime timer 均不再
  在外部预写调度状态；统一 wake 返回本次是否赢得唤醒权。必成功的 publish、fetch
  和 switch-out 迁移在所有构建中 fail-stop，删除 `smp_debug` 和非法迁移计数。
- exit 路径只借用 `Processor.current` 持有的 TCB，不 clone 一个永远不会返回析构的
  本地 Arc；只有切回 idle 后才把 retained Arc 转入 zombie queue，避免提前释放
  当前内核栈，也避免退出栈帧泄漏引用。
- `scheduler_state_has_unique_owner` 只调用生产 API，覆盖提前取消 Blocking、完整
  Completion block/wake、helper publish/fetch/zombie 和重复 wake；删除直接伪造
  `try_sched_transition` 的测试代码及所有生产实验字段。

**审查与已知技术债：**

- 冻结源码只读复核结论为 `ACCEPT WITH CHANGES`，未发现实际并发 Bug；采纳
  `try_sched_transition` 的 `#[must_use]` 和 ktest 延迟 live-count/rusage 注释建议。
- 旧 nice-aware `pop_fair_ready()` 仍在全局 `TASK_MANAGER` 锁内读取
  `task.inner.sched_vruntime/sched_nice`。当前不存在反向同时持锁路径，因此没有形成
  锁环，但这是 Phase 3 拆 per-CPU runqueue 时必须消除的既有技术债。
- 当前仍只有 CPU0 进入 legacy scheduler，AP 只运行 SMP 服务循环；本批没有实现
  per-CPU Processor/runqueue、远程 enqueue、任务迁移或跨核退出协议。

### SMP-P2.5-B16：用户 PTE 的本地 TLB 提交边界

**问题与设计选择：**

- 旧实现由 `Vma`、缺页、CoW、mprotect、OOM 和退出路径分散调用
  `PageTable` 的带刷新方法。这种结构无法在 Phase 4 统一接入 active CPU
  mask、generation 和 shootdown ack，也无法用类型边界表达“旧 PTE 失效前不得
  复用物理页”。
- B16 只实现当前 CPU0-only 调度前提下的本地协议，不提前假设远端
  IPI/ack 已存在。`TlbPublication` 因此显式分为
  `Unpublished/LocalOnly/Published`；`Published` 在任何 PTE 写入前 fail-stop，
  防止将 local flush 伪装成 SMP shootdown。
- 实现前对照 RISC-V Privileged ISA、LoongArch ISA 与 Linux LoongArch 主线实现。
  RV64 的 `sfence.vma va, zero` 可对指定 VA 失效所有 ASID 的本 hart 项；
  LA64 `INVTLB 0x3` 失效本核全部 `G=0` 项。由于当前 LA64 ASID 仍归
  TCB，页表对象不能安全使用“当前 ASID + VA”的 `INVTLB 0x5`，故 B16
  保守清除本核全部非全局项。

**实现与安全不变量：**

- 新增 `mm/tlb_batch.rs`，为 map/unmap、block-write、PPN、flags 和 dirty
  修改提供唯一用户页表提交入口。`PageTable` 同步增加 raw/no-flush
  原语和 `flush_tlb_page()`；原有安全方法仍供内核页表路径使用。
- `UserMapper` 改为借用 `TlbBatch`，用户 PTE 的缺页、filemap、CoW、
  fork、mmap/munmap/mprotect/madvise、OOM/swap、exec、trampoline 和 zombie
  清理均经过同一边界。静态审计确认 raw/no-flush 用户写入没有另外调用者。
- batch 只修改一个 VPN 时请求页级刷新，出现第二个不同 VPN 后升级为
  本核全量刷新。RV64 因此保留单页 fault/CoW fast path；LA64 在 MM-owned
  ASID 完成前由 HAL 保守升级为全部非全局项失效。
- unmap 先清 PTE，再把从 VMA 移出的 `Arc<FrameTracker>` 交给
  `defer_frame()`。batch 严格按“PTE write → local flush → frame drop”提交；
  `Drop` 在 `?` 和提前返回时兜底，延迟队列 `try_reserve` 失败时先结束
  当前小批次，只放弃合并刷新效率。
- CoW 替换 PPN 后才延迟旧 frame；若后续 flags 修改失败，先恢复旧
  PPN，再延迟曾短暂出现在 PTE 中的新 frame。映射中途失败的回滚也先
  unmap 已发布 PTE，避免 VMA 已失去 frame 所有权但页表仍指向该页。
- `Frame::zip/swap_out/force_swap_out()` 改为返回被替换的 resident
  `Arc<FrameTracker>`，OOM 路径因此能在 PTE 清除后将 frame 交给 batch。
  `VmPageStore` 新增无分配的范围扫描入口，使批量 discard/unmap 不需为 VPN
  列表再分配内存。
- `release_for_zombie()` 与 exec 旧 MM 回收不再直接清 VMA，而是先通过
  `unmap_all()` 提交 PTE/TLB/frame，之后才释放页表页。LA64 software dirty
  fault 也不再从 token 重建临时页表，而是在权威 `AddressSpace` 锁内提交 batch。

**DeepSeek 只读审查与人工裁决：**

- 实施前审计指出旧单页 unmap 存在“先从 VMA 移除 frame，后清 PTE”的
  生命周期风险，直接促成 `deferred_frames` 设计。
- 冻结源码审查结论为 `ACCEPT`，无 P0/P1；它发现 LA64 旧安全接口的
  `invalidate_page()` 仍使用当前 ASID 精确失效。虽然 B16 用户路径已不经过该
  接口，仍采纳建议，将非内核分支改为本核全部非全局失效，消除未来误用风险。
- 未采纳将“有 deferred frame 却没有 PTE 修改”的 `assert!` 降为
  `debug_assert!`；该条件意味着可能在未失效 TLB 前释放物理页，属于释放构建
  也必须 fail-stop 的安全不变量。

**Docker/QEMU 验证：**

- 基线 HEAD：`8c3da24c605de2104d6ad43de5c4e2372cc9567f`；受测源码差异
  SHA-256：`8c4c89ce05261dd5339b3291811c5b8da7fde782405e1420fcb3b267df40f118`。
  两个 recipe 的 HEAD、tracked diff、status 和 untracked content 指纹在测试前后一致，
  `mutation_detected=false`。
- RV64 `CORE_NUM=1 KTEST=mm KREPEAT=2`：退出 0，126.287 秒，TAP `1..8`，
  8 passed / 0 failed，`local_tlb_batch_map_protect_unmap` 两轮 PASS。
- LA64 同配置：退出 0，133.659 秒，TAP `1..8`，8 passed / 0 failed，
  新用例两轮 PASS。两架构均无 timeout、panic 或 forbidden marker。
- 双架构 PASS 后只同步了 MM 文档，并更正 `page_fault.rs`/`mapper.rs`/`vma.rs`
  的三处模块级注释，说明用户 PTE 经 batch、`PageMapper` 仅保留内核路径。没有再修改
  Rust item、生成代码或测试逻辑，因此没有为纯注释变化重复执行数分钟的
  双架构 QEMU；上述 SHA-256 绑定的是实际受测代码快照。
- 新用例使用生产 API 执行映射、Store fault-in、mprotect 降权、Load/Store
  权限检查、munmap 与同 VPN 重新映射。它证明双架构本地路径可运行，
  但没有直接观测硬件 TLB 内容，也不代替 Phase 4 的 generation/ack、远端 victim
  与 ack 前 frame 不复用测试。

**阶段结论与边界：**

- `SMP-P2.5-B16=pass`；Phase 2.5 的调度所有权与本地 TLB batch 退场条件
  已完成。下一主线阶段是 Phase 3 per-CPU runqueue/current slot，但用户任务
  在远端 shootdown 完成前继续固定 CPU0。
- B16 未实现 active CPU mask、TLB generation、SBI RFENCE/IPI fallback、LA64
  shootdown slot/ack、MM-owned ASID/epoch 或 kernel-global shootdown；这些均保留给 Phase 4。
- 本包没有产生超出项目现有 TLB/生命周期准则的新通用调试模式，不追加
  workflow references。

  `effort=max`，严格串行执行 RV64 后 LA64，各运行一次。实际构建与 QEMU 均在

- “初赛部分”按仓库 mask 定义收敛为 `mask=0x003`，即 basic 与 busybox；每个
  架构均使用 `CORE_NUM=8`、比赛式单 socket/8 core/单 thread 拓扑、官方 x0 的
  派生副本及本架构 x1 工具盘。未扩展到 `0xFFF` 决赛全量。

**结果与证据：**

- RV64：确定性 recipe PASS，退出 0，430.993 秒；启动日志为
  `configured=8 ... online_mask=0xff`。basic-musl、basic-glibc、busybox-musl、
  busybox-glibc 均到达结束标记且脚本 `exit_code=0`；judge 为 312/314，其中

  `configured=8 ... online_mask=0xff`。同四组均到达结束标记且脚本
  `exit_code=0`；judge 为 305/314，未满分项为 basic-musl 的 `test_brk`
  1/3、basic-glibc 的 `test_brk` 1/3 与 `test_pipe` 1/4，以及两个 busybox
  组各自的 `busybox kill 10` 0/1。

**人工裁决与边界：**

- 两个 recipe 的“PASS”表示 8 核最小启动和初赛组完整执行通过，不等于 judge

  丢分均为单核既存问题或与 SMP 无关；LA64 `test_pipe` 的交错输出在单核抢占下

- 两架构 normal 启动阶段均出现 APK DNS transient error 和可选 e2fsprogs 安装
  错误，但 basic/busybox 随后完整执行。为使后续 focused 初赛配方不再混入网络
  环境噪声，本地配方已增加 `skip_apk=true`；本次受测日志仍如实记录原始错误。
- AP 当前仍 park，用户任务继续只在 CPU0 调度；本次不证明跨核用户调度、远端
  TLB shootdown、FS/NET 多核并发安全或 Phase 3/4 完成。
