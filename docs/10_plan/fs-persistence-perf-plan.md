# FS Persistence & Performance Optimization Plan

> Oracle 分析结论 | 2026-07-29 | develop 分支

## 根因诊断

APK 安装失败是完整持久化故障链：

1. `flush_all_page_caches()` 静默丢弃 `writeback_all()` 错误
2. `DIRTY_EMERGENCY_MIN_PAGES=65536` (256MB) 使正常写入永不触发后台写回
3. `writeback_pages_run_locked()` 失败后页面卡在 Writeback 状态，不可重试
4. shutdown/reboot 忽略持久化失败
5. APK bootstrap 用 `; true` + 忽略返回码掩盖部分安装

### Phase 2 — 建立合理写回水位

**目标**：正常写入能触发后台写回，避免脏页无界累积。

| # | 文件:行号 | 修改 |
|---|-----------|------|
| 1 | `page_cache.rs:2375-2423` | 三段水位：background 8192 / throttle 16384 / emergency 32768 页，同时考虑可用页比例 |
| 2 | `page_cache.rs:2409-2414` | `balance_dirty_pages()` 按水位执行不同策略 |

**启动值建议**（最终由双架构长写测试校准）：
- `DIRTY_BACKGROUND_PAGES = 8192` (32MB)
- `DIRTY_THROTTLE_PAGES = 16384` (64MB)
- `DIRTY_EMERGENCY_PAGES = 32768` (128MB)
- 保留可用页比例保护

**验证 Gate C**：~50 个 LTP 回归全绿，不新增 panic/TFAIL。

## 架构注意事项

- rv64 VirtIO MMIO vs la64 VirtIO PCI — 差异在传输层，不影响 PageCache 逻辑
- 两架构 PAGE_SIZE 都是 4KB
- LA64 内核栈 128KB，批量 I/O staging 放堆或 DMA 池，禁止栈大数组
- 双架构必须串行构建
