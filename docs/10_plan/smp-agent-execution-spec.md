# MangoCore SMP 适配 Agent 执行规范

> 本规范是 SMP 适配期间的人工协作约定。目标是以完整不变量为工作单位，并让
> 审查、验证和证据成本与改动风险匹配；既不把高风险并发改造做成不可审查的大提交，
> 也不把一个语义闭环机械切成大量低效率小 patch。

## 1. 适用范围

以下工作只要服务于 SMP 目标，就必须遵守本规范：

- BSP/AP 启动、boot stack、per-CPU 和 CPU-local 寄存器；
- trap、IPI、timer、idle、抢占点和中断开关；
- 调度器、runqueue、任务状态、affinity 和迁移；
- 页表、TLB shootdown、ASID、CoW 和用户 MM；
- 为 SMP 修改的锁、原子操作、unsafe、驱动、文件系统和网络代码；
- SMP ktest、QEMU 参数、构建配置、Work Log 和设计文档。

纯只读分析不消耗代码额度，但必须汇报重要发现。生产路径代码按风险等级进入相应确认流程；
纯文档、注释和不改变判定语义的诊断修改不要求单独申请。

## 2. 风险分级与人工确认模型

一个批次是围绕一个完整不变量的**工作包**，不是一次 `apply_patch`、一次编译或固定行数切片。
工作包按最高风险分为：

| 等级 | 典型内容 | 人工确认 |
|---|---|---|
| L0 | 文档、注释、日志文字、证据整理，不改变控制流或 PASS 判定 | 无需修改前申请；完成后简要汇报 |
| L1 | 局部机械改造、私有辅助函数、架构隔离且不引入共享并发状态 | 可纳入已批准工作包连续完成；工作包末汇报 |
| L2 | 启动/per-CPU/共享状态的一项完整不变量，但不新增高危生命周期或锁序 | 修改前说明范围；允许在批准范围内连续完成多个紧耦合步骤，末尾统一汇报 |
| L3 | trap 汇编、IPI/ack、runqueue 状态机、TLB/ASID、frame 生命周期、新 unsafe 或锁序 | 修改前明确批准；完成后详细汇报并停止等待人工审核 |

L2/L3 工作包开始前，agent 提交目标、文件范围、预计关键代码、并发影响、风险等级和自适应
验证方案。批准后可以完成保持该不变量闭合所需的实现、注释、focused test、修复编译错误和
文档同步，不在每个中间 patch 或每次构建后重新申请。

用户可以预先批准一个列出编号、范围和风险边界的连续工作包。L1/L2 可按该授权连续推进，
在约定里程碑统一汇报；L3 仍在每个高风险不变量完成后停止。任何工作包都不能借总体授权静默
扩展到新的高风险不变量。

每批使用编号 <code>SMP-P&lt;phase&gt;-B&lt;sequence&gt;</code>，便于报告、Work Log 和证据文件互相对应。

### 2.1 规则与工具上下文复用

- 新任务首次进入 SMP 写操作时，完整阅读本规范和当前 Phase；
- 同一连续任务（包括上下文压缩后的自然续接）且规范文件未变化时，记录
  `smp-agent-spec loaded` 即可，后续只重读当前 Phase、目标代码和本次真正相关的章节；
- 已经读过且未变化的 AGENTS、Skill 和工具 schema 不做机械全文重读或重复发现；
- 规范/AGENTS 发生变化、进入新的高风险子系统、上下文中没有已加载记录，或用户要求重新审计时，
  才重新全文读取；
- `debugging-patterns.md` 只在实际 bug、竞态或故障定位时读取，
  `harness-patterns.md` 只在性能、计数器或长测任务时读取；普通功能推进不为满足形式重复加载。

## 3. 关键代码约 100 行原则

### 3.1 什么属于关键代码

以下内容计入关键代码：

- os/src、user/src 和 dependency 中进入生产路径的 Rust、汇编、C 和头文件；
- linker script、build.rs，以及改变 SMP 启动或运行语义的 Makefile/QEMU 配置；
- unsafe、原子操作、锁、CSR、PTE、IPI、调度状态机相关的宏和常量。

以下内容不计入关键代码额度；在 L2/L3 或明显影响审查规模时单独统计：

- 直接解释关键代码的纯注释行和空行；
- kernel test、用户态 regression 和测试 fixture；
- Work Log、证据 manifest 和设计文档；
- 只改变诊断文本、不改变控制流的日志内容。

测试脚本或配置一旦改变 QEMU 拓扑、超时、PASS 判定或实际功能行为，就按关键代码计算。

### 3.2 计数方法

关键代码按补丁中的非空、非纯注释代码行计算：

<code>critical_lines = critical_added + critical_deleted</code>

- 修改一行按一次删除加一次新增计算；
- 移动关键代码按删除和新增分别计算；
- 同一批次的多次 patch 累计计算；
- 含尾部注释的代码行仍是关键代码行；
- formatter 或 codegen 意外改变关键代码时同样计入。

计数采用“机器生成原始补丁 + 合理语义估算”：

1. 使用 `git diff --numstat`、`git diff --stat` 和目标文件清单防止漏掉配置、汇编或生成文件；
2. 报告 raw added/deleted，并估算 critical、comment/test/doc 三类即可；
3. 只有明显超过预算、L3 高风险、分类存在争议或用户要求时，才制作逐行语义账本；
4. 日志、测试配置若改变控制流、拓扑或 PASS 判定，仍计入 critical。

行数用于控制审查复杂度，不是正确性证明，也不能通过压缩语句或删除注释规避。

### 3.3 合理超出与拆分信号

100 行是默认设计目标，不是硬上限。

- 原则上将关键代码控制在约 100 行；
- 为保持一个不变量完整、双架构接口一致、错误路径闭合或避免不安全中间态，可以合理超过；
- 约 100～130 行只需在报告中解释；预计明显超过约 130 行时在修改前说明；
- 超过约 150 行、同时处理两个可独立审查的不变量，或审查者难以一次理解时，通常应拆分；
- 若拆分会制造不可编译或语义不安全的中间态，可在人工批准后作为一个工作包完成。

不得通过压缩多条语句到一行、删减必要注释或隐藏到测试代码中规避统计。

## 4. 修改前门禁

### 4.1 只读准备

每个新工作包开始前按相关性准备：

1. 在任务首次修改时加载 mango-workflow；连续任务复用已加载状态；
2. 按 §2.1 判断是全文读取规范，还是只读取当前 Phase 和相关章节；
3. 只有实际 bug/竞态诊断才读 debugging-patterns，性能/长测才读 harness-patterns；
4. 检查 git status、目标文件现有 diff 和相关调用链；
5. 只有新增/改变锁关系时才检查并更新 `docs/01_architecture/lock-order.md`；
6. 确认工作位于专用 SMP branch/worktree，并核对上一个相关不变量的状态；
7. RED 能低成本区分根因或验证不确定硬件行为时执行；若缺口已由源码、ABI 或官方规范直接证明，
   可以记录静态证据后实施，不机械制造 RED。

不得只根据旧文档或记忆修改并发代码。当前源码、汇编入口、调用方和测试入口都要重新核对。

### 4.2 修改申请必须包含

| 字段 | 内容 |
|---|---|
| 批次目标 | 本批只建立或修复哪个不变量 |
| 当前证据 | 当前代码位置、实际行为和 RED/缺口 |
| 修改范围 | 精确到文件、函数、类型或汇编标签 |
| 明确不修改 | 防止范围静默扩大 |
| 风险与预算 | L1/L2/L3、关键代码约数及明显超过 100 行的原因 |
| 非关键改动 | 预计注释、测试、文档和 Work Log |
| 并发影响 | 所有权、锁、原子顺序、中断和生命周期 |
| 验证方式 | 选择 T0-T3 验证档，并说明为何足够 |
| 回退边界 | 可以精确反向恢复的 hunk |

L3 申请必须完整包含上述字段；L2 可以使用精简版本。申请要说明为什么工作包结束时能够保持
内核可编译和语义安全，但不要求每个中间 patch 都形成独立提交。

### 4.3 必须重新确认的变化

出现以下任一情况，原批准失效：

- 要维护的不变量或风险等级发生变化；
- 关键代码从约 100 行显著膨胀到约 150 行以上且不能由原不变量解释；
- 原申请未声明却需要新增 unsafe、锁层级、IPI reason 或公共接口；
- 实际锁关系超出 lock-order.md 已批准的部分序；
- 实验结果推翻原根因并要求转向另一子系统；
- 需要触碰用户已有修改；
- 工作包结束状态必须依赖一个未批准的新不变量才安全。

文件数量变化、编译错误修复、同一接口的双架构对称实现、必要注释/测试/文档增加，不单独触发
重新确认，只要仍属于原工作包和风险等级。

## 5. 注释规范

注释要解释“为什么正确、与谁同步、失败会怎样”，而不是逐字翻译代码。

### 5.1 每个关键 hunk 的最低要求

紧邻注释至少说明：

- 当前 CPU、远端 CPU、任务或 MM 中谁拥有状态；
- 哪个锁、原子状态或关中断区保护它；
- 修改前后的合法状态；
- 对应的读取、唤醒或 ack 方；
- 是否允许睡眠、等待或调度；
- 单核退化路径和架构差异。

### 5.2 需要接近一行一注释的位置

以下位置原则上每条关键指令或语句都有直接注释：

- boot entry 的栈计算、CPU ID 保存、BSP/AP 分支和页表切换；
- trap 汇编的寄存器保存恢复、CSR 读写、特权级切换和返回；
- IPI doorbell、pending reason、mailbox 发布、读取和 ack；
- Acquire、Release、AcqRel、SeqCst 原子操作；
- PTE 修改、generation、TLB flush、shootdown 和 frame 延迟释放；
- LoongArch ASID 分配、epoch rollover 和 invtlb；
- runqueue 所有权转移和任务状态 CAS；
- unsafe 块、裸指针、UnsafeCell 以及 Send/Sync 实现。

机械性的连续寄存器保存恢复可以使用分组注释，但必须写明寄存器范围、栈布局和恢复顺序。

### 5.3 原子与锁注释

每个非 Relaxed 原子操作要说明：

1. 发布或获取了哪些数据；
2. 与哪个具体原子操作形成同步；
3. 为什么更弱 ordering 不够；
4. 重复 IPI、并发写入或超时时如何保持幂等。

新增或改变锁使用时，要说明锁顺序、是否关闭本地中断、是否可能进入等待点，以及为何不会和 IPI/trap 自锁。

### 5.4 禁止的注释

- “设置变量”“进入循环”一类复述代码表面的注释；
- 与当前实现不一致的未来时说明；
- 用 TODO 代替当前批次必须满足的安全条件；
- 用“当前只有单核”证明 unsafe、裸指针或 static mut 安全；
- 声称远程 TLB 已刷新，但代码只有本地 sfence.vma 或 invtlb。

## 6. 修改执行纪律

- 使用宿主环境支持的精确 hunk 编辑方式，禁止整文件重写；在 Codex 环境中使用 apply_patch；
- 不运行会重写整文件或全仓库的 formatter；
- 不在同批混合重命名、格式整理和行为变化；
- 不顺手修复无关 warning、typo 或邻近 bug；
- 在范围可能显著扩大时和工作包收尾时统计关键代码，不要求每次 patch 后重复计数；
- 新增测试不得放宽断言、扩大超时或跳过路径来制造 PASS；
- 未经用户明确要求，不委派 subagent 修改 SMP 代码。

工作包结束时必须可编译、可回退、语义闭合。中间 patch 可以暂时未编译，但不能提交或交付
假 IPI、无 ack shootdown、固定 CPU0 等 workaround。

### 6.1 超出范围或验证失败

如果正确修复超出批准范围：

1. 停止继续写关键代码；
2. 汇报已完成内容、实际行数和新发现；
3. 提出更小的拆分或新的批次申请；
4. 等待用户决定继续、保留还是撤销。

验证失败时先定位。若修复仍属于原不变量、风险等级不变且总体规模合理，可以在工作包内继续；
只有根因转移到新不变量、风险升级或规模明显失控时才重新确认。不得为了保持“少量多次”而把
已知的编译错误或对称架构实现留给下一批。

禁止使用 git reset 或 git checkout 清理工作树。需要撤销未提交批次时，使用精确反向 patch 并先
征得用户同意；已经提交且没有后续依赖时优先使用 `git revert`，存在依赖批次时先给出逐 hunk
回退顺序和影响，不能机械 revert 破坏后续不变量。

### 6.2 脏工作树

- 修改前记录 git status 和目标文件 diff；
- 不覆盖、整理或回退用户已有改动；
- 目标 hunk 与已有改动重叠时先请求专项许可；
- 无法可靠分离 agent 与用户改动时停止；
- 不删除无关未跟踪文件或历史证据。

SMP 实施默认从冻结基线创建独立 branch/worktree。人工审核后只有在用户明确授权 commit 时，
才把本批批准文件独立提交；不得为了“一批一提交”把用户无关修改一并暂存，也不得自行 push。

## 7. SMP 专项审查清单

### 7.1 BSP/AP 与启动

- 每个 CPU 在使用前获得唯一 boot stack；
- AP 使用的 stack 和 boot flag 不被 BSP 清 BSS；
- 只有 CPU0 执行全局初始化；
- AP 在访问堆和全局对象前 Acquire 观察 BSP 的 Release；
- 非法 CPU ID 和 online timeout 可诊断；
- Phase 1 AP online 后只进入 park loop，不调用旧 run_tasks，不使能普通 timer 中断；
- CORE_NUM=1 走同一实现的退化路径。

### 7.2 trap、IPI 与 timer

- 用户寄存器和 CPU-local 寄存器保存恢复完整；
- 内核 IPI handler 不分配、不睡眠、不获取普通业务锁；
- doorbell 前发布 payload，handler 正确清中断源并读取 reason；
- 重复或合并 IPI 保持幂等；
- 内核态 timer/IPI 只设置 deferred state，不直接切换任务；
- idle 检查、发布和休眠之间不存在 lost wakeup。
- IPI-only 与 timer-enabled 中断窗口分阶段验证，timer 回调工作延迟到安全点。

### 7.3 调度器

- TCB 只能存在于一个 runqueue 或一个 current 槽；
- 每次状态 CAS 都有成功、失败和重试语义；
- 不同时持有两个 runqueue 锁；
- 不嵌套 task.inner 与 runqueue 锁；
- 远程 enqueue 在释放锁后发送 IPI；
- current_task 返回 Arc，不制造伪 static 引用；
- 可变 current hint 有集中更新/失效协议，或改读权威对象；
- interruptible_queue 不作为 runnable queue，旧扫描不能绕过状态 CAS 重复入队；
- block、wake、exit、migration 和 affinity 有 focused race 测试。

### 7.4 MM、TLB 与 ASID

- PTE 修改明确区分页表是否已经发布；
- 已发布页表只通过统一 TLB batch 修改；
- generation、active mask、远程 flush 和 ack 顺序闭合；
- ack 前不释放或复用 frame、页表页、内核栈或 ASID；
- shootdown 等待路径自身能响应 IPI；
- LoongArch ASID 属于 MM，epoch rollover 做全核失效；
- RISC-V RFENCE 和 IPI fallback 提供相同上层语义。
- RISC-V stale 测试记录 victim 无 trap 窗口和 trap count，不能依赖 trap.S 的全量 sfence.vma；
- Phase 4 跨核用户测试保持 CPU/MM-only，不进入 Phase 5 才审计的共享子系统。

### 7.5 共享子系统

- 删除以单核为依据的 unsafe 安全证明；
- IRQ 可能访问的锁说明 irq-safe 策略；
- 持锁路径不 yield、schedule 或等待远端 ack；
- static mut 替换为原子、锁或 per-CPU 所有权；
- CPU0 housekeeping 与任意 CPU syscall 不重复推进全局状态。

### 7.6 阶段依赖复核

| 阶段 | 允许出现的并发 | 本阶段禁止提前引入 |
|---|---|---|
| 0/0.5 | 单 CPU 任务；锁原语/console focused test | AP 运行任务、普通 timer IRQ |
| 1 | AP online + park mailbox | AP run_tasks、远程 runqueue |
| 2 | IPI-only，随后 deferred timer | per-CPU runnable task |
| 2.5 | CPU0 单核状态 CAS、本地 TLB batch | remote shootdown、用户迁移 |
| 3a | per-CPU queue、目标选择、远程 enqueue | 默认开启 steal、用户 MM 跨核 |
| 3b | 可关闭的 work stealing | 普通用户任务跨核 |
| 4 | hermetic CPU/MM 用户测试 | 未审计 FS/net/device 并发 |
| 5 | 审计通过的共享子系统与普通用户任务 | 未证明的 unsafe/全局状态 |

## 8. 验证与证据

### 8.1 自适应验证档位

验证以“足以推翻本批最可能错误”为目标，不按固定仪式重复全矩阵：

| 档位 | 适用范围 | 最低验证 |
|---|---|---|
| T0 | 纯文档、注释、证据整理，不改变构建和测试判定 | `git diff --check` 与内容审阅；不编译、不运行 QEMU |
| T1 | 局部机械改造、私有 helper、单架构且由 cfg 隔离、无共享并发语义 | Docker 内受影响架构 build；共享代码或准备提交时补双架构串行 build；QEMU 仅在运行行为改变时执行 |
| T2 | 启动/per-CPU/共享原子的一项中风险不变量 | Docker 内相关架构 build；共享代码完成双架构串行 build；运行行为相关时做 CORE_NUM=1/2 focused QEMU |
| T3 | trap、IPI/ack、timer/idle 竞态、runqueue、TLB/ASID、frame 生命周期、锁序或 unsafe | Docker 内双架构串行 build；对应 focused QEMU；按故障模型选择 2/4/8 核和必要重复 |
| 阶段门禁 | 一个 Phase 的不变量准备合并 | 双架构 build、CORE_NUM=1 回归、该阶段 1/2/4/8 focused 矩阵及阶段要求的压力测试 |

补充规则：

- 文档/注释收尾后不重跑已经通过且源码未变化的构建；
- 架构专用代码不要求每次中间 patch 都编译另一架构，但工作包触及公共导出或准备提交时要补齐；
- 4/8 核、长测和高重复次数只在它们能增加竞态覆盖时执行，不作为每批固定动作；
- 能由编译、ELF/反汇编或单次 focused QEMU充分验证的性质，不重复跑完整用户测试；
- 调度、IPI 和 TLB 的真实并发竞态测试应使用 MTTCG；仅验证比赛启动命令兼容性时可直接采用
  官方命令，不强制额外采集宿主 vCPU 线程快照；
- 所有编译和 QEMU 仍必须在 Docker 内，rv64 与 la64 使用不同 nightly 时不得并行。

常用双架构构建命令：

~~~text
make rv64-kernel-build-only
make la64-kernel-build-only
~~~

### 8.2 结果分类

- PASS：所选验证档位的命令、退出码和关键结束标记可复核；
- FAIL：已执行并出现编译、panic、超时或断言失败；
- BLOCKED：环境、镜像、权限或前置资源阻止执行；
- NOT RUN：本批未执行。

报告必须写明选用的档位和未运行项。BLOCKED 和 NOT RUN 不得写成“预计通过”；既有失败要说明
是否与本批相关。

### 8.3 证据归档

证据成本同样分级：

- T0/T1：Work Log 记录修改范围、执行命令、退出码和关键结果即可，不强制创建独立 manifest；
- T2：保存可复核的命令/退出码/关键串口标记；完整日志只在结果不稳定或需要交接时归档；
- T3、阶段门禁、性能对比和难复现失败：写入当天唯一目录
  <code>docs/Work_Log/evidence/YYYY-MM-DD/</code>，使用批次前缀保存完整命令、环境、日志和判定；
- 容器 image/digest、mount、QEMU 版本在同一连续任务未变化时记录一次并引用，不在每次运行重复采集；
- 逐行语义行数账本只在明显超预算、L3 争议改动或用户要求时创建；
- 已有新鲜 PASS 后仅追加文档/注释，不因日志时间早于文档时间而重跑代码验证。

任何层级都不能把未执行项写成 PASS。声称高风险竞态或阶段完成时，必须有与该结论匹配的
持久证据；普通开发迭代不要求为每次成功构建保存整份串口日志。

## 9. 修改后详细汇报

完成一个批准工作包后必须汇报。L3 汇报后停止等待人工审核；L1/L2 若仍处于用户预先批准的
连续工作包序列，可在约定里程碑之间继续，不为机械子步骤重复停顿。

### 9.1 结论

- 批次编号与目标；
- 状态：完成、失败或阻塞；
- 是否完全落在批准范围；
- 风险等级与验证档位；
- 当前动作是“等待人工审核”还是“按已批准序列继续”，必须明确说明。

### 9.2 行数账本

L0/L1 可只报告 raw diff 和“无/约 N 行关键代码”；L2/L3 使用下表：

| 文件 | 关键新增 | 关键删除 | 关键合计 | 注释 | 测试 | 文档 |
|---|---:|---:|---:|---:|---:|---:|
| path | N | N | N | N | N | N |

给出 raw diff 和关键代码约数；超过约 100 行时解释保持不变量完整的原因。只有 L3、明显超过
约 150 行或存在分类争议时，才要求逐行账本、未分类行和辅助工具版本。

### 9.3 修改思路

报告要说明：

1. 修改前的数据流或控制流；
2. 实际竞态、所有权缺口或架构限制；
3. 选择的最小实现方案；
4. 单核和多核下为何成立；
5. 原子、锁、关中断或 TLB 顺序如何闭环；
6. 本批明确没有处理什么。

不得只写“增加 SMP 支持”或“修复竞态”。

### 9.4 逐项变化和风险

按文件、函数或汇编标签列出：

- 行为变化；
- 注释覆盖的不变量；
- 调用方和被调用方变化；
- 错误、超时和重复事件处理；
- 架构共有与专用逻辑边界；
- 未运行验证和尚未证明的场景；
- 下一批前需要人工裁决的风险。

报告末尾声明 mango-workflow 状态。若没有预批准序列，只提出一个下一工作包候选而不直接执行；
若已有预批准序列，说明将继续的编号和边界。

## 10. 明确禁止

- 未经批准直接编辑 L2/L3 SMP 代码，或让 L0/L1 修改实际改变高风险语义；
- 无说明地明显超过约 100 行关键代码，或借一个工作包混入独立不变量；
- 用压缩代码、删除注释或藏入测试规避行数；
- 为减少行数把多个状态变化塞进一行；
- 同批混合启动、调度、TLB 等多个不变量；
- 没有当前源码、官方规范、静态证据或必要 RED 时猜测性修复；
- 用固定 CPU0、全局大锁或关闭中断到底掩盖问题；
- weakening test、扩大超时或忽略失败制造 PASS；
- 验证档位不足却声称高风险不变量或阶段完成；
- 未经要求 commit、push、创建 PR 或越过未批准的工作包边界；
- 用单线程 TCG 结果宣称已覆盖真实 vCPU 并行竞态。

## 11. 批次结束条件

一个批次在以下内容全部交付后结束：

- 已统计实际关键代码行数并解释任何超出；
- 关键 hunk 均有符合要求的注释；
- 已执行风险档位要求的最小验证，或明确标为 BLOCKED/NOT RUN；
- 需要持久归档的 T3/阶段证据已保存；T0-T2 已在 Work Log 记录必要结果；
- mango-workflow A→D 已执行；
- 与风险相称的报告已提交；
- L3 已停止等待用户审核；L1/L2 是否继续遵循预先批准的工作包序列。
