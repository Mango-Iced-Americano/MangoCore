# 2K1000LA GMAC 驱动

## 硬件依据

星云板厂商 Linux 5.10 DTS 与 U-Boot 源码给出的硬件配置如下：

| 资源 | GMAC0 | GMAC1 |
|---|---:|---:|
| DWMAC 版本 | 3.70a | 3.70a |
| MMIO | `0x4004_0000..0x4004_7fff` | `0x4005_0000..0x4005_7fff` |
| MAC IRQ | 12 | 14 |
| PHY | Motorcomm YT8511H，MDIO 地址 0 | Motorcomm YT8511H，MDIO 地址 0 |
| 接口 | RGMII | RGMII-ID |

两路 PHY 地址相同并不冲突，因为每个 GMAC 有独立 MDIO 总线。当前驱动只接入
U-Boot TFTP 已验证的 GMAC0；GMAC1 和中断模式尚未启用。

厂商 U-Boot 的 `include/configs/loongson_2k1000*.h` 定义了
`CONFIG_DW_ALTDESCRIPTOR`。因此不能使用普通 DWMAC 描述符位布局：

- RX chain：control bit 14；
- TX chain：status bit 20；
- TX first/last：status bit 28/29；
- buffer size：13 bit。

## 初始化流程

`Gmac2k1000::new()` 执行以下步骤：

1. 通过 DMW2 强序非缓存别名读取 DWMAC 版本和 U-Boot 留下的 MAC 地址。
2. 停止 MAC/DMA，执行 DMA software reset，并关闭中断。
3. 通过 MDIO 校验 YT8511H ID `0x0000010a`，关闭 PHY auto-sleep，并应用厂商
   Linux 的 RGMII 时钟/发送延迟配置。
4. 从内核帧分配器取得低于 4 GiB 的描述符页和 RX/TX buffer 页。
5. 建立 48 RX + 16 TX 的 64 字节对齐链式 alternate descriptor ring；64 个槽位
   恰好占满一个 4 KiB 描述符页。旧版 8 RX + 4 TX 已由实板 A/B 证明会持续触发
   Receive Buffer Unavailable，不再作为生产配置。
6. 配置 DMA fixed burst、PBL=8、store-and-forward，启动 RX/TX。
7. 根据 YT8511 专用状态寄存器配置 10/100/1000 Mbps 和双工模式。
8. 注册为 `NET_DEVICE`，由 `SmoltcpDeviceAdapter` 接入现有协议栈。

SoC DTS 标记 `dma-coherent`；驱动仍在描述符 OWN 交接前后使用 `dbar 0` 保证
CPU/DMA 访问顺序。描述符地址寄存器为 32 bit，因此所有 DMA 帧都显式检查不越过
`0x1_0000_0000`。

## 地址与构建

直连调试固定使用：

```text
Mac/en8: 192.168.9.10/24
MangoCore eth0: 192.168.9.20/24
```

早期只读寄存器探针、逐包 `gmac_diag` 镜像和 SATA/GMAC 分阶段组合镜像已完成
驱动验收并从公共 Make 目标移除。相关 feature 和历史结果保留，生产及日常回归
不再暴露容易误用的中间镜像入口。

构建不运行测例、直接进入 Bash 的 GMAC0 Shell 镜像：

```bash
python3 -m pip install --user pyserial  # 首次使用时执行
python3 scripts/boot_2k1000_tftp.py  # 进入交互式上板向导
```

`boot_2k1000_tftp.py` 是 2K1000LA 的一键构建与上板入口：默认将宿主机
`en8` 配置为 `192.168.9.10/24`，启动 macOS 内置 TFTP 服务，把镜像校验后发布到
`/private/tftpboot`，自动检测 USB 串口，然后通过 U-Boot 执行 `ping`、`tftpboot`、
`crc32` 和 `iminfo` 校验，最后启动镜像。默认不会写 U-Boot 环境变量，只在当前会话
中设置网络参数。

向导会交互确认镜像来源、编译模式、网卡/IP、串口和执行模式。选择“编译新镜像”时，
固定在 Docker `os-dev` 容器中调用当前 develop 的板级 Make 目标；编译完成后才由
宿主机执行网卡配置、TFTP 发布和串口传输。无参数向导默认选择 `mainline`，支持：

- `shell`：GMAC 网络调试 Shell
- `run`：SATA 正式运行镜像
- `mainline`：SATA 持久根主线镜像
- `core-tests`：SATA 核心测试镜像
- `apk-persist`：APK 持久化 Shell

Docker 编译入口会先执行 `make -C os toolchain-setup`，再执行只读 preflight 和板级
构建，因此新容器会自动安装 `rust-toolchain.toml` 固定的
`nightly-2026-05-10`。如果宿主机的代理监听在 `127.0.0.1`，脚本会自动改写为
容器可访问的 `host.docker.internal`；Rustup/Cargo 缓存保存在 `os_dev_rustup` 和
`os_dev_cargo` Docker 命名卷中，后续重建容器不需要重复下载。

无参数运行会进入完整向导：

```bash
python3 scripts/boot_2k1000_tftp.py
```

需要脚本化调用时，使用 `--build-profile` 编译指定模式：

```bash
python3 scripts/boot_2k1000_tftp.py \
  --non-interactive \
  --build-profile shell \
  --build-mode release
```

若已有镜像，则继续使用 `--image`；这时不会触发编译。

只检查宿主机网络、TFTP、镜像和串口，不打开串口或操作板端时使用：

```bash
python3 scripts/boot_2k1000_tftp.py \
  --image kernel-2k1000-shell.ui \
  --prepare-only
```

如果 USB 网卡或串口不是默认设备，可显式指定：

```bash
python3 scripts/boot_2k1000_tftp.py \
  --interface en8 \
  --serial /dev/cu.wchusbserial1120 \
  --image kernel-2k1000-shell.ui
```

脚本使用的是 U-Boot 的 TFTP（不是带账号密码的 FTP）。默认启动后进入串口监视；
使用 `--no-boot` 可在完成 TFTP、CRC 和 uImage 校验后停在 U-Boot 提示符。

### 通过 HTTP 写入 SSD

如果需要把宿主机文件放到开发板的 SSD，脚本会启动一次性宿主 HTTP 服务，由板端
BusyBox `wget` 拉取到 `/persist` 下的临时文件。传输完成后脚本在板端核对文件长度和
SHA-256，成功才改名为最终路径并执行 `sync`；失败时不会覆盖原文件。默认端口仍为
`2121`（沿用旧 `ftp-upload` 参数名），服务只在本次传输期间存在。主线镜像的 `eth0`
地址会从启动后 Shell 自动探测；如果网络环境使用了无法从 `ifconfig eth0` 读出的地址，
可显式传入 `--ftp-board-ip`。

```bash
python3 scripts/boot_2k1000_tftp.py \
  --non-interactive \
  --build-profile mainline \
  --ftp-upload ./payload.tar \
  --ftp-destination /persist/incoming/payload.tar
```

`--ftp-destination` 必须位于可写 SSD P4 的 `/persist` 树中；嵌套父目录会在传输前创建。
如果板子已经从 SSD 启动并停在 P3 shell，可改用 `--upload-only`，跳过编译、TFTP、U-Boot
命令和复位，直接完成文件传输。该 HTTP 服务只绑定直连调试网段，不应暴露到生产网络。

该镜像仅使用 initramfs，不依赖 SSD。`la64-2k1000-shell` 将
`profile=rescue` 注入内核命令行，PID1 会跳过 `/sdcard`、`/tools` 的持久化挂载并直接
托管 initramfs 内的 `/rescue/sh`；因此不会读取或改写磁盘上的 `os_test.conf`。

### SATA 持久根主线

`la64-2k1000-mainline` 是当前 2K1000LA 的主线启动入口。它使用
`block_sata`，以 `root=/dev/sda3 profile=mainline` 启动；内核把 P3 挂到早期
`/sdcard` 后，PID1 校验 init 或静态 `/bin/busybox`，将 `/proc`、`/sys`、`/dev`、
`/dev/shm`、`/run` 和临时 `/tmp` bind 到 P3，再 `chroot` 并优先执行 init；当前实板
P3 没有 init 时显式进入 `/bin/busybox sh -i`。
因此测试用的 initramfs 只负责加载内核、设备发现和救援，不再作为主线用户态根。

```bash
make -C os la64-2k1000-mainline MODE=release
python3 scripts/boot_2k1000_tftp.py \
  --non-interactive \
  --build-profile mainline \
  --build-mode release
```

`run`、`core-tests`、`apk-persist` 仍保留原有 initramfs + 挂载点合同，便于回归
官方测试和持久化探针；新系统功能应优先在 `mainline` 根上验证。SATA 原始盘及
MBR 分区统一使用 Linux 兼容的 `/dev/sd*` 命名，P1/P2/P3 对应 `/dev/sda1`、
`/dev/sda2`、`/dev/sda3`。

### 吞吐诊断镜像

`net_perf_diag` 是默认关闭的性能诊断 feature，只增加两秒窗口计数，不改变正式
镜像的 TCP 缓冲区、ACK 策略或 48/16 GMAC ring。统一构建入口支持附加一个单变量
feature：

~~~bash
# 生产配置：48 RX / 16 TX，smoltcp 默认 delayed ACK
make -C os la64-2k1000-net-perf-shell \
  NET_PERF_IMAGE=kernel-2k1000-net-perf-shell.ui

# 仅关闭 delayed ACK，用于协议栈单变量诊断
make -C os la64-2k1000-net-perf-shell \
  NET_PERF_EXTRA_FEATURES=net_ack_immediate \
  NET_PERF_IMAGE=kernel-2k1000-net-perf-ack.ui
~~~

诊断输出分为三层：

- `[net-perf][poll]`：全量/单栈 poll 次数、实际 progress 次数、锁竞争和 CPU tick；
- `[net-perf][tcp-rx]`：用户态接收调用、字节、平均请求大小及 `EAGAIN`/EOF；
- `[net-perf][gmac]`：GMAC RX/TX 包和字节、无效帧、描述符繁忙，以及当期新出现的
  `RU`、`OVF`、`RPS`、`TU` DMA 事件。

DWMAC `DMA_STATUS` 低 17 位是 write-one-to-clear 事件。诊断代码每次报告后只回写
该事件范围，不触碰高位 TX/RX process state；因此下一窗口的 `ru/ovf/rps/tu`
表示新事件，而不是启动后一直黏住的历史状态。位定义与清除方式对照 Linux
[`dwmac_dma.h`](https://github.com/torvalds/linux/blob/master/drivers/net/ethernet/stmicro/stmmac/dwmac_dma.h)
和 [`dwmac1000_dma.c`](https://github.com/torvalds/linux/blob/master/drivers/net/ethernet/stmicro/stmmac/dwmac1000_dma.c)。

吞吐 A/B 必须使用同一台 Mac 上的本地 HTTP 大文件并绕过代理，连续执行三次；先
隔离 GMAC、ARP、IP 和 TCP，再测 Clash/PyPI。历史 8/4 与 48/16 单变量镜像及结果
保留在工作日志和实板日志中，不再通过正式构建 feature 生成。

需要 SATA、可写 scratch、GMAC、DHCP 和交互式 Shell 的联合环境时，统一使用
下述 HTTPS curl Shell；它取代此前的分阶段联合与 DHCP Shell 目标。地址、默认
路由及 DNS 分别可通过 `ifconfig eth0`、`/proc/net/route` 和
`/etc/resolv.conf` 查看。

先在 QEMU 构建并运行自包含 HTTPS curl Shell：

~~~bash
make -C os la64-qemu-curl-shell
make -C os la64-qemu-curl-shell-run
~~~

通过 QEMU 门禁后，再构建同一运行时的 2K1000LA DHCP Shell 镜像：

~~~bash
make -C os la64-2k1000-curl-shell
python3 scripts/boot_2k1000_tftp.py --image kernel-2k1000-curl-shell.ui
~~~

curl 8.19.0、静态 Mbed TLS 3.6.7、CA bundle、动态加载器、
glibc/NSS/resolver 和配置文件均打入 initramfs，不依赖或改写 SSD 工具分区。
构建脚本固定两份源码的 SHA-256，并使用通用
`-march=loongarch64 -mabi=lp64d`，避免依赖未启用的 LSX/LASX 上下文。
initramfs 还记录 `/etc/build-epoch`；NTP 不可用时 init 用该构建时间作为实时钟
下界，使证书有效期检查不会退回到过时的硬编码日期。

HTTPS 验收必须同时覆盖成功和证书拒绝，且成功命令不能带 `-k`：

~~~bash
/bin/curl -fsS --max-time 30 -o /tmp/https.body https://www.baidu.com/
echo $?
wc -c /tmp/https.body
/bin/curl -sS --max-time 30 -o /dev/null https://wrong.host.badssl.com/
echo $?
~~~

预期第一条返回 0，错误主机名证书返回 curl 60。

构建自包含网络回归镜像：

~~~bash
make -C os la64-2k1000-net-tests
python3 scripts/boot_2k1000_tftp.py --image kernel-2k1000-net-tests.ui
~~~

该目标组合 `sata_scratch_rw + gmac_dhcp + board_shell`，并把当前构建的
`/bin/inet_test` 和 curl 运行时打入 initramfs。推荐依次执行：

~~~bash
/bin/inet_test core
/bin/inet_test external
~~~

使用 macOS 互联网共享时，U-Boot 仍通过 `en8=192.168.9.10/24` 完成 TFTP；
内核启动后从 `bridge100=192.168.2.1/24` 获取 DHCP。ClashX 等 TUN/增强模式
会把 DNS 结果改为 `198.18.0.0/16` Fake-IP，转发流量无法按普通共享路径出网，
测试前应关闭 TUN 模式。RESET 按键若出现接触粘连，应使用断电重启，避免在
U-Boot 命令输入或 TFTP 期间连续冷复位。

## 已验证结果

- 两路 DWMAC version 均为 `0x0000d137`。
- 两路 PHY ID 均为 `0x0000010a`；GMAC0 链路为 1000 Mbps/full，GMAC1 未接线。
- GMAC0 自有描述符位于第二 DRAM bank，RX/TX OWN 可正常交接并循环复用。
- RX frame length 包含 4 字节 FCS，交给 smoltcp 前必须减 4。
- Mac 能通过 ARP 学到 `8e:f8:cc:05:ed:1b`，并持续 ping `192.168.9.20`。
- 路由器 LAN 协商为 100 Mbps/full，DHCP 获得 `192.168.1.3/24`，网关和 DNS
  均为 `192.168.1.1`；网关 ping 为 2/2、0% 丢包。
- glibc curl 经 `IP_RECVERR + sendmmsg` 完成 A/AAAA 查询，IPv6 无路由后回退
  IPv4，并从 `www.baidu.com` 收到 HTTP 200、2381 字节，返回码为 0。
- macOS Wi-Fi 互联网共享下，DHCP 获得 `192.168.2.2/24`，网关和 DNS 均为
  `192.168.2.1`；连接 Mac 本地 HTTP 服务返回 200，证明 GMAC/TCP 本地链路完整。
- `kernel-2k1000-net-tests.ui` 实板通过 `inet_test core` 29/29 和
  `inet_test external` 9/9，两组返回码均为 0；外网 TCP、HTTP、UDP DNS 和默认
  路由均通过。
- `kernel-la-curl-shell` 在 QEMU DHCP/NAT 环境下以默认 CA 校验访问
  `https://www.baidu.com/` 返回 HTTP 200、2443 字节；访问
  `wrong.host.badssl.com` 因 CN 不匹配返回 curl 60。
- `kernel-2k1000-curl-shell.ui` 在 macOS Wi-Fi 互联网共享环境取得
  `192.168.2.2/24`，同样完成 HTTPS 200/2443 字节与错误主机名返回 60；NTP
  不可达时成功使用镜像构建时间校准证书验证所需时钟。
- 相同 MangoCore TCP/用户态接收路径在 LA64 QEMU 中，从宿主本地 HTTP 服务连续
  读取 71.9 MB，delayed ACK 三次平均约 19.93 MB/s；immediate ACK 三次平均约
  19.71 MB/s，差异约 1.1%，在测量噪声内。QEMU 结果排除了通用 TCP 路径是实板
  约 0.15--0.20 MB/s 吞吐的唯一主因，但不能代替真实 GMAC A/B。
- QEMU 空闲期每两秒约执行 7.3--8.1 万次全量 poll，占模拟单核约 24%--26%；传输
  活跃窗口最高约 68%。这是待优化的次级调度开销，但通用路径仍可达到约 20 MB/s，
  暂不据此修改正式轮询策略。
- 实板使用同一 8 MiB Mac 本地 HTTP 文件、同一用户态和 delayed ACK 连续三轮：
  旧 8/4 ring 平均 `129649 B/s`，每个活跃两秒窗口均新触发 `RU=1`；48/16 ring
  平均 `12286495 B/s`，提升约 94.77 倍，活跃窗口 `RU=0`，且两者均
  `OVF=0`、`RPS=0`、`rx_bad=0`。这确认 8 项 RX ring 持续耗尽是板端本地下载
  约百倍退化的根因。
- 保持 8/4 ring、仅关闭 delayed ACK 后平均 `129296 B/s`，相对旧基线低约 0.27%，
  `RU/TU` 仍持续出现；因此 delayed ACK 不是该问题的原因。48/16 下仍偶见新鲜
  `TU=1`，但无 `tx_busy_drop/tx_reject` 且接收吞吐已恢复，TX underflow 作为独立
  后续问题处理，不能混入本次根因结论。
- 将 48/16 固化为默认后，以不含 `net_perf_diag` 的正式
  `kernel-2k1000-persist-shell.ui` 再跑三轮，得到 12,353,974/12,670,560/
  12,563,457 B/s，平均 `12529330 B/s`，相对旧生产基线提升约 96.64 倍。正式镜像
  启动明确报告 `rx=48 tx=16`，证明收益不依赖诊断 feature。
- 同一正式镜像通过 Clash 显式代理完成 PyPI HTTPS 200；同一 2 MiB Cloudflare
  对象在 Mac 与板端分别为 863,447 和 722,559 B/s，已处于同一数量级。此后公网
  速度较慢应先检查代理节点/远端，不能再归因于已修复的本地 RX ring。
- 片上 APB RNG 已通过 DMW2 地址 `0x800000001fe2b000` 接入统一 ChaCha20
  CSPRNG；实板启动识别 `2k1000-rng`，`getrandom` 与 `/dev/urandom` 回归连续
  运行 5 次全部通过。

## 后续阶段

1. 对生产 48/16 ring 镜像运行本地 HTTP、HTTPS 和长时间双向 TCP/UDP 回归，确认
   无 RU、描述符越界、内存泄漏或链路恢复退化。
2. 分析仍偶见的 TX `TU`，增加必要的 DMA underflow 恢复和 TX 双向压力测试。
3. 接入 ICU IRQ12，保留 NAPI 风格预算轮询，降低空闲轮询开销。
4. 运行 veth、网络 LTP、iperf 和 netperf 实板回归。
5. 随机数链路已经消除全零和弱时间种子，功能性 API 鉴权不再受该问题阻塞；
   长期生产使用前仍需评估片上 RNG 熵质量，并实现运行期周期重播种和密钥存储边界。
6. 增加 LLM API POST、鉴权、超时和流式响应的端到端回归。
7. 评估 GMAC1 和 MAC 地址持久化来源。
